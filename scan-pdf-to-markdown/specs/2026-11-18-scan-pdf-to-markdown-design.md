## 1. 用户拿到什么

一次转换交付一个可移动的结果目录。日常阅读、构建问答库或做“Vibe 知识大赏”，取走 `document.md` 和它相对引用的 `assets/` 即可。正文按原文组织，疑点显示在文字、表格或图片出现的地方。查证时用块标识回到扫描原页。需要修正或重建时使用完整结果目录和同一份源 PDF。

Skill 随包提供 `scripts/scan_pdf.py`，两个入口使用下面的同一套操作。给 Agent 一份本地 PDF 和输出位置，它调用 `parse`，返回正文、报告的位置以及需要核对的页或块。CLI 用户可直接运行脚本。

```sh
python3 scan_pdf.py parse 扫描件.pdf --output 初次结果
python3 scan_pdf.py render 初次结果 --source-pdf 扫描件.pdf --output 重建结果
python3 scan_pdf.py verify 重建结果 --source-pdf 扫描件.pdf
```

`parse` 负责识别，取得原始结果后即走与 `render` 相同的生成过程。`render` 默认沿用输入结果内的复核记录，也可用 `--review 文件` 提供更新后的完整记录。`verify` 只读核对已经落盘的结果，使用该结果随附的复核记录。三种操作都返回通过、降级或失败及其原因。通过或降级的结果可发布，降级须在输出与报告中明确显示。失败返回非零退出码。

## 2. 一次识别，保存可重放的原始资料

**引擎选择。** 建议使用本地 MinerU 4.x 的无状态 CLI，识别整份 PDF，选择支持 OCR、表格和公式的 Basic 档，输出 ZIP。另一条可行路线是独立 Python 进程调用 MinerU SDK 并保存同一结果包。CLI 已提供这个进程边界和文件接口，独立 SDK 包装在此处会重复这两项职责。具体引擎版本以通过真实样本验收的版本为准。[CLI 文档](https://opendatalab.github.io/MinerU/usage/cli_tools/) · [档位说明](https://opendatalab.github.io/MinerU/usage/tiers/)

只读打开源件，记录 SHA-256、物理页数、逐页裁切框和旋转角。从只读快照运行识别，使摘要和引擎输入始终对应。发布前核对原件身份。安装基线使用 ONNX/CPU。新会话中的 CLI 和 Skill 都采用这组缺省值。调用者明确选择的环境变量或配置文件后端、设备优先，沿用 MinerU 的配置路径。保留引擎 ZIP 原字节及其摘要、生产版本、实际识别模式。缺少本地模型时给出依赖诊断。只有 `parse` 使用 OCR 环境，重建和核验仅需能读取 PDF、ZIP、结构化记录和图片的本地环境。

| 内容 | 保存位置与职责 |
| --- | --- |
| 识别依据 | `raw/engine.zip` 和 `raw/source.json` 保存引擎包及上述身份。原始记录定位到 ZIP 内的 `middle_json.json` 和实际对象路径。 |
| 阅读材料 | `document.md` 带物理页和正文块的 HTML 注释。`assets/` 保存可直接打开的图片，正文中的链接始终相对于 Markdown。 |
| 来源记录 | `blocks.jsonl` 逐块保存有效内容、定位、坐标、资产引用及疑点。`source-map.json` 保存源件身份、页状态、坐标转换和排除区域，供逐块记录引用。 |
| 复核与结论 | `review.json` 在有原页复核时随结果保存。它是可重放的复核输入。`qa-report.md` 根据当前文件和复核输入生成，列出完整性检查、抽查范围与未解决项。 |

首版读取引擎公开的 `docvortex.middle` 协议 2.0，有序页面和块是回源依据。从随包的 `structured_content.json` 取正文时，逐页核对顶层块的次序和类型。嵌套块沿 MiddleJson 的原始路径定位，图片使用包内实际引用的成员。组合块的题注、列表子项等须保留到原始子记录的定位关系。引擎生成的整篇 Markdown 会改变部分跨页内容的呈现，直接按其中的文字反查块会混淆重复句。包格式不受支持或必要资产缺失时指出具体问题。[输出合同](https://opendatalab.github.io/MinerU/reference/output_files/) · [块结构规范](https://opendatalab.github.io/MinerU/next/middle-json/current-medium/)

## 3. 页、块与 Markdown 的对应关系

**页覆盖。** 用原 PDF 的页清单核对引擎的整本标记和来源页索引，`page_idx + 1` 为物理页码。缺页、重复页或来源索引越界属于完整性失败。引擎返回了该页但没有正文时，查看原页渲染。原页确实空白才记为空白。有正文却未识别时保留页标记、失败说明和原页线索。尚不能判定的页面在正文及报告中列为待核对。

**混合页与阅读顺序。** 每页采用一份覆盖整张可见页面的有序识别结果。对同时含原生段落与扫描文字的页，使用能读全页图文的 OCR 模式。只从这份结果取一次正文。PDF 文本层可用来核对已识别内容。两个位置的相同文字分别保留。块按引擎给出的阅读顺序排列，保留续段、列表和题注关系。多栏或跨页接续存疑时，在正文标出待核对的物理页。引擎是否实际收齐混合页两部分由 A1 对照原页验证。

**块身份与坐标。** 每个正文块有由物理页、页内原始块索引及必要的子路径确定的 ID。块记录保存原始 JSON 定位，组合内容保留所有来源定位。原始框连同坐标空间、单位一起保存。对于上述协议的 PDF 顶层归一化框，横坐标乘与框同向的引擎页宽，纵坐标乘相应页高，再依据裁切框与旋转关系换算到原页未旋转、左上原点的点坐标。记录变换依据，按实际坐标空间判界。子项没有独立框时保留页和子记录，注明原因。转换依据不足时保留原框并记录原因。已有框数值非有限、边界倒置、越界或零面积时判失败。[块结构规范](https://opendatalab.github.io/MinerU/next/middle-json/current-medium/)

**阅读材料。** 同一组有序块生成 Markdown、块记录与来源映射。列表普通文字按字面显示，包括 Markdown 示例和含下划线的标识符。结构化行内公式、上下标及实际配图按其类型呈现。标题恢复层级，列表保留项序。简单表格按已知行列生成 GFM，保留行名、表头、单位与单元格归属。图片与原图题相邻输出，图片字节绑定至所属记录。复杂表格保留可验证的行列结构，公式保留可核实的表达式。引擎标记不确定、表格结构不一致或原页复核发现问题时，正文就地显示疑点。无法还原的表格或公式优先使用随包的原区域图，缺图时按已验证的坐标从源 PDF 裁取。边界不明则指向物理页。重复页眉等排除项记录页、位置、原文及原因。每个引擎内容块都能对应到正文、排除项或显式疑点之一。

## 4. 原页复核、更正与免 OCR 重建

以表格单元格被识别为 `18`、原页印为 `13` 为例。读者告诉 Agent 表格位置或错误数字即可。Agent 根据表头与行名确定具体单元格，从块 ID 找到物理页与原始表格记录，查看原页相应区域。确认是 `13` 后，Agent 准备复核记录并调用 `render` 生成新目录。仍看不清就保留疑点。在这个过程中原引擎记录始终保存 `18`，新正文和块记录显示 `13`，报告列出更正位置。

一份复核记录可以保存整页抽查与个别问题的结论。记录绑定源 PDF 和原始包摘要，具体项定位到页或块，注明原页依据和结论（确认、更正或存疑）。复核记录以该范围最终确认的内容、顺序和图片摘要为准，对更正项同时保留原值。渲染规则变化导致这部分可见内容不同时，相关结论转为待复核。更正作用于生成 Markdown 之前的块内容，以块、必要的单元格位置及原值为条件。可通过 Skill 准备这份文件，直接使用 CLI 的调用方也可提供同一格式。目标不存在、原值不符或更正相互冲突时，整次重建失败并指出对应项。修改富文本格时保留未改文字的行内格式。原值和替换值不足以唯一确定格式归属时，重建失败并指出块 ID、行和列。单纯确认某页已看过，不能清除其中仍有争议的项。

图文混排中的纯插图页须对照整张原页，明确确认该页只有已交付的插图，且每个图块均有与当前图像绑定的确认。复用页项的 `page_state` 表达「仅插图」；旧值 `has_content` 继续仅表示有内容。原页还有印刷文字、图块存疑、图像未核实或确认过期时，正文和报告仍须定位未解决项。整本未取得可读正文时沿用第 5 节判定。

重建先核对源 PDF、原始包和复核记录的绑定，再按来源顺序恢复块，应用有效更正，生成所有派生文件。新结果携带同一份原始资料及本次采用的完整复核记录，下一次重建可直接沿用。若用户提供了不同 PDF，立即报源件不符。给错复核文件同样指出不匹配，保留既有结果。相同输入、规则与复核记录应得到相同的正文、映射和图片字节。复核报告中的处理状态须与该目录的实际内容一致。

## 5. 核验与发布

`verify` 从磁盘读取源件、结果和图片。它核对原件及原始包的摘要，逐页对齐原页清单，逐块解析 Markdown 的来源标识并检查与 JSONL、实际原始记录的对应，从原始资料与随包的复核记录重算预期内容，核对实际正文、块内容和更正位置。按阅读器语义提取落盘正文中的实际图像引用，逐一核对相对路径与登记资产；悬空或未登记的引用使核验返回 1，并指出引用。字面示例和代码中的图像语法属于文字。检查坐标合法性、图像可解码性与摘要，异常定位到页、块或文件。生成时调用同一核验逻辑。另以原页叠框和人工可读的图文对照检验定位与内容的真实性。

| 优先判定 | 用户看到的结果 |
| --- | --- |
| 失败 | 身份或完整性检查失败，或原件有正文而整本没有可读正文。给出原因和可用的诊断位置。旧结果保留。 |
| 降级 | 完整性通过且正文可用，但规定的原页复核未完成、局部 OCR 失败或仍有疑点。正文就地提示内容疑点，报告列出未闭合页或块。 |
| 通过 | 完整性通过，首、中、末页、出现的难版面及所有未知或失败项已对照原页，已发现的问题均经核实或修正。报告列明实际复核范围。 |

**整本无可读正文时先核实页覆盖。** 若仍有页无法判定是否空白，首次 `parse` 返回失败，在诊断位置保留完整原始包、逐页线索和候选目录，不发布到目标路径。用户可从这个目录执行 `render` 并提供原页复核记录。确认各页都为空白后，保留每一页的标记，按实际复核范围判定通过或降级。确认原页有正文而仍未恢复任何可读内容时继续判失败。输入不可读等早于识别的故障只有错误诊断。

新结果先在目标父目录写入独立暂存目录，再按上述结论发布到新的目标目录。目标已存在、两个任务争用同一目标或运行中断时，保留先前可用结果。发布必须以目标尚不存在为条件一次完成，不能用先检查、再覆盖的两步写法。`verify` 发现成品损坏时返回当前诊断，原包内的历史报告不替代本次核验结果。

## 6. 直接验收

按[需求的 A1–A5](./2026-11-18-scan-pdf-to-markdown-requirements.md#3-直接验收)在仓库外保存真实扫描件、结果与复核证据。先从原页记下指定小节的原句、图题和一个表格值，供独立核对。下面是产品验收动作。

| 场景 | 决定是否满足需求的观察 |
| --- | --- |
| A1 阅读与模型取材 | 移动整个结果目录，在阅读器核对页序、标题、列表、图题和顺序。把 Markdown 和配图单独交给模型，让它引用指定小节、按指定行列读数并指出已标记的疑点，回到样张逐项核对。混合页原生段与扫描段各出现一次，异区同文仍能分开。 |
| A2 逐块查证 | 各从一个段落、图和表的 ID 找到确切原始记录与物理页。在旋转页上把可用矩形画回原图，框住同一内容。合法缺框的子项仍能回到页和记录，并能看到缺框原因。 |
| A3 三种质量结论 | 分别对照空白页、失败页与难辨的公式或表格，核对正文和报告指向同一处。完整但未复核的结果为降级。完成所需复核且无未决问题的结果为通过。移走副本中的配图后核验应失败并定位引用。用空白未明且无可读正文的候选验证失败诊断、旧结果保护及确认全空后从候选重建。 |
| A4 重建与更正 | 禁用 OCR，从原始资料先重建一次，比对正文、映射、图片摘要与复核结论。对照原页修正一个数字后，再从修正包重建，确认数字及其行列、来源和更正记录一致。旧包仍能复现旧值。换入同名不同内容的 PDF 应停止。 |
| A5 两种入口 | 在仓库外运行 CLI，再从已安装的 Skill 对同一样本发出自然语言请求。两边均能打开正文和报告、读到配图、逐块查回原页，质量判定一致。 |

## 7. Karpathy 精简与自检

- **基线。** 新模块目前只有规格。仓库现有 PDF 翻译入口有源文件识别、页几何和区域裁剪，但明确拒绝直接物化纯扫描件。图文媒体 OCR 接收单图，返回拼接文本。两者的输出都不能承担逐块回源。新 Skill 沿用随包分发脚本的方式，直接使用 PDF 库读取几何、渲染区域，避免安装时依赖另一个 Skill 的私有目录。[PDF 勘察入口](../../tech-doc-translator/skills/tech-doc-translator/scripts/prepare_pdf_source.py) · [几何及裁剪实现](../../tech-doc-translator/skills/tech-doc-translator/scripts/_pdf_source.py) · [单图 OCR](../../online-media-reader/skills/online-media-reader/scripts/omr/ocr.py)
- **假设与差异。** 需求 V0.2 已批准。Basic 单引擎、Agent 准备复核记录，以及整本无可读正文且空白未明时保留失败候选，均为本设计的选择。V0.1 草案只接收 raw 路径，本版从结果目录重建，以便自动沿用更正。尚无已发布调用者，既有模块的行为未发生变化。本机当前 PATH 未发现 `mineru-kit`，混合页收齐、表格保真和旋转坐标均待实测。
- **最小方案。** 第 2 节比较两种可行的 MinerU 接入方式。复用 CLI 的整本结果包与结构化正文，再补正文标记、源件绑定和复核记录，足以支撑两个入口及离线重建。保留独立的落盘核验，因为移动或损坏可发生在发布之后。
- **删除审计。** 第 1–2 节共用入口和产物合同（R5、R6）。第 3 节用同一组块同时生成正文与映射（R1–R3）。第 4–5 节将复核输入和派生报告分开（R4、R5），删除旧设计允许核验时另传记录的路径，防止旧正文借用新结论。
- **直接验收。** 第 6 节逐项保留 A1–A5，并用真实取材、旋转页叠框、损坏图片、重放更正和两种入口来证明各项交付。文档评审阶段尚无运行结果。

V0.3 对照现有 `parse/render/verify` 和复核格式，仅修订第 2–5 节的相应行为。列表复用字面转义，实际图链由独立 Markdown 阅读器核验；同一解析器恢复表格结构并保留单位；页、图仍沿用原摘要，各入口共用 OCR 子进程。与扩充富文本编辑协议、另建图页复核文件或改写用户全局 OCR 配置相比，这些选择可以用现有数据表达所需结果。直接验收覆盖字面图链与真实缺图、`13 m²` 更正与回放、纯插图与漏掉扫描说明的对照页、新会话两种入口及配置覆盖。
