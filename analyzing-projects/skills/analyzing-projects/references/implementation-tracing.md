# 实现追踪

## 内容

- 深度完成标准
- 每个主要流程的四层输出
- 完整执行栈
- P0/P1/P2 分级
- P0 函数逐步骤源码分析
- 强制函数级输出模板

## 职责

本参考只规定如何追踪 `SKILL.md` 已选定的每一个主要流程。适用范围、主要流程清单、证据术语、交付物和全局完成门以 `SKILL.md` 为准。

## 深度完成标准

列出符号、调用关系、字段或源码位置不等于完成实现分析。每个主要流程只有同时具备四层输出、完整执行栈、P0/P1/P2 分级、每个 P0 的完整函数模板、逐步骤实际源码、重要下游递归闭包和跨节点总结时，才完成函数级分析。

## 每个主要流程的四层输出

每个主要流程的分析按四层分层输出组织：

1. **端到端执行栈（导航层）：** 从真实入口到最终输出、持久化、外部消费者或项目所有权边界。
2. **关键符号总表（索引层）：** 汇总符号角色、输入、决策、输出/副作用、下游、深度和证据。
3. **函数级源码深度分析（核心分析层）：** 对每个 P0 节点重复执行本文件的完整函数模板。
4. **跨节点系统行为总结（系统行为层）：** 汇总数据演化、状态转换、错误传播、异步延续、一致性和不可逆副作用。

第一、第二层不能替代第三层；第三层不能省略第四层需要综合说明的跨节点行为。

## 完整执行栈

执行栈覆盖实际存在的同步调用、异步 continuation、回调、事件生产/接线/消费、动态分派和跨语言/native 绑定。每一跳记录文件、符号、准确行号、关系类型、调用条件、关键输入输出，以及适用的 `SOURCE`、`TEST`、`CALL-CHAIN` 或 `UNVERIFIED`。

静态证据无法唯一确定动态路径时，列出有证据的候选路径、运行时选择机制和无法确认的部分，标记 `UNVERIFIED`，不得把候选路径提升为确定事实。

## P0/P1/P2 分级

| 级别 | 对象 | 分析要求 |
|---|---|---|
| P0 | 主要流程入口、跨模块枢纽、关键算法、状态转换、数据契约、失败边界、外部副作用和性能关键路径 | 应用完整函数模板、逐步骤源码绑定和递归深度闭包 |
| P1 | 支撑主要流程但不直接决定关键行为的业务函数 | 函数签名、核心逻辑源码、直接下游和证据 |
| P2 | 叶子工具、简单转换和标准库封装 | 符号、用途和必要证据，默认不展开内部步骤 |

P1/P2 用于控制非关键细节，不得把决定主要流程核心行为的项目自有函数降级以逃避 P0 完整分析。

## 每个主要流程的执行顺序

1. 确认真实入口、触发条件、前置条件和最终出口/消费者。
2. 建立完整调用链，列出链上的全部关键符号和直接下游。
3. 按 P0/P1/P2 分级。
4. 对每个 P0 节点执行完整函数级模板。
5. 对决定核心行为的重要项目自有下游递归执行同一完整模板。
6. 递归直到关键行为闭合或到达经过证据确认的项目所有权边界。
7. 汇总跨节点数据、状态、失败和副作用。
8. 检查该流程是否满足全部深度完成条件，再开始下一个主要流程。

## P0 函数逐步骤源码分析

每个 P0 函数必须：

1. 给出完整文件路径、准确行号和完整函数签名。
2. 说明直接及关键间接调用者、触发条件和前置条件。
3. 按真实源码顺序拆分语义步骤。
4. 为每个被描述的语义步骤附对应的连续实际源码块，并标注文件路径和行号范围。
5. 紧邻源码块解释该步骤的实际行为、关键变量、输入输出、数据形态、状态变化和下游影响。
6. 完整说明实际存在的分支、循环、短路、fallback、缓存、重试、并发和异步 continuation。
7. 列出所有直接下游调用，以及参数、返回值和错误映射。
8. 说明返回值、状态修改、外部副作用、消费者、错误传播、恢复、清理和部分成功。
9. 对重要下游递归执行同一完整模板。
10. 标注所有适用的 `SOURCE`、`TEST`、`CALL-CHAIN` 和 `UNVERIFIED` 证据或缺口。

可以把连续的普通语句组合成一个语义步骤，但每一个已经写出的步骤都必须有实际源码。不能描述一个步骤后只给摘要或行号；不能为了减少代码量省略改变语义的分支、状态修改、错误路径或副作用。

### 执行逻辑源码块格式（冻结验证器兼容）

P0 `执行逻辑` 的编号步骤仅使用三反引号源码围栏；不得使用 `~~~` 或其他围栏标记。每个源码围栏的首行必须是相对项目根目录的 `# path:start-end`；`path` 不得是绝对路径或包含 `..`，行号范围必须可解析且与实际源码一致，单行也写 `N-N`。源码围栏闭栏后立即为 `**源码分析**`，中间不得插入其他内容。

P1/P2 不使用 `执行逻辑` 保留标题；它们应按各自分级要求呈现，不得伪装成 P0 完整模板。P1/P2 的实际源码块仍采用上述三反引号围栏、相对路径 `# path:start-end`（单行 `N-N`）和紧邻的 `**源码分析**` 的可解析格式，但此格式要求不新增逐步骤展开或完整模板义务。

## P0 深度闭包

P0 函数调用的项目自有函数，只要直接决定当前流程的关键算法、状态转换、数据契约、控制流、错误处理、性能路径或外部副作用，也必须提升为 P0，并递归应用完整函数模板。

递归持续到该主要流程的关键行为已经闭合，或到达行为无关的 P1/P2 叶子、最终消费者或经过证据确认的项目所有权边界。不得因为调用层数较深、跨模块、进入 native 代码、输出已经很长或已有调用链图而停止。

## 核心 CPU/GPU/native 实现

当项目自有 CPU/GPU/native 函数是主要流程的核心算法时：

- 展示完整函数体；只有函数中存在可明确隔离且不影响算法的样板代码时，才可展示足以完整还原算法的连续代码，并说明省略范围。
- 对决定计算、同步、内存访问、边界处理、shape/device 和数值行为的关键语句逐行解释。
- 从上层 binding 继续追踪到 operator、launcher 和 kernel。
- 项目包含相关汇编或用户明确要求时继续分析 CPU 汇编；否则停在项目自有最低层实现。

## 关键符号总表

| 符号 | 角色 | 输入 | 决策或转换 | 输出或副作用 | 下游 | 深度 | 证据 |
|---|---|---|---|---|---|---|---|

该表只作为索引，不能替代 P0 完整函数模板。

## 证据与真实性

- 所有源码片段必须来自当前工作树的实际代码，不得编造。
- 源码块必须逐字保留原始文件的缩进和内容，不得去除公共前导空格或重排行。
- 每个源码块标注经过重新验证的文件路径和行号范围；所有 `file:line` 引用必须使用相对项目根目录的可解析路径，不得只写裸文件名。
- 带 :数字 的源码引用只允许完整、相对项目根目录的文件路径；禁止 symbol:N、裸文件名或省略顶层目录的路径；普通函数名称不附 :行号。
- 伪代码只能用于额外总结，且必须明确标记，不能替代任何要求的实际源码。
- 测试只能证明其实际覆盖的行为；没有测试时记录 `TEST` 缺口。
- 动态接线、反射或运行时选择无法静态确认时标记 `UNVERIFIED`。
- 基线漂移后重新验证受影响的源码、调用关系和行号。

## 停止边界

- 到达第三方库、标准库、外部生成代码或二进制边界时，记录项目侧调用契约后停止。
- 项目自有 Python binding、C/C++ operator、CPU/GPU kernel 属于项目所有权范围；是核心行为时必须按 P0 契约深入。
- 项目本身包含相关汇编或用户明确要求时分析 CPU 汇编；其他情况下停在项目自有最低层实现。
- 纯格式化、无决策的数据搬运和与主要流程无关的未接线代码保持 P2。
- 不使用固定调用深度作为停止标准；以关键行为是否闭合为判断条件。

## 工具能力

使用当前环境可用的文件枚举、文本/符号搜索、定义跳转、引用查找、AST 搜索、依赖检查和测试发现能力。缺少语言服务器或 AST 工具时，通过源码、构建配置和测试交叉验证；工具缺失不授权猜测调用关系。

## 危险信号

- 只给调用栈、符号表、字段或行号就宣布函数级分析完成。
- 描述 P0 执行步骤却没有为每个步骤提供对应实际源码。
- 粘贴源码但不紧邻解释变量、数据/状态变化和下游影响。
- 重要下游只列函数名，不递归使用同一完整模板。
- 只分析 canonical 主线，跳过主要流程清单中的其他流程。
- 因为输出较长或调用较深而在关键状态、副作用或项目自有 native 边界前停止。
- 将动态分派候选路径写成确定事实。
