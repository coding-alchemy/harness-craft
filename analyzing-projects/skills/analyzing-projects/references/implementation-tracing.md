## 职责

本参考只规定如何追踪 `SKILL.md` 已选定的每一个主要流程。适用范围、主要流程清单、证据术语、交付物和全局完成门以 `SKILL.md` 为准。

## 深度完成标准

列出符号、调用关系、字段或源码位置不等于完成实现分析。每个主要流程只有同时具备四层输出、完整执行栈、P0/P1/P2 分级、每个 P0 的完整函数模板、逐步骤实际源码、重要下游递归闭包和跨节点总结时，才完成函数级分析。

## 每个主要流程的四层输出

每个主要流程的分析按四层分层输出组织：

1. **端到端执行栈（导航层）：** 从真实入口到最终输出、持久化、外部消费者或项目所有权边界。
2. **关键符号总表（索引层）：** 汇总符号角色、输入、决策、输出/副作用、下游、接线状态、分析深度和证据。
3. **函数级源码深度分析（核心分析层）：** 对每个 P0 节点重复执行本文件的完整函数模板。
4. **跨节点系统行为总结（系统行为层）：** 汇总数据演化、状态转换、错误传播、异步延续、一致性和不可逆副作用。

第一、第二层不能替代第三层；第三层不能省略第四层需要综合说明的跨节点行为。

## 完整执行栈

执行栈覆盖实际存在的同步调用、异步 continuation、回调、事件生产/接线/消费、动态分派和跨语言/native 绑定。每一跳记录文件、符号、准确行号、关系类型、调用条件、关键输入输出，以及适用的 `SOURCE`、`TEST`、`CALL-CHAIN` 或 `UNVERIFIED`。

静态证据无法唯一确定动态路径时，列出有证据的候选路径、运行时选择机制和无法确认的部分，标记 `UNVERIFIED`，不得把候选路径提升为确定事实。

## P0/P1/P2 分级

| 级别 | 对象 | 分析要求 |
|---|---|---|
| P0 | 五条 P0 信号任一为 `H`，或任一为 `U`（暂定）的函数 | 应用完整函数模板、逐步骤源码绑定和递归深度闭包 |
| P1 | 五条信号全为 `N`，但含不能由签名和透明映射完整说明的项目自有行为 | 应用 P1 最小输出模板：完整签名与参数语义、覆盖全部行为上可区分控制路径的实际源码、调用者与进入条件、分支/失败/副作用、直接下游、证据与等级依据 |
| P2 | 五条信号全为 `N`，且按 P2 最小模板完成透明性正向证明的叶子 | 应用 P2 最小输出模板；默认不逐步骤展开 |

`P0/P1/P2` 只描述当前主要流程执行栈上项目自有函数的分析深度。栈外符号回到能力地图，记录 `主要`、`辅助`、`可选` 或 `未接线` 接线状态：栈外符号若构成独立主要流程，按该流程重新建立执行栈并分级；可能属于遗漏的辅助或可选流程时，回到流程发现阶段复核；经证据确认的未接线代码只登记接线状态和证据。`OUT-OF-FLOW` 可作为台账中的接线状态标签，不是第四个分析等级；栈外符号不因"栈外"直接判 P2。

### 分级前证据预读

分级前必须完成一次紧凑预读：完整函数体、调用者与进入条件、直接下游、相关测试，以及函数内注释/docstring。缺少证据时把对应信号记为 `U`，不得用"看起来简单"或"无法排除疑点"这类泛化判断代替预读。

### P0 触发信号（五条）

1. **入口与编排：** 当前主要流程的真实入口，或跨模块、跨阶段、跨语言、跨 kernel 的编排枢纽；其行为决定执行顺序、阶段交接或所有权边界。
2. **契约与状态：** 建立或改变跨阶段数据契约、主要状态转换、核心结果、失败语义，或会改变系统状态的外部副作用。纯观测日志只有在参与控制、审计或外部合同语义时才命中。
3. **算法与路径选择：** 选择关键算法、数据访问、launch 几何、调度、编译/缓存 key、重试、回退或性能路径，并改变当前主要流程的结果、正确性或性能行为。host 门面与短 helper 按实际决策判定，不按文件层级或行数判定。
4. **正确性不变量：** 承载同步原语、内存一致性或内存序、对齐、位宽、边界、生命周期、清理、编码协议等被调用者或测试依赖的不变量。
5. **有效设计取舍：** 注释或 docstring 记录了与信号 1—4 直接相关的非显然不变量或取舍，且当前源码、调用者或测试证明该取舍仍由本函数实现。仅解释命名、日志显示或历史背景的注释不单独触发 P0。

### 判定算法与降级义务

对每个栈上项目自有函数，逐条记录五条信号的状态：`H`（命中）、`N`（有证据未命中）或 `U`（证据不足）。

1. 任一信号为 `H`，判 P0，在总表"等级与依据"中列出命中信号编号与因果事实。
2. 任一信号为 `U`，暂定 P0，并在 `UNVERIFIED` 中记录缺失证据；补证后重新分级。
3. 全部信号为 `N`，且预读证据证明函数仍含不能由签名和透明映射完整说明的项目自有行为，判 P1；依据必须落到具体信号的核对结果，"未命中 P0"的统括句不构成合格依据。
4. 全部信号为 `N`，且 P2 最小模板的透明性正向证明完整，才判 P2。
5. P2 所需预读证据尚未取得时，把对应信号记为 `U` 并暂定 P0；预读证据已经取得且否定透明性时判 P1。P2 证据完整但输出漏掉必需模板字段时，结论是输出未完成，不得通过改判等级掩盖缺项。

保留歧义向上取整：可能是 P0 也可能是 P1 → P0；可能是 P1 也可能是 P2 → P1。依据是 P0 假阴性成本更高；假阳性仍会稀释重点，因此疑点必须绑定具体信号与证据，不能使用无边界的泛化疑点。主要流程执行栈上的项目自有函数默认至少 P1；P2 是需要正向证明的例外，不是省事的默认。

分级自查必须重新读取函数体、调用者、直接下游、测试和注释，对五条信号重新核对；不能只扫描已写入总表的摘要关键词。任何一行"决策或转换"列写出了分支、状态、契约或权衡，但等级低于 P0 且五信号核对不支持该降级的，立即提升为 P0 并补齐完整模板。

## 每个主要流程的执行顺序

1. 确认真实入口、触发条件、前置条件和最终出口/消费者。
2. 建立完整调用链，列出链上的全部关键符号和直接下游。
3. 按 P0/P1/P2 分级。
4. 对每个 P0 节点执行完整函数级模板。
5. 对决定核心行为的重要项目自有下游递归执行同一完整模板。
6. 递归直到关键行为闭合或到达经过证据确认的项目所有权边界。
7. 汇总跨节点数据、状态、失败和副作用。
8. 检查该流程是否满足全部深度完成条件，再开始下一个主要流程。

## P0 函数逐步骤源码分析

每个 P0 函数必须：

1. 给出完整文件路径、准确行号和完整函数签名。
2. 说明直接及关键间接调用者、触发条件和前置条件。
3. 按真实源码顺序拆分语义步骤。
4. 为每个被描述的语义步骤附对应的连续实际源码块，并标注文件路径和行号范围。
5. 紧邻源码块解释该步骤的实际行为、关键变量、输入输出、数据形态、状态变化和下游影响。
6. 完整说明实际存在的分支、循环、短路、fallback、缓存、重试、并发和异步 continuation。
7. 列出所有直接下游调用，以及参数、返回值和错误映射。
8. 说明返回值、状态修改、外部副作用、消费者、错误传播、恢复、清理和部分成功。
9. 对重要下游递归执行同一完整模板。
10. 标注所有适用的 `SOURCE`、`TEST`、`CALL-CHAIN` 和 `UNVERIFIED` 证据或缺口。

可以把连续的普通语句组合成一个语义步骤，但每一个已经写出的步骤都必须有实际源码。不能描述一个步骤后只给摘要或行号；不能为了减少代码量省略改变语义的分支、状态修改、错误路径或副作用。

### 执行逻辑源码块格式（冻结验证器兼容）

P0 `执行逻辑` 的编号步骤仅使用三反引号源码围栏；不得使用 `~~~` 或其他围栏标记。每个源码围栏的首行必须是相对项目根目录的 `# path:start-end`；`path` 不得是绝对路径或包含 `..`，行号范围必须可解析且与实际源码一致，单行也写 `N-N`。源码围栏闭栏后立即为 `**源码分析**`，中间不得插入其他内容。

P1/P2 不使用 `执行逻辑` 保留标题；它们应按各自分级要求呈现，不得伪装成 P0 完整模板。P1/P2 的实际源码块仍采用上述三反引号围栏、相对路径 `# path:start-end`（单行 `N-N`）和紧邻的 `**源码分析**` 的可解析格式，但此格式要求不新增逐步骤展开或完整模板义务。

- 输入及进入时数据形态：

### P1 最小输出模板

P1 不使用 P0 的十槽位完整模板，也不得使用 `执行逻辑` 保留标题，但必须包含以下全部内容（顺序可调；源码块沿用冻结验证器格式：三反引号围栏、`# path:start-end` 首行、紧邻 `**源码分析**`）：

1. **文件**、**签名**与**等级依据**（五信号核对均为 `N` 的具体依据，一句话）。
2. 参数语义清单：参数、类型与默认值、语义。
3. 调用者与进入条件。
4. 覆盖全部行为上可区分的控制路径的实际源码块，每块紧邻解释。优先完整函数体；函数过长时可省略，但必须说明省略范围，且每一个改变行为的分支、状态修改、错误路径都保留原码。允许包含局部、封闭的分支或错误处理，但证据必须证明它们不改变五条 P0 信号定义的核心结果、跨阶段契约、正确性不变量或关键路径。
5. 分支、失败与副作用清单。
6. 直接下游与证据（`SOURCE`/`TEST`/`CALL-CHAIN`/`UNVERIFIED`）。

P1 的下限是"读者不打开源码也能完整复述该函数的全部行为上可区分的控制路径"；只给签名加几行摘录不满足 P1。

### P2 最小输出模板

P2 是需要正向证明的例外。栈上项目自有函数判 P2，必须完整提供以下内容（顺序可调；源码块沿用冻结验证器格式）：

1. **文件**与**签名**。
2. 调用者与进入条件。
3. 完整短函数体，或足以证明透明映射的连续源码块，每块紧邻解释。
4. 参数/返回映射：每个参数如何流向下游、返回值如何由下游结果构成。
5. 直接下游与证据（`SOURCE`/`TEST`/`CALL-CHAIN`/`UNVERIFIED`）。
6. 正向证明：无状态修改、无失败语义重映射、无核心副作用的逐项说明；证明材料来自预读事实，例如结果仅流向观测性展示、不参与任何控制、缓存或文件路径。

透明映射指参数按原顺序透传、返回值由下游结果原样构成；纯委托 wrapper 的映射由"参数流入被调用方、返回值为其结果"证明。函数自行构造输出或按输入选择不同输出（例如在两种输出文本之间选择）时，不是透明映射。预读证据否定任一证明项，或证明函数不是透明映射时，判 P1；预读尚未覆盖相关证明项时先补预读，把对应信号记为 `U` 并暂定 P0。已有证据足以判 P2 但输出漏掉上述任一项时，输出未完成，不能用 P1 或 P0 标签替代缺失内容。

## 分批交付与覆盖台账

单次输出长度不足时，以一个主要流程或一个已闭合 P0 子图为交付单元分批输出。覆盖台账持续记录：分析基线、该单元全部符号、接线状态、五信号核对结果、最终等级、模板完成状态和未闭合下游。台账未清零时只能报告"部分完成"并列出剩余符号，不得通过降低等级或省略符号宣布项目分析完成。

## P0 深度闭包

P0 函数调用的项目自有函数，只要直接决定当前流程的关键算法、状态转换、数据契约、控制流、错误处理、性能路径或外部副作用，也必须提升为 P0，并递归应用完整函数模板。

递归持续到该主要流程的关键行为已经闭合，或到达行为无关的 P1/P2 叶子、最终消费者或经过证据确认的项目所有权边界。不得因为调用层数较深、跨模块、进入 native 代码、输出已经很长或已有调用链图而停止。

## 核心 CPU/GPU/native 实现

当项目自有 CPU/GPU/native 函数是主要流程的核心算法时：

- 展示完整函数体；只有函数中存在可明确隔离且不影响算法的样板代码时，才可展示足以完整还原算法的连续代码，并说明省略范围。
- 对决定计算、同步、内存访问、边界处理、shape/device 和数值行为的关键语句逐行解释。
- 从上层 binding 继续追踪到 operator、launcher 和 kernel。
- 项目包含相关汇编或用户明确要求时继续分析 CPU 汇编；否则停在项目自有最低层实现。

## 关键符号总表

| 符号 | 角色 | 输入 | 决策或转换 | 输出或副作用 | 下游 | 接线状态 | P0 信号核对 | 等级与依据 | 证据 |
|---|---|---|---|---|---|---|---|---|---|

栈上项目自有函数的 `P0 信号核对` 固定格式为 `1:H/N/U; 2:H/N/U; 3:H/N/U; 4:H/N/U; 5:H/N/U`。栈外符号的 `接线状态` 写 `OUT-OF-FLOW` 及其能力地图状态，`P0 信号核对` 和 `等级与依据` 均写 `N/A (OUT-OF-FLOW)`，不得填写 P0/P1/P2。栈上函数的 `等级与依据` 记录最终 P0/P1/P2、命中信号、`U` 缺口或透明性证明；`证据` 记录支持判定的 `SOURCE`、`TEST`、`CALL-CHAIN` 或 `UNVERIFIED`。该表只作为索引，不能替代 P0 完整函数模板，也不能替代对原始证据的重新核对。

## 证据与真实性

- 所有源码片段必须来自当前工作树的实际代码，不得编造。
- 源码块必须逐字保留原始文件的缩进和内容，不得去除公共前导空格或重排行。
- 每个源码块标注经过重新验证的文件路径和行号范围；所有 `file:line` 引用必须使用相对项目根目录的可解析路径，不得只写裸文件名。
- 带 :数字 的源码引用只允许完整、相对项目根目录的文件路径；禁止 symbol:N、裸文件名或省略顶层目录的路径；普通函数名称不附 :行号。
- 伪代码只能用于额外总结，且必须明确标记，不能替代任何要求的实际源码。
- 测试只能证明其实际覆盖的行为；没有测试时记录 `TEST` 缺口。
- 动态接线、反射或运行时选择无法静态确认时标记 `UNVERIFIED`。
- 基线漂移后重新验证受影响的源码、调用关系和行号。

## 停止边界

- 到达第三方库、标准库、外部生成代码或二进制边界时，记录项目侧调用契约后停止。
- 项目自有 Python binding、C/C++ operator、CPU/GPU kernel 属于项目所有权范围；是核心行为时必须按 P0 契约深入。
- 项目本身包含相关汇编或用户明确要求时分析 CPU 汇编；其他情况下停在项目自有最低层实现。
- 与主要流程无关的未接线代码进入能力地图的未接线状态，不参与当前流程深度分级。
- 纯格式化和无决策的数据搬运只有在满足 P2 最小模板的正向证明时才判 P2。
- 不使用固定调用深度作为停止标准；以关键行为是否闭合为判断条件。

## 工具能力

使用当前环境可用的文件枚举、文本/符号搜索、定义跳转、引用查找、AST 搜索、依赖检查和测试发现能力。缺少语言服务器或 AST 工具时，通过源码、构建配置和测试交叉验证；工具缺失不授权猜测调用关系。

## 危险信号

- 只给调用栈、符号表、字段或行号就宣布函数级分析完成。
- 描述 P0 执行步骤却没有为每个步骤提供对应实际源码。
- 粘贴源码但不紧邻解释变量、数据/状态变化和下游影响。
- 重要下游只列函数名，不递归使用同一完整模板。
- 只分析 canonical 主线，跳过主要流程清单中的其他流程。
- 因为输出较长或调用较深而在关键状态、副作用或项目自有 native 边界前停止。
- 将动态分派候选路径写成确定事实。
- “这个函数看起来是简单封装，定为 P1 就行。”没有完成五信号 H/N/U 核对并写出等级依据。
- “host 门面、几何选择、编译缓存只是胶水代码。”它们决定 launch 契约与缓存行为，命中 P0 触发信号第 3 条。
- “P1 给签名和几行核心代码就够了。”P1 有自己的最小输出模板，必须覆盖全部行为上可区分的控制路径。
- “输出已经很长，这个函数降一级吧。”篇幅不是降级理由，是请求分批交付。
