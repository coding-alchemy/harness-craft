# 分析项目

## 概述

文档只是线索；源码、测试和真实调用链才是证据。接手陌生代码库时，其中的文档只能说明过去有人如何描述它，不能证明当前代码实际做了什么。在具体文件、测试或经过追踪的调用链确认一项结论之前，将其视为未经验证。本技能设置六个必须按顺序通过的门，使分析和文档在截止时间与权威压力下仍然可审计。

进入本技能后先确认两个条件：分析对象存在可验证的现有实现；交付物是面向开发者的完整源码级项目架构与实现文档。任一条件不成立，停止使用本技能。

## 不适用范围

- 不产出完整源码级项目介绍的普通仓库调查。
- 单个 bug、函数、调用链、代码审查问题、重构建议或实现计划。
- 只核对一项架构结论而不交付完整项目介绍。
- 安装、使用、部署、API、贡献或环境搭建专项手册。
- 没有现有实现可供验证的全新概念架构设计。

## 必需工作流

按顺序完成每一道门；前一道门未满足时，不得开始后一道门。

1. **冻结可复现基线。** 在实质性分析前记录分支或 detached HEAD、commit 和工作树状态，区分用户原有变更与任务变更。最终验证前检查基线漂移；变化时重新验证受影响的证据、符号和行号。

2. **建立全仓地图并让结论扎根于证据。** 识别仓库形态、语言、构建与运行机制、可执行/公共/测试入口、主要模块、外部边界、生成代码及第三方边界；从真实入口识别全部主要流程。能力地图至少记录能力或流程、入口、关键阶段、主要模块、输出或消费者、接线状态和证据。对事实使用所有适用的 `SOURCE`、`TEST`、`CALL-CHAIN`；缺失证据明确记录，无法确认的结论标记为 `UNVERIFIED`。

3. **逐一深入分析所有主要流程并规划权威文档落点。** 每一个主要流程都必须形成独立、清晰的函数级分析单元，建立从真实入口到最终消费者或项目所有权边界的完整调用链，并对链上符号执行 P0/P1/P2 分级。流程之间串行完成；一个流程满足 `references/implementation-tracing.md` 的深度完成标准后，再开始下一个。仓库规模只改变发现和分批交付策略，不允许静默省略已识别的主要流程。每项能力指定一个权威文档落点；实际并行编辑时再为每个文件指定排他写入者。

### 函数级追踪路由

分析每一个主要流程时，都必须完整读取并执行 `references/implementation-tracing.md`。该 reference 规定每个流程的四层输出、完整执行栈、P0/P1/P2、逐步骤实际源码、重要下游递归同模板和深度闭包。普通目录说明、无决策的叶子工具和未接线代码不单独触发函数级展开，但不得借此跳过它们所属主要流程中的关键行为。

任何主要流程未完成独立函数级分析时，端到端调用栈、关键符号表或 canonical 主线分析都不能单独满足完整项目分析要求。

4. **保护已获授权的编辑。** 只分析或审计时保持只读；新建文档时确定目标位置并建立 protected fact inventory；改写已有文档时额外保存编辑前快照。只有实际使用并行写入者时才应用文件互斥规则。

5. **执行最新的机械验证。** 针对有效基线重新运行链接、符号、占位符、章节配对和重复内容检查；通读不能替代机械验证。

6. **按两个读者视角审阅并设置完成门。** 分别执行初学者和维护者审阅。环境支持时优先使用独立审阅者；不支持时记录独立性限制并分离审阅回合。Critical 或 Important 问题阻塞完成，修复后按相同读者视角复查。

## 输出契约

### 1. 项目级架构总览——必需

1. **项目定位与系统上下文：** 要解决的问题、使用者/调用者、外部系统、运行时入口、主要输入、输出/消费者和系统边界。
2. **概念架构：** 逻辑组件/分层及职责；如适用，说明数据面与控制面；显式标注概念视图与真实源码边界。
3. **项目结构与构建上下文：** 给出经过筛选的二至三级源码目录视图，说明主要目录、关键配置、构建文件和运行方式。目录树只用于导航，不能代替模块职责分析。
4. **依赖与外部边界：** 按功能汇总直接依赖及其实际用途，区分核心、辅助和可选依赖；版本从 manifest、lockfile 或构建配置取证，不机械罗列全部传递依赖。
5. **主要流程清单：** 列出所有主要流程，以及辅助、可选和未接线路径；每项记录入口、关键阶段、出口/消费者、接线状态、证据和权威文档落点。主要流程清单决定后续函数级分析范围。
6. **项目级模块职责表：** 主要目录/模块、真实源码符号、职责、输入输出和相互关系。仅列目录树不满足本项。
7. **能力地图：** 主要、辅助、可选和未接线能力，每项链接到唯一 canonical owner，并包含接线状态和权威文档落点。
8. **横切架构约束：** 只列出源码证据支持的安全、状态/一致性、并发、可移植性、确定性和扩展等定义实现的工程原则。
9. **阅读路线与源码导航：** 30 秒总览、5 分钟主流程、维护者下钻，以及总览、流程分析和专题之间的链接。

当模块关系或跨阶段流程仅靠文字难以理解时，提供 Mermaid 图；图中节点必须映射到真实模块或符号，且图不能代替调用栈和源码证据。

### 2. 端到端实现全景——必需

以下七项对每一个主要流程分别重复；不得只为 canonical 主线提供实现全景。

1. **真实编排入口：** 用户/API/CLI/事件入口如何到达实际的 orchestrator、dispatcher 或主调用链。
2. **正常端到端主线：** 从输入到最终输出/消费者的真实调用与数据流，并标注阶段交接。
3. **阶段契约总表：** 每个主要阶段的真实入口符号、输入、输出、状态/副作用、下一消费者和 canonical owner。
4. **数据形态演化：** 跨阶段类型、schema/关键字段、持久化形态和转换边界。
5. **关键控制流分支：** 实际存在的可选阶段、分支、短路、fallback、缓存命中、增量、重试、并发和异步路径。
6. **跨阶段失败与副作用边界：** 相关的错误传播/隔离、降级、部分成功、事务/原子性、外部写入和恢复行为。
7. **概念模型与真实源码映射：** 概念阶段或现有文档术语与真实函数、命令和运行路径之间的对应与不对应关系。

### 3. 能力专题——条件必需

当某项能力具有独立入口/流程、重要算法/状态/数据契约、独立的安全/失败/性能/依赖边界，或在项目级叙事中展开会破坏主线可读性时，为其建立独立专题或等价清晰边界。每个选中的能力或 Pipeline 阶段都必须使用下面全部九项显式内容；否则不要仅为凑文件数创建空专题。

以下九项全部使用显式标题或表格字段；任何一项都不能隐含表达，也不能由笼统的“实现细节”章节替代。函数级追踪细节遵循 `references/implementation-tracing.md`。

1. **目标与边界：** 职责、排除范围，以及与更大系统或 Pipeline 的关系。
2. **入口与调用链：** CLI/API/事件/Hook 或其他运行时入口、调用方，以及真实的内部调用链。
3. **输入与前置条件：** 类型、schema 或关键字段、配置、校验和前置要求。
4. **处理与决策：** 有序步骤、关键算法、分支、短路、fallback 选择，以及相关情况下的并发行为。
5. **输出与消费者：** 返回类型、schema 或关键字段、产生的产物/事件，以及下游消费者。
6. **状态与副作用：** 缓存、持久化、文件、队列、状态变更、幂等性和清理。
7. **依赖与集成：** 内部协作者，以及必需依赖、外部依赖和可选依赖。
8. **失败与限制：** 错误、重试、降级、安全边界、性能/规模约束和不支持的情形。
9. **证据：** 源码文件和符号、测试及每项测试实际证明的行为、经过追踪的 `CALL-CHAIN`，以及明确的 `UNVERIFIED` 缺口。

对于分阶段 Pipeline，为每个阶段重复这九项，并补充阶段间数据契约、转换、可选路径、缓存命中、增量行为，以及简化模型和真实控制流之间的差异。

### 完成证据

- 已记录分析基线；最终验证前已检查基线漂移。
- 每项事实结论都有适用的 `SOURCE`、`TEST`、`CALL-CHAIN` 引用，或明确标记为 `UNVERIFIED`。
- 已建立全仓能力地图并完整追踪 canonical 主线。
- 每一个主要流程都有独立函数级分析、完整调用链和 P0/P1/P2 分级。
- 每个主要流程都已执行 `references/implementation-tracing.md` 的四层输出；其中每个 P0 节点均使用完整函数模板，关键下游已递归闭合。
- 每个 P0 语义步骤都有对应连续实际源码和紧邻解释；不存在只给调用栈、符号表、字段摘要或行号就宣布完成的流程。
- 原始 Phase2 迁移矩阵没有未映射项，负向差异审计没有未经批准的能力损失。
- 每项能力都有一个权威文档落点；实际并行写入时，每个文件只有一个写入者。
- 新建或改写文档时已有 protected fact inventory；改写已有文档时另有编辑前快照。
- 已针对有效基线通过最新机械验证。
- 已完成初学者和维护者视角审阅，不存在未关闭的 Critical 或 Important 问题。

## 快速参考

| 门或产物 | 要求 |
|---|---|
| 1 基线 | 记录引用、分支/commit、工作树状态；最终验证前检查漂移 |
| 2 证据 | `SOURCE`、`TEST`、`CALL-CHAIN` 或 `UNVERIFIED`；说明每项引用实际证明什么 |
| 3 所有权 | 每个主题只有一个 canonical owner；指定权威文档落点；并行编辑时文件互斥 |
| 4 保护 | 只读分析时不编辑；新建文档建 protected fact inventory；改写已有文档再建编辑前快照 |
| 5 验证 | 重新执行链接、符号、占位符、章节配对和重复度检查 |
| 6 审阅 | 初学者 + 维护者审阅；Critical/Important 阻塞完成并要求复查 |
| 交付物 | 必需的项目级架构总览 + 必需的实现全景 + 条件式九项能力专题 |

## 危险信号

发现自己产生以下想法时，立即停止：

- “我正在分析一个仓库，所以这个技能自动适用。”除非交付物是源码级项目架构与实现文档，否则不适用。
- “README 很可能准确，所以可以直接相信。”README 只是线索；使用所有实际适用的 `SOURCE`、`TEST` 或 `CALL-CHAIN` 证据类型确认，并将证据缺口标记为 `UNVERIFIED`。
- “组件和数据存储清单已经足以作为证据。”没有经过追踪的调用链就不够。
- “canonical 主线分析完就代表所有主要流程完成。”每一个主要流程都必须独立深入分析。
- “调用栈、符号表和字段已经齐全，所以不需要逐步骤展示实际源码。”这些只是导航和索引，不能替代函数级源码分析。
- “证据台账可以算作编辑前快照和 protected fact inventory。”必须先为每篇文档建立快照，并列出其中受保护的事实。
- “并行追加共享索引是安全的。”必须通过一个写入者串行执行。
- “一致性通读就是验证。”应重新运行机械检查。
- “我已经检查过自己的工作，所以任务完成了。”必须安排初学者和维护者审阅。
- “链接能够渲染，而且先前会话已经报告成功，因此可以交付。”Critical 或 Important 问题会阻塞完成，直到修复并复查。
