# 分析项目

## 概述

文档只是线索；源码、测试和真实调用链才是证据。接手陌生代码库时，其中的文档只能说明过去有人如何描述它，不能证明当前代码实际做了什么。在具体文件、测试或经过追踪的调用链确认一项结论之前，将其视为未经验证。本技能设置六个必须按顺序通过的门，使分析和文档在截止时间与权威压力下仍然可审计。

仅当以下两个条件同时成立时使用本技能：分析对象是已有代码库，且要求的交付物是向开发者解释整体架构与实现的源码级项目文档。任一条件不成立，都不要使用本技能。

## 何时使用

- 为已有仓库产出源码级架构与实现介绍。
- 从源码和测试重建已有项目的整体架构与端到端实现，用于开发者文档。
- 重组或刷新项目介绍文档，且结果仍须完整解释源码架构与实现。
- 审计架构文档，且任务包含交付修正后的完整源码级项目介绍。

## 何时不使用

- 不产出源码级项目介绍文档的仓库分析。
- 单个 bug、函数、调用链、代码审查问题、重构建议或实现计划。
- 只核对一项架构结论而不产出完整项目介绍。
- 安装、使用、部署、API、贡献或环境搭建手册。
- 没有现有实现可供验证的全新概念架构设计。

## 必需工作流

按顺序完成每一道门；前一道门未满足时，不得开始后一道门。

1. **冻结事实基线。** 在读取或编辑前，记录仓库引用和工作树状态，包括分支、commit、未提交或未跟踪的变更。之后的所有分析和验证都基于这个固定基线。

2. **让证据扎根于源码。** 对每项结论引用所有实际适用的证据类型，并标记为 `SOURCE`（实现该行为的代码）、`TEST`（验证该行为的测试）和 `CALL-CHAIN`（经过追踪的请求或数据流）。如果某种证据不存在，明确记录该证据缺口，不得捏造。没有经过追踪的调用链时，仅有组件或数据存储清单不能算作证据。README 和现有文档只能作为线索。将任何无法确认的内容标记为 `UNVERIFIED`，绝不能将其提升为事实。

3. **确定所有权和结构。** 划分能力边界，并为每个主题和每篇文档指定且只指定一个 canonical owner，不允许共享写入者。每篇文档都服务两类读者：需要总览的初学者和需要源码细节的维护者。深入专题之前，先定义两个必需的项目级视图：项目级架构总览和端到端实现全景。仅当某项能力的独立流程、算法/状态/数据契约、风险边界或篇幅会使这两个视图过载时，才增加能力专题。

4. **保护编辑和并行过程。** 编辑任何文档前，先保存编辑前快照，并建立 protected fact inventory，记录编辑不得破坏的准确事实。证据台账或结论台账不能替代这两项产物。为每个并行工作者分配互斥的文件集合；README、总览和导航等共享索引只能由一个写入者串行修改。禁止并发追加共享索引，因为这会丢失数据。

5. **执行最新的机械验证。** 针对冻结的基线，重新运行链接、符号、占位符、章节配对和重复内容检查。跨文档一致性通读不能替代机械验证。

6. **审阅并设置完成门。** 同时安排初学者审阅者和维护者审阅者；不得相信实施者自评、先前会话的成功声明，也不能因为链接可以渲染就认定完成。对每个问题分级；任何 Critical 或 Important 问题都会阻塞完成，直到问题修复并由原审阅者复审。

## 输出契约

### 1. 项目级架构总览——必需

1. **项目定位与系统上下文：** 要解决的问题、使用者/调用者、外部系统、运行时入口、主要输入、输出/消费者和系统边界。
2. **概念架构：** 逻辑组件/分层及职责；如适用，说明数据面与控制面；显式标注概念视图与真实源码边界。
3. **项目级模块职责表：** 主要目录/模块、真实源码符号、职责、输入输出和相互关系。仅列目录树不满足本项。
4. **能力地图：** 主管线、主管线外、可选和未接线能力，每项链接到唯一 canonical owner。
5. **横切架构约束：** 只列出源码证据支持的安全、状态/一致性、并发、可移植性、确定性和扩展等定义实现的工程原则。
6. **阅读路线与源码导航：** 30 秒总览、5 分钟主链、维护者下钻，以及总览、全景和专题之间的链接。

### 2. 端到端实现全景——必需

1. **真实编排入口：** 用户/API/CLI/事件入口如何到达实际的 orchestrator、dispatcher 或主调用链。
2. **正常端到端主线：** 从输入到最终输出/消费者的真实调用与数据流，并标注阶段交接。
3. **阶段契约总表：** 每个主要阶段的真实入口符号、输入、输出、状态/副作用、下一消费者和 canonical owner。
4. **数据形态演化：** 跨阶段类型、schema/关键字段、持久化形态和转换边界。
5. **关键控制流分支：** 实际存在的可选阶段、分支、短路、fallback、缓存命中、增量、重试、并发和异步路径。
6. **跨阶段失败与副作用边界：** 相关的错误传播/隔离、降级、部分成功、事务/原子性、外部写入和恢复行为。
7. **概念模型与真实源码映射：** 概念阶段或现有文档术语与真实函数、命令和运行路径之间的对应与不对应关系。

### 3. 能力专题——条件必需

当某项能力具有独立入口/流程、重要算法/状态/数据契约、独立的安全/失败/性能/依赖边界，或在项目级叙事中展开会破坏主线可读性时，为其建立独立专题或等价清晰边界。每个选中的能力或 Pipeline 阶段都必须使用下面全部九项显式内容；否则不要仅为凑文件数创建空专题。

以下九项全部使用显式标题或表格字段；任何一项都不能隐含表达，也不能由笼统的“实现细节”章节替代。

1. **目标与边界：** 职责、排除范围，以及与更大系统或 Pipeline 的关系。
2. **入口与调用链：** CLI/API/事件/Hook 或其他运行时入口、调用方，以及真实的内部调用链。
3. **输入与前置条件：** 类型、schema 或关键字段、配置、校验和前置要求。
4. **处理与决策：** 有序步骤、关键算法、分支、短路、fallback 选择，以及相关情况下的并发行为。
5. **输出与消费者：** 返回类型、schema 或关键字段、产生的产物/事件，以及下游消费者。
6. **状态与副作用：** 缓存、持久化、文件、队列、状态变更、幂等性和清理。
7. **依赖与集成：** 内部协作者，以及必需依赖、外部依赖和可选依赖。
8. **失败与限制：** 错误、重试、降级、安全边界、性能/规模约束和不支持的情形。
9. **证据：** 源码文件和符号、测试及每项测试实际证明的行为、经过追踪的 `CALL-CHAIN`，以及明确的 `UNVERIFIED` 缺口。

对于分阶段 Pipeline，为每个阶段重复这九项，并补充阶段间数据契约、转换、可选路径、缓存命中、增量行为，以及简化模型和真实控制流之间的差异。

### 完成证据

- 每项事实结论都带有 `SOURCE`、`TEST` 或 `CALL-CHAIN` 引用，或标记为 `UNVERIFIED`；使用所有适用的证据类型，不要在某种证据不存在时强制凑齐三种。
- 已存在基线记录、每篇文档的编辑前快照和 protected fact inventory。
- 每个主题都有一个 canonical owner，共享索引均以串行方式写入。
- 已针对基线通过最新机械验证。
- 已记录初学者和维护者审阅，且不存在未关闭的 Critical 或 Important 问题。

## 快速参考

| 门或产物 | 要求 |
|---|---|
| 1 基线 | 接触任何内容前记录引用和工作树状态 |
| 2 证据 | `SOURCE`、`TEST`、`CALL-CHAIN` 或 `UNVERIFIED`；说明每项引用实际证明什么 |
| 3 所有权 | 每个主题只有一个 canonical owner；同时提供初学者与维护者视图 |
| 4 保护 | 编辑前快照 + protected fact inventory；文件互斥；共享索引串行更新 |
| 5 验证 | 重新执行链接、符号、占位符、章节配对和重复度检查 |
| 6 审阅 | 初学者 + 维护者审阅；Critical/Important 阻塞完成并要求复审 |
| 交付物 | 必需的项目级架构总览 + 必需的实现全景 + 条件式九项能力专题 |

## 危险信号

发现自己产生以下想法时，立即停止：

- “我正在分析一个仓库，所以这个技能自动适用。”除非交付物是源码级项目架构与实现文档，否则不适用。
- “README 很可能准确，所以可以直接相信。”README 只是线索；使用所有实际适用的 `SOURCE`、`TEST` 或 `CALL-CHAIN` 证据类型确认，并将证据缺口标记为 `UNVERIFIED`。
- “组件和数据存储清单已经足以作为证据。”没有经过追踪的调用链就不够。
- “证据台账可以算作编辑前快照和 protected fact inventory。”必须先为每篇文档建立快照，并列出其中受保护的事实。
- “并行追加共享索引是安全的。”必须通过一个写入者串行执行。
- “一致性通读就是验证。”应重新运行机械检查。
- “我已经检查过自己的工作，所以任务完成了。”必须安排初学者和维护者审阅。
- “链接能够渲染，而且先前会话已经报告成功，因此可以交付。”Critical 或 Important 问题会阻塞完成，直到修复并复审。
