## 1. 目标与使用场景

### 1.1 核心目标

在仓库中新增 `frontend-design-workflow` 模块，将已收集的前端美化方法整理成一个模型可以读取和使用的 Skill。这里的 Skill 是一组工作指令和参考资料，工作流是模型使用这些资料完成任务的过程。

开发者提出具体页面目标后，模型应能判断问题、选择方法，在授权范围内改动或提出建议，并说明结果如何验证。维护者应能查到每项外部方法来自哪里、被怎样修改、哪些效果尚未证实。模块支持直接从仓库读取，也支持完整复制后独立使用。

使用过程中还要留下可跨任务回看的经验：哪些方法被采用、效果如何，哪些需求未被 Skill 覆盖、借助什么外部能力完成，以及流程哪里反复卡住。维护者能够据此形成有证据的 Skill 改进建议。

### 1.2 目标使用者与运行假设

主要使用者是开发者和 Skill 维护者。指令面向能理解自然语言、读取文件的主流模型；是否能读图、操作浏览器、截图或执行命令，取决于实际环境，不绑定单一平台的工具名。

有代码和运行环境时，可以在授权范围内实施并验证；只有截图时，分析可见特征；只有文本或源码时，给出相应范围内的判断。交付时说明没有完成的验证，不能把阅读源码说成已经运行过页面。

### 1.3 支持的任务

| 场景 | 典型请求 | 用户可观察的结果 |
| --- | --- | --- |
| 已有页面美化 | “把这个后台页面调整得清晰、统一一些，保持功能” | 针对实际问题的页面改动，能够比较改善与检查保留行为 |
| 新页面设计 | “为这个产品做一页界面，有明确风格” | 与产品内容和使用任务相符、内部一致且能按任务要求运行的界面 |
| 参考风格迁移 | “参考这些截图的风格，应用到我们的页面” | 说明借鉴的视觉关系并适配自己的内容，不将截图推断冒充事实 |
| 仅评估或建议 | “先看看哪里需要优化，不要修改” | 有具体对象、问题、影响与调整方向的建议，保持只读 |

这些场景可以组合，例如已有页面参考另一套风格进行改造。模型依据任务决定进入流程的位置、需要读取的资料和允许的动作，不要求用户先选择某个固定命令。

## 2. 背景与已有决定

### 2.1 为什么需要整理这些素材

需求起点是用户收集的一批前端设计与美化 Skill。最初希望先整理可复用的方法，随后决定做成模型可用的工作流，再进一步明确纳入当前仓库，成为独立模块。

素材包含完整流程、单项技巧、风格偏好、示例模板和效果评价。不同材料有重复，也有冲突：例如，一份材料鼓励某种装饰，另一份可能禁止它；有些入口还依赖其他文件或工具。模块需要保留有用细节，并说明什么情况下使用，避免模型同时执行互相矛盾的要求。

用户特别要求：不确定的经验先保留，等到真实任务中使用时再验证。因此，本模块既要整理已知方法，也要保留值得尝试的候选方法及其来源。

### 2.2 已经讨论并同意的方向

| 阶段 | 用户要求与讨论结果 | 当前效力 |
| --- | --- | --- |
| 素材整理 | 参考 Downloads 中已搜集的材料，整理前端优化方法论；当时项目正在进行其他工作，先不写入工作区 | 素材范围与方法论目标保留；不写工作区的限制已被后续模块化要求替代 |
| 方法论认可 | 用户整体同意六步方法；不确定的内容先保留，后续在真实场景使用时再验证 | 持续有效，不能因缺乏效果测评而直接删除候选技巧 |
| 模型可用形式 | 允许组织为 Skill、工作流或其他模型可以读取和使用的形式 | 采用一个 Skill 入口承载工作流，详细内容按条件读取 |
| 纳入仓库 | 用户明确要求放入当前项目，作为独立模块存在，并重新评估接入方式 | 模块名沿用 `frontend-design-workflow`，遵循仓库模块与规格约定 |
| 外部 Skill 处理 | 用户关注大量引用的外部 Skill 如何保存、引入、使用和更新；随后同意来源管理与分类处理方向 | 外部来源必须可追溯；改编、原文引用和可选依赖分别处理 |
| 需求初稿 | 用户表示“同意，先写一版本试试”，并明确“先整理一套需求文档”“把上下文写详细点” | 先写需求文档；不据此越过设计、计划及执行授权门禁 |
| 需求批准与设计 | 用户批准 V0.1，要求编写设计文档；设计初稿已形成，尚未获批 | 原有需求继续作为基线，尚未授权实现 |
| 使用中持续改进 | 用户要求沉淀优化经验、未支持需求，尤其是借助 Skill 之外能力完成的功能，以及使用频率、效果和流程问题 | 在原反馈机制上扩展记录、跨任务汇总与改进建议；具体规则纳入 V0.2 审阅 |

这些决定保留了全部四类任务。允许以后验证候选技巧，并不意味着可以跳过当次页面任务的功能检查。

### 2.3 与现有仓库的关系

仓库定位见[根 README](../../README.md)。已有模块将完整 Skill 放在 `<模块>/skills/<技能>/`，模块说明和规格保留在外层。可参考 [analyzing-projects 的纯文档 Skill](../../analyzing-projects/README.md) 与 [online-media-reader 的分发边界](../../online-media-reader/README.md)。前者说明纯 Markdown 也可以构成独立模块，后者说明模型运行所需资源应随 Skill 完整分发。

本模块开发遵循[项目协作约束](../../AGENTS.md)、[规格工作流](../../docs/agents/issue-tracker.md)和[状态标签约定](../../docs/agents/triage-labels.md)。这些开发管理规则不整体复制进通用 Skill；Skill 被用于其他项目时，遵守目标项目和用户的有效要求。

## 4. 模块与分发要求

1. 模块位于 `frontend-design-workflow/`。模型执行任务所需的内容集中在模块内的 `skills/frontend-design-workflow/`，`SKILL.md` 是唯一公共入口。
2. 入口说明共同流程，以及何时读取视觉方向、具体技巧和验证反馈等参考文档。同一规则只维护一份，避免多个文件给出不同指令。
3. 模块 README 说明用途、使用示例、分发方式和实际支持边界。需求、设计、计划及维护资料保留在模块外层，不要求最终使用者先阅读开发规格。

6. 根 README 在模块形成后增加入口；无需为了发现本模块改动根 Agent 规则，也不要求其他现有模块依赖它。

## 5. 模型怎样完成一次任务

工作流保留以下六个环节及其依赖关系。局部任务可以使用已有成果满足前置条件，不重复生成已经有效的产品说明、视觉规范或完整页面方案。

| 环节 | 必须明确的内容 | 完成依据 |
| --- | --- | --- |
| 明确目标与现状 | 用户任务、优化对象、当前问题、保留行为、现有规范、授权范围及可用工具 | 能说明本次改善什么，以及用什么证据判断 |
| 视觉方向 | 产品语境、用户指定风格、品牌约束或参考图中值得借鉴的关系 | 方向能指导布局、排版、配色和强调程度的具体取舍 |
| 视觉规则 | 满足当前任务所需的色彩角色、文本层级、间距、组件、响应式及动效规则 | 实现有一致依据，观察、估算和补充设计分开 |
| 验证代表页面 | 选一个能覆盖主要难点的页面、组件或流程，使用真实或接近真实的内容 | 能判断规则是否适用，再决定是否推广到其他页面 |
| 定向打磨 | 具体问题、原因判断、调整方法与影响 | 目标问题改善，必须保留的行为未退化 |
| 实际验收 | 与目标相符的视觉比较、操作走查及必要质量检查 | 已验证结果、仍有缺口及待验证经验分别说明 |

### 5.1 内容与目标优先

“高级、清爽、专业、有活力”等描述需要落到具体页面选择。例如，让用户更容易找到重点，可以调整内容顺序、字号层级和主要按钮，而不是一律增加留白或动画。品牌展示页与长时间使用的后台可以采用不同的信息密度；配色和主题应结合实际使用场景，不能只按行业名称决定。

用户明确的内容、功能、品牌、技术栈和既有行为优先于来源中的偏好。任务已明确时直接利用现有信息；只有会造成不同行为的实质歧义才需要澄清，不将每次美化都变成完整 PRD 访谈。

### 5.2 现有页面与参考材料

已有页面需要结合实际界面与相关实现判断问题；具备运行条件时查看运行结果，识别现有组件和视觉规则。调整范围与用户目标相称，不为局部问题自动扩展为整个产品重设计。

参考图分析应说明借鉴的是布局比例、层级、字体处理、颜色关系、间距节奏还是组件形态。精确字体、参数、动效、悬停状态、隐藏状态和响应式行为未被材料展示时，标记为估算或补充设计，不能称为已提取事实。

多份参考出现冲突时，依据用户目标与既有规范作出可解释选择；会改变要求的差异先确认。参考风格迁移不自动等同于逐像素复刻，也不默认引入参考产品的功能。

### 5.3 实施与迭代

一个主要问题可以涉及多个关联维度，但每轮调整应能解释为何实施、怎样验证。先处理任务阻断、难以阅读或无法操作的问题，再改善层级、一致性、个性和细节；该优先关系不限制用户明确要求的专项工作。

使用能够暴露问题的内容与状态，例如长标题、中文、较长数字、表单错误或空列表；覆盖程度按实际页面和风险选择。实施后重新查看相关界面与操作，避免只凭代码外观或编译通过判断美化完成。

## 6. 需要保留哪些美化技巧

| 类别 | 需要保留的能力 |
| --- | --- |
| 结构与阅读 | 信息层级、主次操作、布局、分组、对齐、间距、密度、字号、字重、行高与行宽 |
| 视觉表达 | 色彩角色、对比关系、图像与图标、组件一致性、品牌特征及视觉重点 |
| 调性调整 | 更大胆、更克制、删繁就简、增加趣味和探索强视觉效果等不同方向 |
| 交互体验 | 文案、操作反馈、状态过渡、动效、错误说明与恢复路径 |
| 使用质量 | 响应式、长内容、加载、空态、错误、禁用、成功状态、可访问性和与本次改动相关的性能 |
| 评审与精修 | 问题定位、用户影响、反模式提示、局部一致性修正和前后比较 |
| 风格参考 | 素材中的极简、编辑式、粗野主义、玻璃质感等风格候选及其适用条件 |

素材中的具体技巧、参数建议和独特例子不能只因尚未测评而被全部压缩成通用建议。允许合并重复表达，但要能从能力对应关系中追溯其去向。仅有名称、无法取得正文的能力记录为来源线索，不补造实现细节。

字体、渐变、圆角、卡片、纯色或动画类型不天然构成缺陷。来源中的绝对审美禁令应保留其原始立场，并在本模块中按适用风格和用户约束使用。固定 React、Tailwind、Lucide、移动端三套和 Web 两套方案等设置保留为来源中的实现选择，不自动约束所有项目。

可访问性和性能检查服务于当前任务，不无条件要求新增暗色主题、缓存、动效库或其他能力。发现超出任务范围的问题时说明影响，不以美化任务为由自动实施。

## 7. 外部 Skill 怎样引入和维护

### 7.1 记录来源与每项能力的去向

逐项登记原始清单涉及的外部 Skill，说明正文是否已取得、是否采用或合并、哪些效果待验证。采用的内容至少记录以下信息：

- 名称、原始作者、原始地址，以及转引或改编来源；聚合仓库不是所有条目的原始作者。
- 固定版本或 commit、取得日期；本地包及无版本文件使用内容校验值识别。
- 原始文件与必要资源的位置、许可及归属声明、工具和运行依赖。
- 引入方式、本地对应章节或文件、实质改动及改动原因。
- 已知适用条件、验证状态与仍需核对的事项。

来源清单还要说明每项能力的去向。例如，外部 `layout` Skill 中的方法进入了本地哪个章节，哪些与其他来源合并，哪些作为候选保留，哪些因材料或许可不明确暂未分发。这样既能回查原文，也能发现整理时的遗漏；一条仓库链接不足以代替这些记录。

### 7.2 三种引入方式

| 方式 | 适用情况 | 要求 |
| --- | --- | --- |
| 吸收并改编 | 与共同工作流重叠，需要合并、处理冲突或适配项目 | 本地维护整理后的指令，保留来源、能力对应关系与实质改动说明 |
| 保留原文并按需引用 | 内容相对独立、细节值得保留，或尚需验证 | 明确读取条件及参考或执行用途；执行所需内容随 Skill 分发 |
| 可选外部依赖 | 能力需要独立脚本、工具或完整运行环境 | 明确能力用途、版本、前置条件和不可用时的行为；不能把提及或链接视为已经安装 |

初版以改编和按需引用为主。具体条目选择哪一种方式，需要根据其正文和依赖确定；未完成核对的条目保持显式状态，不批量承诺能够直接运行。

### 7.3 原文与本地维护内容

对实际纳入且允许复制的材料，保存一份原样副本，与我们改编后的内容分开维护。原样副本用于回查，不能直接覆盖修改。执行流程需要的参考文件、脚本和资源必须一起分发，不能只复制入口文件。

每份原文要说明用途：供模型参考，还是在特定条件下执行。读取它不代表允许执行其中所有命令；原文里的安装步骤、写入路径和审批流程不能覆盖用户要求、目标项目规则或扩大本次授权。

### 7.4 许可与更新

复制或改编前核对具体内容的许可、归属与必要声明，随分发内容保留适用的许可证、NOTICE 和修改标记。许可不明确的内容保留来源与候选记录，待澄清后再决定复制分发；不能因为聚合仓库附有许可就推定所有收录条目都适用。

外部来源的版本在引入时固定，日常任务不自动下载最新版。需要更新时，先比较外部变化与我们的改编，再更新受影响的来源记录、方法和验证结论。

## 8. 使用经验、能力缺口与持续改进

### 8.1 哪些必须遵守，哪些可以尝试

| 内容性质 | 模型如何处理 |
| --- | --- |
| 用户要求、品牌规范、既有行为 | 当前任务必须满足，不因技巧偏好而改变 |
| 有适用条件的经验方法 | 按问题选择，在本次任务中检查影响 |
| 尚未证实的技巧或参数建议 | 保留来源、适用条件和验证问题，可以在授权范围内作为候选尝试 |
| “最强”“更惊艳”等比较主张 | 保留为来源观点，不能直接作为选型事实或交付效果 |

对重要的待验证经验，用简短条目说明做法、来源、适用场景与限制、预期改善、验证方式和已有结果。不要求每个普通建议都建立复杂记录。

例如，“减少卡片容器可能改善拥挤感”可以保留。遇到容器过多的页面时，比较分组清晰度、信息查找和视觉干扰；如果去掉容器使关系更模糊，应记录不适用条件，而不是把某一次尝试推广为通用禁令。

### 8.2 反馈与结论

实际使用后的结论可以表述为“该场景支持”“该场景不支持”或“证据不足”，同时保留页面类型、相关内容和验证条件。一次成功不升级为普遍规律，一次失败也不直接删除整个方法。模型模拟用户和启发式评分可辅助发现问题，但不等于真实用户完成率、效率或转化率证据。

候选经验在后续真实任务中逐步验证，不要求初版前全部测完。当次任务仍要检查功能和交付结果，未测的页面或方法保持未验证状态。

### 8.3 每次使用沉淀什么

在前端任务收尾时，将本次真实观察整理成简短使用记录；包括成功、部分完成、失败及仅评估的任务。任务在可正常交付的阶段暂停时，也记录已有结果和未完成项。用户明确不记录或限制写入时遵守其要求，不能为了收集经验扩大任务。

| 记录内容 | 至少能够回答的问题 |
| --- | --- |
| 任务与版本 | 什么场景、什么目标、用了哪一版或哪份 Skill、结果到哪一步；不明信息保持未知 |
| 优化经验 | 采用了什么做法，在哪种条件下改善、没有改善或产生副作用，有什么直接证据 |
| 未支持或支持不足的需求 | 用户需要什么；Skill 缺少方法、只覆盖一部分、已有方法难以找到或执行，还是本次环境缺能力；判断依据是什么 |
| Skill 之外的补充 | 为满足哪个需求，使用了其他 Skill、工具、外部资料或模型自行提出的做法；做了什么、是否成功、如何验证，哪些内容值得纳入本 Skill |
| 使用情况 | 本次相关的流程、参考章节或技巧哪些被读取、实际应用、调整后应用、考虑后未采用；已知未采用原因是什么 |
| 效果与流程问题 | 哪些部分省力、清楚、有正向结果，哪些无明显收益、反复澄清、重复读取、返工或缺少衔接；建议改哪里及理由 |

外部工具的正常执行与 Skill 的能力缺口分别记录。例如，按 Skill 的方法用现有浏览器截图，不代表 Skill 缺少截图能力；必须自行补充 Skill 未提供的适配方法，才构成需要研究的内容缺口。其他能力完成了功能，也不意味着这项能力已经被 Skill 支持。

记录聚焦本次有关的部分，不要求逐条评估整套方法库。未读取不等于未使用，未提及也不等于不适用：已有上下文中的方法可能被直接应用；无法确认的使用情况记为未知。结果与某个技巧相似，不足以证明该技巧被使用。事实、用户反馈、模型判断和待验证的改进建议需可区分。

### 8.4 如何保存并跨任务使用

经验必须能在后续任务中重新读取，不能仅依赖当前聊天上下文或会被清理的临时证据。每次任务有一份可识别的记录；同一任务后续补充和重试继续关联原记录，不能被当成多个独立使用样本。没有新问题时保留简短的使用与结果信息，不编造发现。

用户已选择统一放在工作区外的持久目录，便于跨项目汇总。该目录与 Skill 分发内容分开，避免安装、更新时覆盖经验；设计提供默认位置，用户或目标项目的有效约定可以覆盖。已确定且仍有效的位置沿用，不每次重复询问。本轮只确定设计，不创建记录目录。

本仓库的截图、日志、评估记录和临时产物仍遵守工作区外临时目录规则；需要长期保存经验时，明确约定与获授权的持久位置。临时产物只作补充证据，记录正文应包含足以理解结论的摘要；证据已不可用时说明，不能把失效链接当成可回查证据。只记录总结所需的最少业务信息，不默认保存完整代码、客户数据或对话，也不自动外发。

记录位置尚未确定、不可写，或当前任务禁止写入时，在交付中提供未保存的记录内容并说明状态；已有明确授权允许记录到单独位置时可以遵循。页面任务的完成状态与记录是否保存分开报告，不能声称尚未持久保存的内容已经沉淀。

### 8.5 怎样用记录改进 Skill

在用户要求回顾或优化 Skill 的维护任务中，读取指定范围的历史记录，按场景、Skill 版本和具体方法归纳：高频使用且有正向证据的内容、采用少及其原因、无明显收益或有副作用的内容、反复出现的能力缺口，以及流程的改进机会。

“使用更多”必须说明统计了哪些任务、时间和版本，以独立任务计数，不能把重复读取或同一任务多轮尝试当作多个使用样本。只有记录了适用机会，才能比较采用比例；没有这类数据时只报告观察到的次数和覆盖缺口。未出现使用记录、没有适用机会、未被模型发现和采用后无效是不同情况，不能合并成“没价值”。

每条改进建议应能回查原记录，指出拟调整的 Skill 部分、建议动作、预期改善及验证方法。可以提出补充方法、改善入口提示、合并重复规则、调整流程或保留候选；低频和单次负面结果不自动触发删除。方法有效性、使用频率和用户偏好分开判断，缺少对比或多项改动无法归因时保持不确定。

沉淀和归纳属于本能力；修改 Skill 的源码、安装副本、能力范围或外部依赖仍需相应维护授权。归纳结论可以成为后续需求或设计的依据，不能自动变成已经批准的执行任务。完成获授权的改进后，将变更位置和后续验证结果关联到原建议，保留从使用反馈到改进结果的来龙去脉。

## 9. 交付什么以及怎样验收

### 9.1 单次使用的交付

交付内容随任务规模组织，但必须让用户看清本次目标、采用的方法与理由、实际改动或建议、直接证据和仍未验证的事项。只读任务交付评估；已授权实施的任务交付相应页面或代码与检查结果。发现不在当前范围内的问题单列说明，不混入已完成结果。

### 9.2 初版 Skill 是否能正确使用

先检查模型能否按要求使用 Skill，以及复制出去后能否独立使用。具体检查如下。

| 编号 | 场景 | 用户可观察的通过条件 |
| --- | --- | --- |
| A1 | 从仓库入口读取，以及将完整 Skill 复制到工作区外后读取 | 模型能够找到实际需要的参考，执行内容不依赖源码外层、Downloads 或临时笔记 |
| A2 | 要求局部美化，并明确保留功能、品牌和技术栈 | 模型围绕局部目标选择方法，沿用有效规则，不自动扩展产品功能或全面换肤 |
| A3 | 新页面请求提供产品、内容和目标受众 | 模型能把语境转化为具体视觉选择，并说明代表页面如何检验这些选择 |
| A4 | 只提供一张参考截图 | 模型区分可见特征、估算和补充设计，不声称已从截图确认动态或隐藏行为 |
| A5 | 明确要求仅评估，或环境缺少运行验证能力 | 模型保持授权范围，交付结论准确表达已观察内容和未验证边界 |
| A6 | 检查采用、合并、候选及暂未纳入的外部能力 | 每项能追溯到具体来源与处理结果；适用的随包许可和执行资源完整；原文与本地改编可区分 |
| A7 | 选择一个尚未证实的技巧；存在可选依赖时另检查其不可用场景 | 候选仍保留但不冒充已证实；适用时依赖缺失得到说明，不假装执行成功或擅自安装，不为验收另造依赖 |
| A8 | 使用 Skill 完成或尝试一个任务，其中一项需求需要借助 Skill 之外的方法；同时出现有效、无明显收益和考虑后未采用的内容 | 使用记录与实际动作一致，明确需求缺口、补充能力、结果与证据；正常使用执行工具不误记为内容缺口，失败和未完成结果不遗漏 |
| A9 | 汇总多份不同场景、不同版本的使用记录，其中包含同一任务的重试、已知未采用原因和未知项 | 使用次数不重复计算；能区分少用、未发现、不适用、无正向结果和未验证；频率及效果结论可追溯且不超出数据覆盖范围 |
| A10 | 在已约定位置保存记录，后续会话重新读取；另检查禁止写入或保存失败的情况 | 记录脱离当前会话仍可用，更新 Skill 不覆盖经验；不能保存时交付内容并明确未保存，保持写入边界 |
| A11 | 根据历史反馈提出 Skill 改进建议 | 建议指向具体内容与证据，包含拟改动和验证方式；不会自动修改 Skill、删除低频方法或扩大依赖；后续获授权的变更可关联原建议 |

通过让模型实际读取 Skill 并处理具体请求，检查它的回答、动作和产物。文义检查、文件头元数据（frontmatter）、链接与复制完整性检查只能辅助验证；不能用标题、关键词、行数或文件存在代替行为判断。试跑采用足以区分实际决策的少量场景，无需另建形式化评测框架。

### 9.3 真实页面是否得到改善

后续试用时，围绕具体任务执行以下检查，并只报告已经覆盖的场景：

1. 在相同内容、视口和状态下比较前后界面，能指出与目标对应的层级、阅读、密度、一致性或风格改善。
2. 走通受影响的关键操作，检查与页面有关的加载、空态、错误、禁用、成功及长内容状态，确认必须保留的行为没有退化。
3. 按改动风险检查窄屏适配、键盘操作、焦点、对比度、减少动效偏好和性能等相关质量，不用截图替代操作验证。
4. 将候选方法的结果与具体场景关联；没有改善或存在副作用时如实记录并调整适用条件。

尚未有真实页面证据时，可以交付可试用模块，不能宣称美化效果已验证。若任务目标涉及完成时间、转化率或真实用户偏好，需要相应测量或反馈，不能由模型评分推导。

## 10. 范围边界与待确定事项

### 10.1 初版不承担的职责

- 不默认批量安装或执行所有外部 Skill，不自动更新上游、发布模块或修改全局安装目录。
- 不创建独立工作流引擎、自动评分平台、浏览器封装、模型服务或自行改写 Skill 的自动学习系统；第 8 节的使用记录、历史归纳和改进建议属于初版范围。
- 不要求新增安装器、演示站点、固定前端模板或技术栈；必要性应由具体使用需求证明。
- 不把局部美化扩展为后端改造、业务流程重写、全站架构重构或完整 PRD 重建。
- 不把所有风格、所有技巧和所有目标环境的实测作为初版整理工作的前置条件，也不据此省略当次实际任务的验收。

### 10.2 仍需确定的事项

| 事项 | 当前边界 | 确定时机 |
| --- | --- | --- |
| 外部 Skill 的完整清单与固定版本 | 已有来源入口，不代表逐项正文、资源和许可均已核对 | 正式引入前，在设计中明确采用与候选范围 |
| 个别内容的许可与运行依赖 | 不明确时保留来源；不直接复制分发或声称可运行 | 决定引入方式前 |
| 参考文档粒度与来源文件组织 | 沿用第 4 节的文件职责；细化内容与引用关系，组织调整不能改变要求和能力范围 | 模块设计阶段 |
| 首批真实页面与重点验证技巧 | 尚未指定，不擅自修改当前仓库其他模块的界面 | 后续真实试用任务 |
| 目标平台的具体安装位置与工具能力 | 使用通用 Skill 结构，运行时按实际环境判断 | 安装或使用任务 |
| 经验记录的持久位置 | 用户已选择工作区外统一持久保存；默认路径由设计明确，并遵守实际写入约束 | 审阅设计中的默认位置；首次使用时若存在约束冲突再处理 |

这些未定项不阻塞本需求文档的整理。涉及行为变化、能力缩减或新增执行依赖的决定，需要在后续设计中显式说明，不能作为实现时的隐含选择。
