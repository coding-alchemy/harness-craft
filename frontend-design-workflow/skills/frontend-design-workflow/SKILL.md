# 前端设计工作流

让视觉选择服务内容和使用任务，用实际界面与操作判断结果。支持已有页面优化、新页面设计、参考风格迁移和仅评估。任务收尾保存使用记录；明确的维护请求可回顾记录、提出建议，并关联获授权改进后的结果。

## 进入任务

从请求、项目资料和环境确认：目标对象、希望改善的问题、必须保留的功能/品牌/技术栈/规范、允许的动作，以及能取得的验收证据。已有信息直接使用；只有缺口会造成不同决策时才澄清。沿用目标项目与用户的有效规则和授权。

先查看实际界面及相关实现，识别已有组件、颜色角色和排版规则。有运行条件时观察运行结果；只有源码时给出静态判断。仅评估请求止于评估交付，不改页面或 Skill；全程只读请求保持所有文件不变，独立反馈写入仅沿用有效的单独授权。无法读图、运行、操作或保存时，明确相应限制，继续可独立完成的部分。

## 按需读取

- 新页面、参考图迁移、风格选择或现有规则不足时，读[视觉方向与规则](references/visual-direction.md)；已有页面方向有效时直接沿用，无须重读整个分支。
- 发现具体布局、阅读、视觉或交互问题时，读[优化技巧](references/improvement-techniques.md)的相关小节。
- 确定成功标准、检验代表对象和收尾时，读[验证与反馈](references/validation-and-feedback.md)。

明确要求回顾使用记录或改进本 Skill 时，直接读[验证与反馈的历史归纳和维护规则](references/validation-and-feedback.md#历史归纳与改进)，按指定范围读取记录；不重新启动页面制作或完整需求访谈。记录和建议不构成修改 Skill、增加依赖或下载上游的授权。

## 六个环节及继续条件

1. **明确目标与现状。** 用简短任务说明连接问题、保留约束和成功表现，不要求另建文件或完整 PRD。
2. **视觉方向。** 确认现有方向仍有效；需要补充时说明它如何服务主要任务。方向应能指导强调程度、布局、文字与颜色选择。
3. **视觉规则。** 只补充受影响的色彩角色、文字层级、间距、组件、响应式或状态规则；写清值或关系、适用对象、依据，区分事实、估算和补充设计。
4. **验证代表页面。** 选择能暴露主要难点的页面、组件或流程，使用真实或接近真实的内容。先观察规则是否适用，有问题先调整，再推广到其余目标。局部组件本身可作为代表对象，不另建展示工程。未运行的方案保持未验证。
5. **定向打磨。** 围绕一个主要问题处理必要关联变化，说明原因、方法与影响。优先解除任务阻断和阅读/操作障碍，再改善层级、一致性及细节；用户指定的专项目标优先。达到目标后停止扩展。
6. **实际验收。** 同条件比较界面，走通受影响操作，按风险检查相关质量。用证据判断改善与保留行为，缺口保持明确；测试通过或自评分不能替代页面验收。

已有有效成果可满足相应前置条件，无须重做。局部优化不自动变成完整重设计、固定数量方案或切换技术栈。用户内容、品牌、功能与指定风格优先于来源偏好。

## 任务收尾记录

前端任务成功、部分完成、失败、仅评估或可正常交付的暂停时，按[验证与反馈](references/validation-and-feedback.md#任务记录)整理本次实际使用与结果，默认保存一份简短记录。沿用用户/目标项目有效位置约定；没有覆盖约定时默认 `~/.frontend-design-workflow/feedback/`，实际写入仍须满足授权、信息范围和环境约束。测试覆盖为工作区外临时目录，不使用真实经验位置。

全程只读、禁止写入或关闭记录的要求优先；已有有效授权允许单独反馈位置时沿用，不重复询问。页面结果与保存状态分别交付，不能将未保存内容称已沉淀。

## 交付与来源边界

交付本次目标、采用方法及理由、实际改动或有具体对象的建议、已完成检查和未验证项。仅评估给出位置、问题、影响、调整方向与验证办法；已实施任务提供实际页面与操作依据。另用一句话返回记录位置，或明确未保存原因；详细字段留在记录里，不重复铺满普通交付。
