## 2. 用户可观察的结果与范围

Codex 在设计规定的首次场景先发一张测试卡片，用户确认真实收件及固定目标后，才开始或继续已获执行授权的任务；同一对话不重复测试，新对话重新测试。任务终态使用现有审批可见命令，符合条件的权限请求由 Auto-review 处理，用户离席时仍能收到有任务和结果信息的通知。首次成功不构成后续必达承诺。

复用现有 `prepare-shell`、`send`、`rich`、`task`、固定接收人、脱敏、重试及六文件安装链路；新增内容仅为 Codex 指令路由及其验证。其他 Harness 不增加首次测试或确认门禁。CLI、配置 schema、HTTP、卡片、客户端、安装机制和 Codex policy 不变，不增加后台服务、本地确认文件或发版步骤。

## 4. 验证门禁与覆盖

| 设计要求 | 阶段 01 的证据 | 阶段 02 的证据 |
| --- | --- | --- |
| 首次发送、待收件确认、同对话去重、新对话/分叉与恢复 | 源指令语义核对、必要合同断言 | 安装后会话的调用顺序、用户回执与卡片数量 |
| Auto-review 可用性、审批可见正文及离席终态 | 无强制人工持久规则、无审批后 stdin；现有接口回归 | 当前会话模式、完整可见调用、无人工审批等待、实际终态收件 |
| 通知不授权执行、仅状态通知与仓库自动通知例外 | 正反例语义核对，不从收件确认推导任务执行授权 | 最少行为试跑，核对任务未被错误启动或恢复 |
| 拒绝、超时、未知投递、隐私重写与失败隔离 | 保留现行合同，检查停止与单次重写条件 | 安全可复现的行为试跑；区分模拟证据与真实外发结果 |
| 其他 Harness、argv/stdin、卡片、配置和安装行为 | 检查非 Codex 分支未变，运行模块现有回归 | 核对安装一致性及其他 Harness 无新增门禁的行为证据 |

阶段 01 运行项目现有模块回归：

```bash
python3 -B -m unittest discover -s feishu-connector/tests -p 'test_*.py' -v
```

指令以自然语言语义核对为主，只用最少行为试跑消除会改变决策的歧义；不新增评测框架或测试工具链。实现差异须通过适用评审及单独的 Karpathy 精简与自检，再进入真实验收。无现成适用 Markdown 静态工具时检查相对链接、命名、代码块和 `git diff --check`，如实说明局限。

所有试跑材料、回执记录、测试日志和临时安装副本放在 Git 工作区外的临时目录；仓库计划仅记录批准、执行状态与验收是否满足，不保存测试报告副本。真实外发使用操作者明确指定的测试应用及固定测试接收人，不记录真实秘密或完整 Open ID。

## 5. 整体完成标准与收尾

1. 源 Skill 与安装副本符合 V0.5，其他 Harness 的当前行为及现有发送合同得到保留。
2. 设计第 8 节的各项验收均有相应证据；首次测试必须真实收件，离席成功、失败、待确认卡片必须与各自获授权的测试任务一致，且发送没有等待人工审批。模拟结果不能代替这些真实收件。
3. 同对话第二次无测试、新对话/分叉重测、恢复可复用、通知授权边界及失败不补发均已核对；安装一致、离线回归通过，适用评审无未闭合问题。
4. 使用文档据实记录最终行为和限制；本次 V1.5 正式记录已获用户明确授权。后续补充验收不改写已发布历史，也不按验收轮次新增产品版本，不宣称绝对必达。
5. 所有直接验收满足后，在同一收尾变更中删除本路线图与两张 ticket，从[计划索引](../README.md)移除，并清理设计与公开说明中指向已删除计划的链接。当前产品行为保留在现行合同、使用文档和 CHANGELOG。

缺少客户端能力、测试环境、用户收件确认或其他必要证据时，保留计划与未完成项；不得以测试通过、安装成功或一次 reviewer 放行关闭任务。涉及人工操作或决定时标记 `ready-for-human`，缺失必要信息时使用 `needs-info`，与文档批准状态分开维护。

## 6. Karpathy 精简与自检

复核已批准设计的基线、差异、最小方案、删除审计和直接验收，不重新引入持久命令规则、接收人绑定或第二套发送机制。本计划仅分开“源行为可审阅”和“安装后真实结果可验收”两个必要阶段；文档同步归入阶段内，不另设纯收尾阶段。测试规模限于现有模块回归、关键指令分支及设计要求的直接结果。
