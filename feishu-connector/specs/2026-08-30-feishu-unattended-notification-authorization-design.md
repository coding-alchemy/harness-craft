## 1. 问题与目标

V0.4 把离席通知建立在“先切人工审批、保存精确 `task` 允许规则，再测试收件”之上。当前 Codex 已支持 Auto-review：需要审批的调用可以交给独立 reviewer 决定，无须每次等待人在场。持久命令允许规则不再是本设计的必需前提。

本轮用户已明确选择：Codex 采用 Auto-review；其他 Harness 保持当前已实现的发送与审批行为，不新增首次测试。Codex 继续保留每对话首次真实收件确认，确认后同一对话不重复测试。

核心结果是：用户在场时完成一次测试并认可当前固定接收人；在原任务已经获得执行授权的前提下，Agent 随后工作，离席终态通知由平台自动审批并实际送达。首次测试证明当时链路可用，后续每次调用仍独立接受平台判断，不能承诺必达。

用户于 2026-10-18 明确批准本版设计，并要求编写执行计划。设计批准时尚未实现；当前实现已纳入 V1.5，剩余实际上下文压缩后的确认保留验收由[实施路线图](plans/feishu-unattended-notification-authorization/README.md)跟踪。设计批准不等于执行计划批准或实现执行授权。

## 2. 基线与 Codex 当前能力

本节记录设计修订时的基线；当前实现与验收状态由第 7 节及实施路线图说明。

### 2.1 仓库现状

本轮已对照源 [Skill](../skills/feishu-notify/SKILL.md)、[CLI](../skills/feishu-notify/scripts/feishu_connector/cli.py)、[配置解析](../skills/feishu-notify/scripts/feishu_connector/config.py)、[客户端](../skills/feishu-notify/scripts/feishu_connector/client.py) 和 [Skill 合同测试](../tests/test_skill.py)：

- 当前 V1.4 已具备 `send`、`rich`、`task`、`task --auto`、离线 `prepare-shell` 和审批可见正文；尚无对话级测试与确认路由。
- `prepare-shell` 使用当前解释器和入口的绝对路径、`--project-root=<绝对路径>` 及真实消息字段生成命令；不读飞书配置、不联网。POSIX Shell 与完整命令 96 KiB 上限继续适用。
- 真实发送读取固定接收人配置。配置优先级为环境变量、项目 JSON、全局 JSON；诊断只显示来源并隐藏完整 Open ID。因此项目根固定并不等于接收人被命令绑定。
- 结果正文、隐私脱敏、一次有条件的隐私重写、`sent`/`skipped`、退出码、进程内 UUID 与重试继续遵守现行合同，不另建通知接口。
- [安装器](../install_skill.py) 的六文件清单已包含 `SKILL.md`；只修改 Skill 内容不需要改变 manifest 或安装行为。

### 2.2 官方能力与适用边界

以下结论按 2026-10-18 获取的 OpenAI 官方文档核对：

| 能力 | 对本设计的影响 |
| --- | --- |
| [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review) 在交互式审批策略下接管符合条件的请求；`approval_policy = "never"` 没有请求可供审查 | 使用当前会话的 Auto-review，保留沙箱与权限边界；不以关闭审批换取离席运行 |
| reviewer 能看到压缩后的可见对话与具体审批请求，看不到隐藏推理；可独立拒绝或发生超时 | 将用户授权、测试收件确认和完整发送正文留在可见上下文；这提供判断证据，不保证通过 |
| [Permissions](https://learn.chatgpt.com/docs/permission-modes) 中的 **Approve for me** 是否可用、是否选中取决于会话、客户端和组织要求 | 按实际会话确认能力；不能从“安装了新版本”或模型名称推定已启用 |
| [Rules](https://learn.chatgpt.com/docs/agent-configuration/rules) 的允许前缀可让匹配命令免于提示；持久保存的文档说明针对 TUI，规则仍属实验能力 | 移除“所有 Codex 界面均可保存精确前缀”的假设，也不把前缀规则当作接收人或正文授权证明 |
| [审批与网络边界](https://learn.chatgpt.com/docs/agent-approvals-security) 独立于 reviewer 选择；托管限制优先 | Auto-review 不授予网络权限。真实发送继续按当前执行器合同申请权限 |

本地 `codex --version` 为 `codex-cli 0.147.0`，仅代表本地 CLI，不代表桌面端或官方最新发行版本。本次会话提供 `auto_review`；本轮没有测试飞书审批与真实收件，不能据此判定该链路已可离席使用。

## 3. 保留要求与行为差异

保留固定接收人、结果优先与隐私脱敏、审批可见命令、每个通知节点最多一次逻辑发送、未知投递状态不跨进程重试，以及通知失败不改变原任务结果。Skill 不读取或展示秘密来证明接收人归属。

相对 V0.4 的变化集中为：

| 项目 | 本版设计 |
| --- | --- |
| Codex 首次准备 | 保留测试与用户收件确认；使用 Auto-review，取消必须切人工审批和保存 `task` 前缀的步骤 |
| Codex 后续发送 | 每次提交审批可见命令；需要审批时由平台自动审查，不把首次通过视为后续豁免 |
| 其他 Harness | 保持当前已实现行为，不新增首次测试、对话确认或 Codex 配置要求 |
| 只有通知请求、没有正在执行的任务 | 按仓库规则发送一次前一任务的当前状态；不为测试而启动、恢复或继续任务，也不额外发送测试卡片 |

前三项依据本轮用户确认；第四项落实仓库已有通知授权约束。本版整体已获用户评审批准，设计批准本身不改变实现；后续实现按已批准范围执行。

同一对话期间假设固定接收人配置保持不变；用户主动修改后应明确要求重新测试。继续不新增接收人指纹、CLI 参数、配置字段、本地确认文件、MCP、插件、Hook 或后台服务。安装器和 Skill 不自动修改 Codex 配置、规则、网络 allowlist 或组织策略。

## 4. 方案比较与选择

| 可行方案 | 选择依据 |
| --- | --- |
| 保持当前 Skill，由用户手工测试并确认 | 可以发送，但不能落实每个 Codex 对话首次测试与去重，仍依赖用户记住流程 |
| 在 Skill 中加入 Codex 路由，复用 Auto-review 与现有发送链路 | 采用；只补触发、确认和发送时序，不改变连接器接口 |
| 由用户预先配置精确持久命令规则 | 是减少人工提示的另一条路径，但需要维护解释器、入口与项目路径，也不能绑定隐藏的接收人。本轮不新增该设置流程或要求；用户已有规则继续由平台处理 |

保留现有发送调用是实现量最少的方案，但缺少用户要求保留的首次确认行为；因此采用 Skill 层补充。接收人绑定 CLI 需要改变配置与发送合同，完整自定义 reviewer policy 需要维护平台策略，事件 Hook 需要另行判断任务终态，均不属于本轮目标。

只有一项新增的对话记录：本对话测试已获用户确认。业务通知授权仍来自用户针对相应任务的请求或仓库规则；审批模式由平台提供，不复制到数据库或激活文件中。

## 5. Codex 流程

### 5.1 先判断请求与任务授权

每次请求先按下表判断授权与路由；仅需首次测试的分支进入后续准备，不能用测试状态扩大任务或通知授权：

| 情况 | 行为 |
| --- | --- |
| 用户仅说“完成后通知我”，没有正在执行的任务，也没有新的任务执行授权 | 只发送一次前一任务当前状态；不进入额外测试，不记录离席准备完成 |
| 仓库规则只授权结果或待确认节点的自动通知 | 按原有 `task --auto` 发送；该规则本身不授权增加一张前置测试卡片 |
| 本对话已有确认记录 | 跳过测试；核对本次通知授权后进入后续发送 |
| 用户已授权具体任务执行，并要求结果通知，且本对话未确认测试 | 在任务开始或继续前进入首次测试；收件确认前暂停原任务后续执行 |
| 用户直接要求发送指定消息，且本对话未确认测试 | 先完成首次测试与确认，再按原有 `send`、`rich` 或 `task` 路由发送原消息 |

需要首次测试时，先检查本对话已有调用证据：测试已发送但待确认时只继续等待；已有失败或状态不明时按第 6 节处理；尚未发起时才准备新测试。再次出现通知请求不构成重复测试或重试授权。

测试确认不批准需求、设计或执行计划，也不授权开始或恢复原任务。测试准备完成而原任务仍待批准时，保持待批准状态；不得把“收到测试”当作“按计划实施”。

### 5.2 确认 Auto-review 可用

以会话提供的权限信息为准。桌面端检查本对话已选择 **Approve for me**；CLI 的对应设置为 `approvals_reviewer = "auto_review"`，并需保留会产生相关请求的交互式审批策略，例如 `approval_policy = "on-request"`。这些是环境前提，不是 Skill 自动写入配置的步骤。

已知当前使用 Auto-review 时直接继续，无需再次询问用户。信息不足时只核实缺失项；当前为人工审批且客户端支持切换时，请用户通过支持的入口选择 Auto-review，选择前不发送测试卡片。功能不可用或组织不允许该模式时，报告本方案在当前环境不可用，不反复要求切换。

不把 Full Access、关闭审批、扩大网络访问或新增宽泛命令规则作为替代。精确规则可能改变平台是否需要审查；Skill 不承诺每次必然出现 reviewer 项，也不擅自修改用户已有规则。

### 5.3 一次测试与收件确认

1. 在可见对话中说明本次向已配置固定接收人发送非敏感测试卡片，用于确认当前对话的通知链路，不附加工作区数据。
2. 使用现有离线 `prepare-shell` 准备显式 `task`，不加 `--auto`。固定字段如下：

   ```json
   {"flow":"task","status":"success","project":"Codex","conversation":"飞书通知测试","content":"这是当前 Codex 对话的飞书通知测试。请回到本对话确认已收到，并认可当前配置的固定接收人用于本次请求的通知。"}
   ```

3. 只移除准备结果最后一个换行，原样提交完整命令。使用当前 Codex 执行器的 `sandbox_permissions=require_escalated`；支持限制目标时仅允许 `open.feishu.cn:443`。审批理由说明本次测试用途与固定目标，不建议新的持久 `prefix_rule`，不改用审批后 stdin。
4. stdout 出现 `Feishu message sent` 后，等待用户明确确认真实收件并认可该固定目标。命令成功、reviewer 批准和 Agent 自述都不能代替用户确认。尚未确认时等待，不再发送测试催收。
5. 用户确认后，在当前对话公开记录“本对话飞书测试已确认，用户认可当前固定接收人”；随后核对原任务的执行授权，满足时才继续。记录不包含完整 Open ID、凭据或配置值。

首次测试和原通知是不同用途的消息；测试卡片不代替用户要求的原消息或任务终态通知。固定的测试正文也不表示已批准未来所有正文。

### 5.4 后续发送与确认复用

- 同一对话已有确认时不再发送测试，也不再要求收件确认；每次业务通知仍须有对应授权，原请求的完成后通知只覆盖该任务一次结果。
- 显式任务通知用 `task`，仓库自动通知用 `task --auto`；指定消息仍按现有 `send`、`rich` 路由。持久规则或首次测试不扩大这些接口的授权范围。
- 任务正文反映真实的 `success`、`failure` 或 `confirm`，保留任务与结果语义，仅替换敏感值。每次重新离线准备完整正文并原样提交，接受当次平台决定。
- 成功只按现有 `sent` 信号报告；`skipped` 不算发送。一次测试收件不能代替任务终态的实际收件证据。
- 当前会话切回人工审批或权限条件变化时，重新核实离席条件；不为此重复发送收件测试。无法自动继续时报告需要用户处理，不能声称离席通知仍可用。
- 新对话（包括分叉）重新测试，不沿用父对话确认；恢复同一对话可以复用其明确记录。上下文压缩应保留确认归属；无法确定记录属于当前对话时，不能推定已确认。
- 用户明确修改固定接收人或要求重新测试时，清除本对话确认并重新执行首次流程。无此信号时不增加每次配置探测；自动检测接收人变化仍不在范围内。

## 6. 拒绝、失败与离席边界

| 条件 | 行为 |
| --- | --- |
| reviewer 拒绝测试或终态发送 | 展示拒绝动作与原因；仅可按现行合同提交实质更安全的替代，否则停止该发送并请求用户处理，不换规则、审批模式、渠道或间接执行来绕过 |
| 发送进程未创建，拒绝指向隐私或目标信任，且明确允许更安全替代 | 严格沿用现行合同的单次脱敏重写；仅隐藏或删除具体敏感值。目标归属证据不足时，删空结果不能补足授权，不重复申请 |
| review 超时、中止或工具错误 | 不等同于安全拒绝；按执行证据区分未执行与状态不明，本流程不自动再次发起发送 |
| 测试成功但用户未确认 | 保持未确认，原任务后续执行等待；不能自动发送第二张测试卡片 |
| 配置或飞书远程错误，或网络重试耗尽 | 沿用退出码与错误分类；不跨进程重试。无法确定投递结果时明确报告状态不明，不能断言未送达 |
| `task --auto` 输出 `skipped` | 没有发送，不当作链路测试或收件证据 |
| 休眠、断网、进程退出、任务取消或平台中断 | 不保证通知；保持现有手动取消不发送的合同，不增加补发队列或后台服务 |

Auto-review 的否决后恢复能力因客户端而异，不把某个 TUI 命令当作桌面端通用操作。测试通过后仍可能因真实正文、组织策略或运行状态变化而失败；通知链路也不能保证通过同一链路报告自身失败。通知失败单独报告，不把已完成的原任务改成失败。

## 8. 直接验收设计

以下是未来实现的验收要求，本轮没有执行真实外发。使用测试应用与用户认可的固定测试接收人：

| 场景 | 必须观察到的结果与证据 |
| --- | --- |
| 新 Codex 对话，已授权任务执行并要求飞书通知 | 原任务开始前只收到一张测试卡片；可见调用包含完整测试字段；用户确认收件及目标后才开始任务 |
| 已在执行的任务中追加通知请求 | 先暂停后续执行并完成首次测试；确认后继续，不把通知请求当作新增执行授权 |
| 测试成功但用户未回复 | 不开始或继续原任务，不再投递测试卡片；只看到待收件确认状态 |
| 同一对话第二次已授权通知 | 没有测试卡片或额外收件确认；实际业务通知按授权发送 |
| 用户离席，任务分别到达成功、失败和待确认节点 | 每个获授权节点收到一张有任务与结果信息的对应卡片；当次调用由平台允许且未等待人工审批，并有真实收件证据 |
| 新对话、分叉及同一对话恢复 | 新对话与分叉重新测试；恢复同一对话可复用其确认，不误用父对话记录 |
| 没有正在执行的任务，只要求“完成后通知” | 只收到一次前一任务当前状态，未启动或恢复任务，未插入测试卡片 |
| Codex 模式不可用或终态审批被拒 | 如实报告限制或拒绝；没有改写配置、放宽规则或重复发送，无成功假报 |
| 网络或投递状态不明 | 没有跨进程补发；通知结果与原任务结果分开，未知送达不报成确定失败 |
| 其他 Harness 的显式 argv、兼容 stdin 与仓库自动通知 | 继续遵循现有接口与平台审批，没有新增首次测试、确认等待或 Codex 设置要求 |

另对既有隐私重写正反例做针对性验证：只有满足现行全部条件才重写一次，结果语义保留；没有更安全替代或已经重写过时停止。单元测试、命令成功和文件检查均不能替代真实收件，以及离席时没有人工审批等待的证据。

## 9. 假设、限制与待验证项

- 用户首次收件并认可目标，是当前配置可用且符合其意图的证据，不是 Open ID 的密码学绑定；同一对话内未声明的环境变量或配置变化仍无法自动识别。
- Auto-review 依据保留的可见上下文和当次动作决定。显式请求、真实收件确认及完整正文有助于审查，但不能据此断言后续普通结果必定获批。确认信息经压缩后的保留效果需要行为试跑验证。
- 组织要求、客户端功能与工具接口可能不同；实际会话不支持必要审批或权限申请时，该环境不能通过本设计的离席验收，不通过自定义 policy 绕开。
- 本轮不增加其他 Harness 能力，也不据其一次发送成功声称支持本设计的离席流程。

## 10. Karpathy 精简与自检

以下为设计修订时的检查记录，不代替后续实现与真实链路验收。

- **基线：** 第 2 节对应当前合同、源 Skill、CLI、配置、客户端、安装器与测试，并将官方当前能力和本地 CLI 观测分开。连接器已有完整发送链路，缺口在 Codex 指令路由。
- **假设与差异：** 第 3 节逐项列明用户确认的 Harness 分流与仓库授权约束；第 9 节保留接收人变化、上下文保留及平台可用性的限制。只更新设计，没有未经批准的实现行为变化。
- **最小方案：** 第 4 节比较手工现状、Skill 补充和精确持久规则；复用现有发送与平台审查，不新增接收人协议、状态文件或平台策略。更少的改动不能实现保留的首次测试与去重要求。
- **删除审计：** 以第 2–3 节承载基线与要求、第 4–6 节承载决策与行为、第 7–9 节承载范围与验证。删除强制切人工审批、持久前缀申请、双重确认“已保存规则且收件”及其失败分支；不再重复 CLI schema、卡片 JSON 或既有脱敏规则。三处使用文档收敛为状态说明和本文链接，避免继续维护旧流程副本。保留首次测试、真实收件、同对话去重、新对话重测和结果内容要求，没有以精简削弱验收。
- **直接验收：** 第 8 节要求观察首次测试时序、真实收件、同对话无重复、离席无人工审批等待及其他 Harness 行为不变；失败场景同时检查未知投递和原任务授权边界。当前仅完成设计核对，真实链路验收留给获授权的实现阶段，不宣称已可无人值守送达。
