## 1. 问题与目标

当前连接器已经能通过 `prepare-shell` 把完整正文放入真实发送命令，也能在用户在场时发送 `task` 测试卡片。实际缺口不在连接器，而在 Skill 没有把下列人工可行流程自动化：

1. 用户先要求发送一张飞书 `task` 测试卡片。
2. 用户在工具审批中持久允许连接器的精确 `task` 命令前缀。
3. 用户确认飞书真实收件后再开始原任务。
4. 任务结束时复用持久规则发送终态卡片，不再等待用户审批。

核心目标是把这四步收进 Skill：当前对话第一次出现明确飞书发送意图时立即执行一次，之后该对话不再重复；新对话第一次使用时重新测试。

直接验收不是文件或规则存在，而是：第一次请求时原任务尚未开始，用户收到测试卡片并确认；同一对话第二次请求没有测试卡片；用户离席后仍收到终态卡片且没有新的运行时审批。

## 2. 用户要求与边界

- 当前对话第一次出现“发送飞书”“完成后飞书通知”或同等明确意图时，Skill 必须在原任务开始前立即进入测试流程。
- 测试卡片真实送达、用户已选择持久允许精确规则，并在当前对话明确确认这两件事后，Agent 才开始原任务或发送用户原本要求的消息。
- 同一对话确认成功后，后续飞书发送不再测试或询问确认。
- 新对话第一次使用时重新测试；已有持久规则时只测试收件，不重复申请规则。
- 持久规则只覆盖连接器的 `task` 子命令；`send`、`rich` 和其他命令继续按现有一次性审批合同执行。
- 固定接收人沿用现有配置；Skill 不修改、推断或动态选择 Open ID。
- 不新增接收人指纹、CLI 参数、配置字段、MCP Server、插件、Hook、后台服务或本地激活文件。
- 不通过 Full Access、`approval_policy = "never"`、宽泛解释器规则或关闭安全审批换取成功率。
- 当前 V1.4 尚未实现本设计，不能承诺无人值守送达。

## 3. 基线对照

现有能力已经覆盖大部分链路：

- `task` 已限制为 `success|failure|confirm`，并复用固定接收人、脱敏、失败关闭和进程内重试。
- `prepare-shell` 已生成审批可见的真实命令，命令顺序稳定为绝对解释器、入口、当前项目根、`task` 和动态字段。
- OpenAI Rules 支持精确 `prefix_rule`；用户在审批界面保存允许规则后，规则写入用户层并可供后续运行复用。
- 当前 Skill 已要求显式飞书发送使用沙箱外权限，但每次授权不自动延续，也没有“本对话已测试”的路由。

当前连接器命令不在审批前暴露完整 Open ID，因此不提供密码学意义的接收人绑定。对本设计的固定接收人场景，第一次真实收件和用户确认作为目标可用性证据；同一对话期间假设接收人配置保持不变。

## 4. 方案比较与决策

| 方案 | 结论 |
| --- | --- |
| 用户在每个对话手工先要求测试 | 能工作，但依赖用户记住顺序，不能保证原任务前执行 |
| 只在 Skill 中自动执行现有人工流程 | 采用；直接复用现有 `task`、`prepare-shell` 和平台持久规则 |
| 新增 Open ID 指纹和绑定 CLI | 拒绝；能检测配置变化，但不是“每对话首次测试一次”的必要条件 |
| 修改完整 Auto-review policy | 拒绝；操作和覆盖风险高，且不如精确命令规则确定 |
| MCP、插件、Hook 或守护进程 | 拒绝；当前流程不需要新的运行面 |

最小方案只有两个状态：

- **用户层持久规则：** 允许当前项目的连接器 `task` 前缀，解决任务结束时再次审批的问题。
- **当前对话确认：** 记录用户已确认持久允许并收到测试卡片，解决首次时序与重复测试问题。

不再引入接收人指纹。若未来核心目标改为自动检测 Open ID 变化并使旧规则失效，再单独设计连接器绑定；本次不为假设场景预留代码。

## 5. Skill 设计

### 5.1 首次触发

测试触发条件是：当前对话第一次出现明确飞书发送意图，且对话历史中没有由本流程建立的确认记录。

Skill 必须先暂停原任务，再按顺序执行：

1. 若当前 Auto-review 或其他审批模式不向用户展示持久规则选项，立即要求用户切换到可人工保存规则的审批模式；切换前不发送测试，避免为了取得规则而重复投递。
2. 使用现有 `prepare-shell` 准备固定 `task --status success` 测试卡片。项目为 `Codex`，对话为“飞书通知测试”，正文为“这是当前 Codex 对话的飞书通知测试，请确认已持久允许并回当前对话确认收到”。测试不得包含工作区数据、原任务结果或秘密。
3. 真实测试调用请求沙箱外网络权限，并建议持久允许下列精确前缀：

   ```text
   [绝对解释器, 已安装入口绝对路径, --project-root=<当前项目绝对路径>, task]
   ```

4. 用户必须在审批界面选择持久允许。只批准本次或只由 Auto-review 放行，不能满足离席条件。
5. stdout 出现 `Feishu message sent` 后仍须等待用户明确确认“已持久允许并收到测试”。审批通过、命令成功或 Agent 自述不能代替用户确认。
6. 用户确认后，Agent 在当前对话公开记录“本对话飞书测试已确认”，然后才继续原请求。

规则不得缩短为解释器、脚本入口或项目根，也不得扩展到 `send`、`rich`、Shell 包装器或任意 URL。动态状态、项目名、对话名和正文位于 `task` 之后，终态通知可以复用同一前缀。

### 5.2 后续路由

当前对话存在确认记录后：

1. 任务结果通知继续使用现有显式 `task`；仓库自动通知继续使用 `task --auto`。
2. 成功映射 `success`，不可恢复失败映射 `failure`，需要用户决定映射 `confirm`。
3. 同一对话的任何后续飞书请求都不再发送测试卡片或要求测试确认。
4. `send`、`rich` 仍按现有合同单独审批，不因 `task` 规则自动放行。
5. 只有 stdout 出现 `Feishu message sent` 才能报告已发送；投递状态不明时不得跨进程重试。

新对话没有确认记录，因此第一次飞书意图重新发送测试卡片。用户层规则仍然生效时，测试可以直接执行，但仍须等待本对话的真实收件确认。

### 5.3 接收人配置边界

本方案以“同一对话期间固定接收人配置不变”为明确前提。当前 Skill 无法在审批前证明完整 Open ID，也不自动检测配置变化。

用户若在同一对话中修改接收人，应明确要求“重新测试飞书接收人”；Skill 清除当前对话确认并重新走首次流程。无此明确信号时不增加每次发送诊断，以免违背“同一对话只测试一次”。

## 6. 失败行为

| 条件 | 结果 |
| --- | --- |
| 首次飞书意图出现 | 暂停原任务，立即进入测试流程 |
| 当前审批模式不能让用户保存规则 | 要求切换人工审批模式；不先发送测试 |
| 用户只批准本次 | 不记录确认，不开始离席任务 |
| 测试命令成功但用户未确认收件 | 不记录确认，不开始离席任务 |
| 同一对话已经确认 | 后续不再测试或询问确认 |
| 新对话第一次使用 | 重新测试；已有持久规则时不重复申请 |
| 用户明确说明接收人已修改 | 清除对话确认并重新测试 |
| 组织策略禁止精确规则 | 当前环境不支持无人值守通知，不绕过 |
| 电脑休眠、进程退出或断网 | 无法保证送达，不新增后台服务 |

通知链路失败时不能依赖同一链路报告失败。第一时间测试只用于在用户离席前暴露问题，不构成绝对必达保证。

## 7. 修改范围

设计批准并形成获批执行计划后，预计只修改：

- `skills/feishu-notify/SKILL.md`：加入首次触发、固定测试、持久前缀建议、对话确认和后续跳过规则；
- `tests/test_skill.py`：静态验证上述 Skill 合同以及禁止宽泛规则；
- `README.md`、`docs/USAGE.md`、`docs/FEISHU_APP_SETUP.md`、`CHANGELOG.md`：同步使用流程和边界；
- 安装 manifest 与安装测试：仅在现有受管 Skill 内容变化确实要求时更新。

不修改 `config.py`、`cli.py`、`client.py`、配置 schema、飞书 HTTP 请求、卡片结构、重试或安装器行为。

## 8. 直接验收

使用测试应用和固定测试接收人完成：

1. 在新对话第一次输入“完成后飞书通知我”时，Agent 在原任务开始前进入测试流程。
2. 若 Auto-review 不展示持久选项，Agent 先要求切换人工审批；切换后只发送一张测试卡片。
3. 审批建议只覆盖绝对解释器、入口、当前项目根和 `task`；用户选择持久允许并收到测试后，在当前对话确认两件事。
4. Agent 收到确认后才开始原任务，并公开记录本对话已确认。
5. 同一对话第二次要求发送飞书时不出现测试卡片或测试确认。
6. 用户离席后收到一张与真实终态一致的 `success`、`failure` 或 `confirm` 卡片，且终态发送没有新的审批。
7. 新对话第一次要求发送时重新收到一张测试卡片；已有规则时不出现新的规则审批。
8. `send`、`rich`、其他项目根和其他脚本不匹配该规则。

文件存在、静态测试、`git diff --check`、测试命令成功或一次性批准，都不能单独代替真实收件、持久规则复用和“同一对话只测试一次”的结果。

## 9. 假设、不确定项与取舍

- 假设接收人由用户预先配置，并在同一对话期间保持不变；测试收件代表用户认可当前固定目标。
- 假设审批界面允许用户保存 Agent 建议的精确 `prefix_rule`。官方 Rules 文档说明 TUI 可把允许规则写入用户层，但规则能力仍是实验性功能；不可用时方案保持阻塞。
- 当前对话状态只依赖对话历史，不新增本地数据库。分叉或历史丢失时若无法确认状态，按新对话重新测试，可能多一张测试卡片，但不会静默跳过首次确认。
- 取舍是规则绑定当前项目和 `task`，不绑定隐藏在配置中的 Open ID。它满足固定接收人的当前目标；若要求自动识别接收人变化，必须另行批准代码方案。
- 待评审取舍：相较 V0.3 草案，本版删除接收人变化自动检测，改为同一对话期间配置不变；用户主动修改接收人时明确要求重新测试。该差异尚未进入实现，须随本设计由用户批准。

## 10. Karpathy 精简与删除审计

- **基线对照：** 当前 Skill 手工先发 `task` 测试已经能工作；缺口仅是首次触发时序、持久前缀建议和对话内去重。
- **最小方案：** 只修改 Skill 及合同测试。完全不改 Skill 会继续依赖用户每次记住流程，因此不能保证首次时序；修改连接器则超出核心目标。
- **删除审计：** 删除 Open ID SHA-256、`--approval-recipient`、绑定准备模式、规则只读检查、配置变化自动检测，以及对应 `config.py`、`cli.py` 和单元测试改动；继续拒绝标签、完整 Auto-review policy、MCP、插件、Hook、守护进程和本地状态文件。
- **直接验收：** 首次请求必须在原任务前真实收件并确认；同一对话第二次必须没有测试；离席终态必须无新审批真实送达。
- **行为差异：** 同一对话第一次飞书请求会增加一次前置测试和用户确认；确认后该对话不再增加步骤。相较 V0.3 草案，接收人配置变化不再自动检测，这是保持 Skill-only 方案的待评审取舍。
