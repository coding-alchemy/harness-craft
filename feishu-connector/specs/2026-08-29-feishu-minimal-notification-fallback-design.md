## 1. 修订原因

V1.0 把“减少审批隐私风险”错误地提升为默认目标：无正文通知只发送固定状态句，不再包含任务和执行结果。三条固定正文中的失败与待确认消息只要求用户回到 Codex，无法回答“什么任务、发生了什么、需要做什么”。这不满足用户要求飞书通知的主要用途。

用户确认的真实目标是：绝大多数通知直接给出有信息量的执行结果；只有密钥、密码、Token、凭据和个人信息等真正敏感内容才脱敏。隐私保护是对结果正文的局部约束，不是把结果正文整体删除。

因此本版撤销固定空提醒方案，恢复“结果优先”，并把隐私拒绝后的降级定义为“保留任务和结果语义的脱敏重写”。

## 2. 核心目标与直接结果

用户明确要求飞书通知但没有指定正文时，Agent 根据本次任务的真实结果生成简短、自包含的通知。用户无需打开 Codex，就能从飞书判断任务、状态和关键结果。

通知按状态至少回答：

| 状态 | 必须包含的信息 |
| --- | --- |
| `success` | 任务标识、已完成的核心结果，以及相关时的验证证据或产物位置 |
| `failure` | 任务标识、未完成的具体原因，以及存在时的安全下一步 |
| `confirm` | 任务标识、需要用户决定的事项，以及选项或影响 |

“请回到 Codex 查看结果/原因/处理”不能单独构成通知正文；需要查看完整细节时，它只能放在上述有效信息之后作为补充。

## 3. 外发授权与正文合同

### 3.1 未指定正文

用户说“飞书通知我”“完成后发飞书”或同等表达，即授权向连接器已配置的固定接收人发送一次本任务通知，无需再次确认正文。Agent 使用本次任务上下文生成第 2 节要求的结果通知。

普通研发信息默认可以发送，包括项目或模块名、任务名称、分支、提交号、测试数量、仓库相对路径、公开错误类别和不含秘密值的失败原因。Agent 不因这些字段是动态内容而主动删除它们。

原始日志、完整 Diff 和内部推理不默认附加；这项限制用于保持通知简短、可读，并不把其中所有内容认定为隐私。用户明确要求某项非敏感细节时可以发送。

### 3.2 用户指定正文

用户指定正文时保留其原意和具体信息，不自行改写为状态模板。正文包含第 4 节定义的敏感值时，只替换敏感值，保留其余文字和结果语义；用户的发送授权不构成明文外发秘密值的授权。

### 3.3 授权边界

本次授权只覆盖已配置固定接收人的本次通知，不允许更换、推断或扩大接收人，也不自动延续到后续消息。真实发送继续接受执行器的平台审批；Skill 不能绕过审批，也不能保证网络、配置或飞书服务始终可用。

## 4. 隐私脱敏

### 4.1 必须脱敏的内容

以下内容不得以明文进入飞书 payload：

- 密码、API key、访问 Token、Cookie、私钥、验证码及其他认证秘密；
- App Secret、连接串中的凭据、配置文件或环境变量中的秘密值；
- 身份证件号、电话号码、私人邮箱、家庭地址等可识别个人的信息；
- 用户明确标记为保密、不可外发或仅限当前环境的具体内容。

替换文本使用能说明遗漏类别的短标记，例如 `[已脱敏：Token]`、`[已脱敏：个人信息]`。脱敏保留任务名、状态、非敏感原因和结果；不能把整条消息替换为无信息的固定提醒。

### 4.2 首次发送前

Agent 在准备真实命令前检查拟发送正文，只对 4.1 的具体值脱敏。项目名、提交号、测试结果等普通任务信息不进入脱敏分支。没有证据表明某个字段属于 4.1 时，按普通任务信息保留，不因它是动态内容、来自工作区或可能接受平台审查而脱敏。

### 4.3 平台隐私拒绝后的单次重写

首次正文只有同时满足下列条件才允许重新发送：

1. 工具明确表示发送进程尚未创建，不存在重复投递风险；
2. 拒绝原因指向正文中的隐私、秘密或目的地信任；
3. 工具明确允许提交更安全的替代内容；
4. 本通知尚未执行过隐私脱敏重写。

满足时，Agent 根据拒绝原因只删除或替换敏感值，继续保留任务标识、状态和可安全表达的执行结果，再重新运行离线 `prepare-shell` 并申请一次新的平台审批。

如果结果本身依赖敏感数据，正文仍需说明非敏感结论，例如“凭据轮换未完成：目标服务拒绝认证；具体凭据已脱敏”，而不是“任务未完成，请回到 Codex 查看原因”。

第二次审批仍被拒、执行器不支持升级、配置错误、远程错误或投递状态不明时立即停止并如实报告未发送；不得继续重写、跨进程重试或更换渠道。

## 5. 既有能力与限制

以下基线保持不变：

- `send` 发送纯文本，`rich` 发送通用 Markdown 卡片，`task` 发送带项目、对话和状态标题的任务卡片；
- 仓库规则驱动的自动通知继续使用 `task --auto`；
- Codex 真实发送继续先用 `prepare-shell` 生成审批可见命令；
- 接收人、配置优先级、消息卡片、网络重试、UUID、退出码和错误脱敏保持不变；
- 退出码 `5` 或其他可能已经创建发送请求的失败不得跨进程重试；
- 通知失败不得改变 Agent 原任务结果。

当前分支新增的 `notify` stdin flow 和 `NOTIFY_MESSAGE` 固定正文不属于上述基线：它们尚未进入主分支，并且直接造成第 1 节的问题，应从最终实现和公开合同中删除。

## 6. 最小方案

### 6.1 复用现有 `task`

无正文的任务结果通知使用现有显式 `task`：项目和对话字段标识任务上下文，`status` 表达完成、失败或待确认，`content` 承载第 2 节要求的结果。存在标题、列表或链接但不适合任务状态卡片的用户指定正文，继续按现有规则使用 `rich`；简单指定原文继续使用 `send`。

不新增结果 schema、模板配置、摘要级别、公开子命令、网络接口或客户端实现。正文由已经掌握任务上下文的大模型生成，连接器只负责安全传参与发送。

### 6.2 删除固定 `notify` flow

删除 `_stdin_argv` 中的 `notify` 白名单和 `NOTIFY_MESSAGE`，stdin/`prepare-shell` 恢复 `send`、`rich`、`task`、`task-auto` 四种 flow。删除只验证固定空提醒的测试和公开文档描述。

### 6.3 Skill 单一决策点

源 `SKILL.md` 在“外发授权”中集中定义一次通知正文决策：先生成有信息量结果并完成首次脱敏；只有 4.3 的平台拒绝触发一次脱敏重写。执行权限章节只引用这个例外，不再另写一条可能覆盖它的无条件停止规则。

这同时修复此前评审发现的“权限拒绝规则可能跳过降级”问题。

## 7. 拒绝的替代方案

### 7.1 给固定 `notify` 增加任务和结果字段

这会重新实现现有 `task` 已提供的 `status`、项目、对话和正文能力，增加第二套任务通知接口。复用 `task` 已能满足核心目标，因此不扩展 `notify`。

### 7.2 只把三条固定正文写得更长

静态正文不知道任务和真实执行结果，无法让用户通过消息判断发生了什么。即使加入更多通用句子，仍然没有本次任务信息，因此不采用。

### 7.3 编写通用秘密检测或任意文本脱敏器

秘密和个人信息依赖上下文，正则脚本既可能漏掉敏感值，也可能把普通项目信息误删。现有大模型已经掌握任务上下文，先用明确的敏感类别约束其生成；只有未来出现可复现的遗漏证据时，才考虑增加确定性检测器。

### 7.4 绕过平台审批或新增送达守护进程

Skill 无权改变平台 auto-review，队列或守护进程也不能保证外部系统必达，却会增加安装、状态和重复投递问题。本次不改变平台或网络边界。

## 8. 修改范围

设计批准后的实现只修改：

- `skills/feishu-notify/SKILL.md`：结果优先、敏感类别、首次脱敏和单次重写；
- `skills/feishu-notify/scripts/feishu_connector/cli.py`：删除未发布的固定 `notify` flow；
- `tests/test_cli.py`、`tests/test_skill.py`：删除错误合同，验证四种既有 flow 与新的 Skill 决策；
- `README.md`、`docs/USAGE.md`、`specs/feishu-connector.md`：同步现行合同；
- `CHANGELOG.md`：把尚未发布的 V1.4 记录修正为最终用户行为；
- 已安装 Skill：测试通过后只通过现有 `install_skill.py --force` 更新。

不修改 `client.py`、`config.py`、安装 manifest、卡片渲染、HTTP 请求或重试实现。

## 9. 验收标准

### 9.1 离线接口

1. stdin/`prepare-shell` 继续接受 `send`、`rich`、`task`、`task-auto`，拒绝 `notify` 和其他未知 flow；现有配置、卡片和重试测试全部通过。
2. `prepare-shell` 的任务命令完整展示项目、对话、状态和结果正文，不读取配置、不构造客户端、不联网。
3. 源 Skill 与公开合同只有一个隐私拒绝分支：满足 4.3 时重写一次，网络错误或投递状态不明时不跨进程重试。

### 9.2 Skill 行为试跑

使用安装后的 Skill 在新对话分别试跑三类结果：

1. 普通成功任务的首次 payload 包含任务、核心结果和相关验证，不含“请回到 Codex”式空正文；
2. 普通失败任务的首次 payload 包含具体、非敏感的失败原因和可用下一步；
3. 含模拟 Token 与个人信息的结果只隐藏具体敏感值，仍保留任务和结果；模拟审批前隐私拒绝时最多生成一次仍有信息量的脱敏替代正文。

试跑使用模拟秘密，不把真实凭据写入测试、工作区或会话记录。

### 9.3 安装与真实用户结果

1. `install_skill.py --force` 成功后，六个受管文件与源码内容及权限一致；安装副本可独立准备任务通知。
2. 在用户明确要求通知的真实任务结束后，向测试用户发送一条有信息量的任务通知；stdout 出现 `Feishu message sent` 才报告 `sent`。
3. 用户在飞书直接看到任务标识、状态和执行结果；消息不含真实秘密值。平台、网络、配置或飞书拒绝时准确报告失败，不宣称必达。

上述新对话行为与真实飞书收件是核心验收；测试通过、文件一致、`git diff --check` 或提交存在不能代替它们。直接验收未完成前，执行计划不得删除。

## 10. 假设、取舍与行为差异

- 假设“绝大多数情况发送执行结果”表示 Agent 根据任务规模选择简短段落或少量列表，不引入固定字数、字段数量或可配置模板。
- 假设项目名、模块名、提交号、测试数和仓库相对路径属于普通任务信息；命中第 4 节具体敏感类别时才隐藏相应值。
- 取舍是由大模型做语义脱敏，而不是新增不可靠的通用检测脚本；平台审批仍提供独立外发检查。
- 相对 V1.0 的行为差异是删除固定 `notify` flow，恢复并强化现有 `task` 结果通知；该差异已随 V1.1 设计获得用户批准。
- 除本节列出的差异外，不改变既有接收人、发送接口、卡片、配置、网络和重试行为。

## 11. Karpathy 精简与删除审计

- 核心方案只复用现有 `task` 并删除错误的 `notify` 分支，没有新增实现接口。
- 每项正文规则都直接映射到“消息里看懂任务与结果”或“只隐藏真实敏感值”；删除了固定三句、通用摘要配置和无关扩展点。
- 隐私降级只覆盖已经发生过的审批前隐私拒绝，次数保持一次；不扩大到网络和未知投递错误。
- 直接验收要求用户在飞书看到任务与结果，不用单元测试或文件存在替代产品结果。
