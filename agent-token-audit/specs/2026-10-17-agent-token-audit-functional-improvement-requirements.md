## 3. 费用与性能分析

本节归并原三期需求正文，保留已交付行为及 P3 验收。后续默认价格需求由[默认价格与查询体验设计](./2026-10-11-agent-token-audit-pricing-query-design.md)补充：自定义历史规则仍按记录时间匹配生效区间；随包默认规则明确按所选官网当前 API 价格快照估值，并记录读取时间，不冒充历史账单价格。第 3.6 节的“实施前”基线是历史设计依据，不代表当前仍缺少费用或性能功能。

### 3.1 核心目标与阶段依赖

在整体分析和消耗解释之上，用户可根据明确价格规则查看已记录用量的估算费用，并按各指标所需的真实证据查看 TTFT、生成吞吐和工具耗时。估算金额、实际用量和性能样本各自说明依据与覆盖，不能把估算变成账单结论。

沿用 Harness 对话中的 Skill、本地网页和供其他工具调用的 Python CLI 三种入口；相同来源记录、范围与规则下的费用、性能数值及状态一致。保留现有会话/轮次选择、整体查询、固定截止点、报告复用与离线展示合同；前序未闭合验收仍按实现文档第 10 节单列，不能因三期验收追认通过。

费用估算使用已记录 token 和明确计价配置，不放宽既有“缺失用量不估算”要求。性能依真实来源能力提供，来源未记录时明确不可用及原因，不通过默认零或全未知图表宣称完成支持。

### 3.2 费用估算

#### 3.2.1 用户行为与价格依据

用户能够查看和选择价格配置，在原统计范围内按模型、会话或日期查看估算费用及未定价部分。每份估算显示币种、计价单位、实际采用的单价及规则来源/版本、生效区间、模型及供应商身份、计算范围与覆盖。

价格绑定来源证实的供应商、完整模型身份及适用时间。别名或映射须有明确配置与依据，不能去掉供应商后把同名模型当成同价。历史记录按照记录所属时间匹配生效规则，不用当前本地时钟价格覆盖全部历史；缺身份、缺价格、时间冲突或规则重叠分别报告。

输入、输出、缓存读取/写入、推理等计价依据来源字段包含关系和价格规则确定，不套用会导致重复计费的统一相加公式；已包含项不能再计一次。套餐额度、折扣、汇率或额外费用无配置或账单证据时不能自行假定。

#### 3.2.2 已定价小计与覆盖

只对计价所需 usage、身份和规则均有依据的部分计价。缺少其中任一项，不填零、不把已定价小计命名为完整总费用。分别显示已定价金额、未定价记录/指标和原因；覆盖分母有依据才给比例，不能以金额覆盖替代用量覆盖。

不同币种分别表达；未确定汇率依据时不合并。模型、日期和会话视图均投影同一计价结果，不再加入总金额。确认价格为零与价格未知可辨；费用保留可复算精度和明确显示精度。

#### 3.2.3 保存、重算与价格变更

保存报告保留所用价格规则及计价依据，不能只记录可能被覆盖的配置路径或规则名称。加载只展示保存结果，不因打开时间或本地配置更新而换价，也不读取原始来源。

原范围重算默认沿用保存的价格规则、来源、范围和固定截止点；只有用户明确选择新规则并发起重新计算，才改用新规则。新结果标明实际规则及其变化，与旧估算可辨，原文件不改写；价格变更不自动扩展统计范围。固定范围仍可能因来源后补记录而改变，缺少对应规则的新增记录按未定价处理，不默用当前配置。

### 3.3 性能分析

| 指标 | 依据与限制 |
| --- | --- |
| TTFT（首 token 延迟） | 同一次请求/调用的实际首 token 时间减去可信请求起点；注明时间事件定义与单位，不用响应结束时间或调用耗时代替首 token；不以具备输出 token 数为前提 |
| 生成吞吐 | 同一次调用的已知输出 token 除以首 token 至可信结束事件的有效时长；输出计数口径与时间区间须匹配。用户已接受 ZCode 的 `first_token_at→completed_at` 来源观测区间，必须标明终点含完成事件处理开销，不称服务端纯生成速率。缺首 token、可信区间终点或输出量的记录不进入吞吐计算；聚合用该指标同一有效样本集合的总输出除以总区间时长，单位为 token/秒，不平均逐调用速率 |
| 工具耗时 | 仅展示有明确工具执行身份和起止或直接耗时证据的样本，不要求有模型 usage；不把模型调用耗时当工具耗时，不将并行工具时长之和当墙钟跨度 |

各指标独立判断有效样本，不要求三类指标共用字段齐全的交集。例如已完成调用有请求起点和首 token、缺输出量时，可计 TTFT，不能计生成吞吐。每项分别显示有效样本数、排除原因及覆盖；覆盖分母无依据时不给比例，不把一项指标的覆盖当作其他指标的覆盖。

零或负时长、时间顺序冲突、未完成记录和缺字段各自说明，不产生无穷吞吐或伪造零延迟。生成吞吐的分母必须大于零。性能样本和 token 统计范围可能不同，不能把已计入 token 的所有记录默认当作性能样本。

指标使用固定结果范围及截止点，图表筛选仅改变视图。不同来源有不同时间事件或计量口径时明示，不能据此输出未经控制的 Harness 效率优劣结论。

### 3.4 直接验收

| 编号 | 直接验收标准 |
| --- | --- |
| P3-A1 | 用明确测试规则独立复算：输入 1,000,000（含缓存读取 400,000）、输出 100,000、确认缓存写入零；每百万非缓存输入/缓存读取/输出分别为 10/2/20 测试币种单位，费用为 `(1,000,000−400,000)÷1,000,000×10 + 400,000÷1,000,000×2 + 100,000÷1,000,000×20 = 8.8`；推理已含输出时不再计价。测试价格不是实际模型价格 |
| P3-A2 | 同名模型不同供应商、规则跨生效日期、缓存写入语义差异、缺价/缺身份/缺 usage、确认零价格、重叠规则及不同币种样例均正确处理；已定价小计和未定价原因可见，不产生伪完整金额 |
| P3-A3 | Codex、ZCode 各自用真实记录核对供应商/完整模型身份、计价字段和三项性能指标所需证据，记录来源版本与入口；已计价部分和有效性能样本从原始记录独立复算。源未提供的项有核查依据与可见原因，尚未核查或无法读取不得写成源不支持；构造样例不能冒充真实字段覆盖 |
| P3-A4 | 用含可信请求起点、首 token、可信生成结束或已接受的来源观测区间终点及输出量的已完成调用独立复算，数值预期见下方样例；再混入缺字段、零/负时长、时间冲突和未完成记录，逐指标核对有效集合、排除原因及覆盖。保留“可算 TTFT 但不可算吞吐”和“无模型 usage 但可算工具耗时”的样例；串行/并行工具独立核对耗时与墙钟区别 |
| P3-A5 | 在真实浏览器查看模型/会话/日期费用、单价和规则依据、未定价部分、有有效样本的性能图与明细；无有效样本显示原因。视图过滤前后报告合计、范围和截止点不变；编辑价格配置不改已有结果，明确计算后新旧结果及所用规则可辨 |
| P3-A6 | 实际导出 JSON/CSV/Markdown 并核对费用、性能、规则依据和状态，重新加载 JSON 后一致；隔离来源和本地价格配置后，保存结果仍可离线展示。修改本地配置后原范围重算仍沿用保存规则，明确选新规则后才换价；原文件不改写，来源缺失不回填旧值。合法旧报告无费用/性能字段时仍能展示已有值并说明未保存这些能力，不补零或自动回源；明确更新及两端此前已验收行为无回归 |
| P3-A7 | 两端分别从真实 Harness 对话调用 Skill、在网页明确查询，并与 Python CLI 在相同来源记录、范围及规则下的结果核对；完整安装副本实际运行相应路径。来源只读，不改 Harness 或发送埋点请求；普通查询不启动持续采集或自动保存报告，导出不含正文/认证信息 |

P3-A4 数值样例：两条已完成调用的“请求起点、首 token、区间终点”相对秒数分别为 `(0, 1, 2)` 和 `(0, 2, 11)`，输出各 100 token，则 TTFT 分别为 1 秒、2 秒，聚合吞吐为 `200 ÷ (1 + 9) = 20 token/秒`。两次工具执行各 10 秒：串行为墙钟 20 秒、耗时和 20 秒；区间为 `[0,10]` 与 `[5,15]` 时墙钟 15 秒、耗时和仍为 20 秒。样例只验证计算，不证明真实来源支持。

三类性能指标的逐端支持状态须在设计中由真实来源核查确定；无法取得来源证据时保留未决项，不默认为全部支持，也不自动扩大为采集或埋点工程。

### 3.5 非目标与设计待定

本期不做账单对账、套餐扣减、自动汇率换算、成本节约或质量保证，不实施持续采集、增量缓存、自动刷新、永久历史库、实时上下文成分拆解或新的 Harness 接入。

价格配置与保存规则、匹配与冲突处理、模型别名依据、历史生效时间、费用精度及报告兼容由已批准的[实现文档第 11 节](./2026-10-07-agent-token-audit-implementation.md#11-费用与独立性能的实现决定)承接；其来源核查明确了逐端时间事件、输出计数口径、配对身份、可用字段及未完成记录的逐指标处理。设计依据不替代实现验收；不新增价格服务、配置平台或统一性能埋点，缺字段不得改来源补造。

### 3.6 Karpathy 精简与自检

需求制定时的基线（实施前）：已核对[实现合同](./2026-10-07-agent-token-audit-implementation.md)、[前端合同](./2026-10-07-agent-token-audit-implementation.md#91-前端组织视觉与可达性)及 `codex.py`、`zcode.py`、`core.py`、`operations.py`、`formats.py` 的相关路径。现有能力包括精确 usage、归属、固定截止点、模型调用/逻辑请求耗时及报告展示/重算；没有费用、TTFT、生成吞吐或独立工具耗时接口。ZCode 读取 provider 后用于 usage 语义判断，当前记录与模型分组未保留独立供应商身份；Codex usage 时刻不能当首 token。不能直接用现有模型标签定价或用现有耗时字段替代新指标，真实来源支持仍须按 P3-A3 核查。

假设与差异：价格规则和新性能字段需要明确依据；费用估算不等于估算缺失 token。用户已确认逐指标独立样本、重算默认沿用保存价格规则，以及 ZCode 来源观测区间吞吐的明确口径，正文与验收同步适用。真实来源支持边界见本轮设计核查，不能从适配器未读取推断源无字段；本轮未新增来源、采集或对账能力。原三期需求 V0.4 与设计 V0.1 已获整体批准，计划审批及实施授权独立记录。

### 4.2 长期保留的需求判断

#### 4.2.1 每项盘点的交付内容

用户明确启动某次需求判断后，记录本次选定主题；其余主题仍作为未决需求保留。修改本文或其他阶段完成不自动启动本次判断。

对第 4.2.2、4.2.3 节每个主题说明：用户要回答的问题、场景、来源、统计粒度、身份与去重、历史缺失表达、隐私与文件副作用、最小可行方案、依赖与成本、直接成功标准，以及建议实施或暂缓的理由。

#### 4.2.2 跨会话汇总与历史趋势

#### 4.2.3 费用、持续采集和长期保存

| 主题 | 需要厘清的问题 |
| --- | --- |
| 费用 | 需求是价格估算、套餐消耗还是账单对账；模型/供应商/日期/币种、缓存和推理计费、折扣如何处理；未知价格如何显示 |
| 持续采集 | 需求是实时更新、避免轮转丢失还是定时报告；运行环境、启动停止、增量读取、重试、去重、资源消耗和权限 |
| 长期保存 | 保存报告、归一化数据还是原始来源；保留期限、删除导出、备份迁移、兼容升级及回源能力 |

分别评估三项：费用展示不自动等同账单对账；长期保存不自动绑定持续采集；采集不能恢复过去未记录的用量。沿用报告不含正文和认证信息的边界，任何变化单独决策。

#### 4.2.4 研究提出的条件候选

自动刷新、增量缓存与实时上下文成分展示继续作为独立候选，不自动归入三期：刷新须先确认用户时效目标与触发/停止；缓存须先确认真实扫描成本、失效与完整性；上下文成分须先确认用途及实际/估计口径。各项均沿用第 4.2.1 节逐项判断要求，来源证据、直接成功标准和实施授权不足时不建设对应机制。

现行本地网页服务已有有界进程内解析缓存，每次请求仍重新核验来源并读取当前有限快照；这不等同逐行增量读取或持续采集，不能将本节增量缓存候选整体标为已完成。已交付缓存边界见[默认价格与查询体验设计第 4.5 节](./2026-10-11-agent-token-audit-pricing-query-design.md#45-性能收敛与缓存边界)。
