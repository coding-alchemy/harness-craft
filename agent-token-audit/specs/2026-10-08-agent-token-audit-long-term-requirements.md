## 1. 核心目标与迭代边界

保留跨会话汇总、跨会话任务、历史趋势与历史来源、费用、持续采集和长期保存七个主题的需求判断。已选部分映射到明确阶段，未选部分供用户后续决定是否实施及何时实施；阶段范围确认、详细判断和产品验收分别记录。

本文件承接 2026-10-01 分期调整前原四期第 4 节及当时 P4-A5、P4-A6 的需求盘点（历史编号，不指现四期验收）。当时用户确认长期保留，不绑定二至五期完成或日期；2026-10-05 进一步选定下表部分范围。七个主题和逐项判断要求完整保留，已选范围不把其他可选项打包实施，也不把尚待设计或验收的能力标为已完成。

| 主题 | 2026-10-05 分期决定的现行映射及未决边界 |
| --- | --- |
| 跨会话汇总 | 二期整体分析纳入明确范围的整体汇总、模型/会话分布；项目身份等具体查询行为待设计，不自动关联业务任务 |
| 跨会话任务 | 仍独立判断；二期普通汇总不等于跨会话任务识别 |
| 历史趋势 | 二期整体分析纳入按日趋势和日期下钻；更多粒度、来源迟到及历史覆盖处理须在设计中确认，不绑定持续采集 |
| 历史来源 | 二期整体分析先读取现存历史及按需结果；新增历史存储、归档或轮转前保留仍独立判断，不能宣称恢复缺失记录 |
| 费用 | 三期纳入有依据价格估算、价格配置及覆盖；套餐消耗、账单对账、折扣与汇率扩展不随之自动纳入 |
| 持续采集 | 仍独立判断；实时刷新、采集和定时报告不作为二期整体分析、消耗解释及三期费用与性能的默认交付 |
| 长期保存 | 仍独立判断；按需报告与永久历史库分别决定 |

表中纳入阶段只确认范围，细节仍须完成相应判断与设计；本轮不宣称 LT-A2 已完成或任何新增产品行为已验收。

## 2. 长期保留的需求判断

### 2.1 每项盘点的交付内容

用户明确启动某次需求判断后，记录本次选定主题；其余主题仍作为未决需求保留。修改本文或其他阶段完成不自动启动本次判断。

对第 2.2、2.3 节每个主题说明：用户要回答的问题、场景、来源、统计粒度、身份与去重、历史缺失表达、隐私与文件副作用、最小可行方案、依赖与成本、直接成功标准，以及建议实施或暂缓的理由。

盘点可以建议暂缓，但不能只写“未来再做”。有行为差异的多种解释列明影响并交由用户决定。需求盘点本身不等于功能实施，也不授权扩大到其他可选项。

### 2.2 跨会话汇总与历史趋势

| 主题 | 需要厘清的问题 |
| --- | --- |
| 跨会话汇总 | 用户明确多选会话，还是按日期/项目/Harness 查询；项目身份如何确认；恢复、分叉、后代及重叠选集如何去重 |
| 跨会话任务 | 是否需要将多个会话识别为同一业务任务；关联由谁指定、证据何在；如何避免与普通会话汇总混淆 |
| 历史趋势 | 日/周等时间粒度、时区、迟到记录、历史缺口、来源版本变化及零值语义 |
| 历史来源 | 读取仍存在的日志、保存按需报告或新增持久存储；各方案历史范围和证据限制 |

跨会话汇总不自动需要跨会话任务识别；历史趋势不自动要求持续采集或数据库。先评估读取现存历史的最小方案，只有无法满足已确认目标时才提出新增机制。

### 2.3 费用、持续采集和长期保存

| 主题 | 需要厘清的问题 |
| --- | --- |
| 费用 | 需求是价格估算、套餐消耗还是账单对账；模型/供应商/日期/币种、缓存和推理计费、折扣如何处理；未知价格如何显示 |
| 持续采集 | 需求是实时更新、避免轮转丢失还是定时报告；运行环境、启动停止、增量读取、重试、去重、资源消耗和权限 |
| 长期保存 | 保存报告、归一化数据还是原始来源；保留期限、删除导出、备份迁移、兼容升级及回源能力 |

分别评估三项：费用展示不自动等同账单对账；长期保存不自动绑定持续采集；采集不能恢复过去未记录的用量。沿用报告不含正文和认证信息的边界，任何变化单独决策。

### 2.4 研究提出的条件候选

自动刷新、增量缓存与实时上下文成分展示继续作为独立候选，不自动归入三期：刷新须先确认用户时效目标与触发/停止；缓存须先确认真实扫描成本、失效与完整性；上下文成分须先确认用途及实际/估计口径。各项均沿用第 2.1 节逐项判断要求，来源证据、直接成功标准和实施授权不足时不建设对应机制。

## 3. 迭代判断的直接验收

| 编号 | 直接验收标准 |
| --- | --- |
| LT-A1 | 本文保留第 2 节所有主题及逐项判断要求；每次具体迭代明确涉及主题，不将未判断项标为已完成，也不把剩余项丢弃 |
| LT-A2 | 对本次迭代选择判断的每个主题，有用户问题、场景、来源、粒度、身份/去重、历史缺口、隐私/副作用、最小方案、依赖/成本、直接成功标准及实施或暂缓理由 |
| LT-A3 | 多种解释导致不同行为时列明影响供用户决定；跨会话汇总与任务关联、趋势与采集、费用与对账、保存与采集分别判断，不互相默认绑定 |
| LT-A4 | 判断结论与功能实施授权分开；未选能力不暗中实施，不改变现有范围或报告边界；暂缓项保留理由、依赖及后续重新判断所需证据 |

这些标准验证每次被明确启动的需求判断，不要求现行各期一次性完成所有长期判断，也不将长期需求池声明为整体已完成。

## 4. 与现行阶段的关系及非目标

判断时以现行已批准需求及已验收实现为基线，明确现行各期尚未批准、实现或验收的部分，不把未来能力当成已有事实，也不将五期完成设为需求判断的统一前置条件。长期判断不能追认先前未授权的功能。若用户选择实施某项，另行确认需求、设计、执行计划及实施授权；不因更新本文或阶段完成而新增产品版本或发布。

方案未获实施授权时，不修改实现或引入数据库、常驻服务。

## 5. Karpathy 精简与自检

基线：2026-10-01 调整前原四期第 4 节及当时 P4-A5/P4-A6 的全部主题与判断要求；一期已批准的单会话任务、按需读取、未知不估算及报告隐私边界。现有 CLI 仅接入 Codex、ZCode，保存结果展示不读取日志，重算读取当前来源，不能将后续能力当成已实现事实。

假设与差异：2026-10-05 已选跨会话汇总、日期趋势与价格估算的现行映射分别为二期整体分析、三期费用与性能；其他范围未决，来源、价格和历史可用性仍须核验。分期调整已获确认，需求细节不当作批准的实现；无新增产品行为变化。

最小方案：采用一份共用判断清单加逐主题问题表；分别为七个主题重复完整交付清单也能满足要求，但重复维护更多，因此共用清单，保留各主题独立问题和决定。本次复用判断合同并记录已选阶段映射，不预建采集或存储机制。

删除审计：用一张状态表收敛已选阶段与未决主题，替换“全部仍未决定”的旧表述；原七个主题、每项交付、最小方案及独立决定均保留。条件候选单列，不把价格、趋势、刷新、缓存、上下文或采集打包实施。

直接验收：LT-A1 保证全部主题及未决项保留，LT-A2 验证选定主题的逐项判断，LT-A3 验证歧义与独立决定，LT-A4 验证暂缓理由和实施授权边界；不以文档存在代替实际判断，也不宣称长期需求池整体完成。
