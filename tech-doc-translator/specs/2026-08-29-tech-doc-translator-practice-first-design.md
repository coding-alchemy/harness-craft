## 1. 目的与核心结果

`tech-doc-translator` 面向计算机、工程、数学、物理等理工科英文技术文档，提供一个由 Agent 使用的翻译 Skill。用户给出权威源和交付范围后，Skill 应协调现有工具、确定性脚本和大模型，产出可逐项回源核对的中文 Markdown 译文。

核心结果不是“跑完一套流程”，而是用户实际得到满足以下条件的译文：

1. 技术含义准确，没有漏译、擅自补写或静默修正原文。
2. 标题、段落、列表、表格、公式、代码围栏、图片、脚注和提示框等结构完整。
3. 代码、标识符、命令行选项和其他要求逐字保留的内容没有被解析、翻译或合并过程破坏。
4. 项目内及声明的基准项目之间术语一致；同词多义时能按语境保留不同译法。
5. 中断后能从已有源文件、译文和校验事实继续，只重做缺失或已证明失效的部分。
6. 可获得时如实报告使用的模型、token 和墙钟时间；不可获得时明确标注未知，不估算成事实。

## 2. 权威来源与约束顺序

### 2.1 设计基线

本规格从 `HPC_Trans` 的已完成项目提炼当前行为，而不是从旧平台抽象反推需求。影响设计的实践事实如下：

| 实践事实 | 本规格中的决定 |
| --- | --- |
| 多个大型文档由主 Agent 集中预处理、分派、复验和合并完成 | Skill 编排工作；不建立独立工作流引擎 |
| 项目 `术语表.md` 已能支持项目内与跨项目统一 | 继续以 Markdown 术语表为权威；不建术语数据库或快照系统 |
| HTML 解析器随 NVIDIA 分页文档、BPG、cuBLAS、PTX、cuTile 等源结构分别演进 | 保留源家族脚本；不强制统一解析器或注册中心 |
| 自动校验多次抓出漏图、漏公式、围栏损伤和合并损伤，但不能证明语义正确 | 脚本负责确定性校验，主 Agent 另做回源语义复核 |
| 固定并发数在账户负载变化后失效 | 并发按用户约束、宿主能力、当前负载和在途任务动态决定 |
| 已有译文和文件可以支持补派、复验和续做 | 从文件事实恢复；不建立逐段状态机 |

`HPC_Trans` 是设计证据和脚本来源，不是运行时必须存在的外部依赖。实现时应把采用的规则和脚本放入本模块，Skill 不得要求其他用户拥有该绝对路径。

### 2.2 单次翻译任务的优先级

发生冲突时，按以下顺序执行：

1. 用户对当前任务的明确要求；
2. 当前翻译项目中的 Agent 指令、交付约定和 `术语表.md`；
3. 当前项目声明的基准项目术语及已经批准的同项目译文；
4. 本 Skill 的默认规则；
5. 建议性参考和一般翻译习惯。

[英文技术文档结构化翻译完整方案](../docs/英文技术文档结构化翻译完整方案.md)继续保留，但不构成严格设计合同。该文档已按本规格重构：当前能力以既有 Skill 和脚本为准，PDF/OCR、动态页面、版本增量维护与出版 PDF 等仅在真实需求触发后进入后续设计。

### 2.3 当前假设与不确定项

1. 当前唯一对外入口是 Agent Skill；没有需要兼容的公共 CLI、Python API 或状态文件调用者。
2. 首批内置脚本聚焦 `HPC_Trans` 已反复验证的 HTML/Markdown 源家族。PDF 可由 Skill 按任务调用宿主已有工具，但当前不为 PDF/OCR 自建通用处理层。
3. 脚本的具体参数和文件名可以在执行计划中从实践代码原样收敛；本规格只固定能力、输入输出责任和失败条件，不提前设计统一协议。
4. `HPC_Trans` 中的脚本是候选实现来源，不因“已经存在”而全部照搬；只有本规格第 7 节要求且通过回归验证的部分进入模块。

上述假设及对应行为已随本文于 2026-08-29 获得用户批准；后续若改变这些边界，必须重新评审。

## 3. 最小模块边界

### 3.1 唯一外部 seam

模块只向 Agent 暴露一个 `tech-doc-translator` Skill。Skill 说明：

- 何时适用、何时停止并向用户确认；
- 如何读取项目规则、术语和既有译文；
- 如何识别源家族并选择脚本或外部工具；
- 如何组织翻译、分派、复验、合并、恢复和度量；
- 每类参与者的写权限与完成标准。

脚本是 Skill 的内部执行工具，可以被 Agent 直接调用，但不承诺稳定的仓库外 CLI 或 Python API。模块不包含模型 SDK、队列、数据库、Web UI、常驻服务或自有调度器。

### 3.2 内部材料

实现至少包含三类材料：

1. `SKILL.md`：短而完整的入口、决策顺序、工作流和停止条件。
2. 参考规则：从实践中提炼的翻译约定、术语制度、源家族选择和校验清单；只在需要时由 Skill 读取，避免把全部经验堆进主 Prompt。
3. 功能脚本：解析、资源核对、结构校验、代码围栏拼接和安全合并等确定性操作。

目录和脚本名称由实现计划确定，但所有材料应随 Skill 一起交付，不依赖旧平台模块或 `HPC_Trans` 的绝对路径。

### 3.3 明确不做

当前不实现：

- 统一文档 IR、解析器注册中心或插件框架；
- 术语候选审批数据库、不可变快照或自动抓取平台；
- 逐段任务状态机、恢复数据库或双模式审计平台；
- 固定 Agent 数、固定 token 分块或固定工作包大小；
- 公共 CLI/Python SDK、模型客户端、任务队列、Web UI；
- 默认 OCR、版面重建或出版级 PDF；
- 为假设中的未来文档预建抽象、配置项和扩展点。

## 4. 参与者职责

### 4.1 Skill

Skill 提供行为指令和工具选择规则，不复制大模型能力，也不把自然语言判断伪装成程序状态。它负责确保主 Agent 按第 5 节执行，并在条件不满足时停止。

### 4.2 主 Agent

主 Agent 持有全局视角和最终写入责任：

- 确认权威源、版本、范围、官方目录和交付格式；
- 读取项目规则、项目术语、基准术语和同构样文；
- 选择或适配源家族脚本，集中提取源文和处理资源；
- 建立标题、图片、脚注和跨章节引用等全局映射；
- 按结构与体量划分工作包并动态控制并发；
- 对每份译文独立运行校验并回源复核，不采信“Agent 已自检”作为完成证据；
- 集中裁决并写入术语，合并最终译文，执行全量终验；
- 记录来源、模型、token、墙钟时间以及任何未知项。

### 4.3 翻译 Agent

翻译 Agent 只处理分配给自己的源文件，并只写唯一指定的译文目标。每个任务必须提供自包含上下文：必读规则和术语、唯一源路径、目标路径、输出模板、内容类型特殊规则及完成清单。

翻译 Agent 不得修改源文件、术语表、其他 Agent 的译文或全局映射。完成时返回：

- 新术语候选及首次出现位置；
- 疑似原文错误、解析缺失或结构歧义；
- 已执行的自检及仍不确定的内容。

Agent 可以报告现象，不负责最终认定原文错误、修改全局口径或跳过复验。

### 4.4 确定性脚本

脚本只处理可机械验证的事实。它们不得翻译正文、自动裁决术语、把结构计数通过解释成语义正确，或在不报告的情况下修复源文。

## 5. Skill 执行流程

### 5.1 确认任务与权威源

翻译前检查 URL 重定向链、版本号、Archive/最新版关系、官方目录和用户指定范围。源无法确认、版本冲突会影响译文或页面不完整时，停止并向用户说明差异。

将实际使用的 HTML、PDF 或其他源保存为本地只读输入。解析产物是翻译的唯一正文依据；需要核对复杂表格或疑似缺失时再回到权威源，不凭模型记忆补写。

多页面文档还必须建立源页面清单：规范化相对路径并去除 URL 锚点，持续检查新发现的范围内页面直到清单不再增长，再与官方 TOC 或导航对账。清单未闭合时不得开始翻译。

### 5.2 建立项目口径

先读取项目指令、`术语表.md`、声明的基准项目术语和同构已译样文。若项目没有术语表，主 Agent 创建最小 Markdown 表；若没有明确格式，至少记录英文原词、中文译法或保留方式、语境/备注和首次出现位置。

只预置高频、标准或事后统一代价高的术语。外部检索用于解决真实待定项，并记录可靠出处；不为了扩大词库而批量抓取候选词。

### 5.3 识别源家族并选择工具

主 Agent先检查 DOM/文档结构、页面组织、代码、公式、图片、脚注和标题深度，再选择最接近的已验证源家族脚本。

- 结构不变量一致时复用已有脚本，并在分派前做总量与顺序对账。
- 结构有新变体时，从最近的源家族脚本做最小派生，并用已知正确样本回归。
- 找不到适配脚本时，可直接调用可靠外部工具或编写任务局部脚本；完成后只有重复价值被证明的能力才沉淀进 Skill。
- PDF 优先调用宿主现有提取和渲染工具；仅当实际源是扫描件且用户目标需要时才使用 OCR。

不得为了“以后统一”先把不同源家族塞进一个通用解析器。

### 5.4 集中预处理

主 Agent统一完成：

1. 保护代码围栏后提取标题、正文、列表、表格、公式、图片、脚注、提示框和其他源结构。
2. 将图片等资源本地化，按文件魔数验证有效性，并核对源中的数量与顺序。
3. 建立全局标题、图号、文件名和跨章节复用映射；无编号图片不占用正式图号命名。
4. 对解析产物与源做结构对账。未处理的块级元素必须显式标记或导致失败，不能静默丢弃。

预处理通过后才能分派翻译。

### 5.5 划分工作包与动态并发

工作包沿章节、小节、API 页面或指令组等自然边界划分，并按实际体量和结构复杂度平衡。优先保持完整小节；确需把同一小节拆到多个工作包时，主 Agent必须记录“小节—片段—源顺序”映射，供合并和复验使用。小文档可以由主 Agent 直接翻译，不为使用多 Agent 而分派。

工作包 Prompt 中的标题数、内容块数等计数必须由脚本生成；不能可靠生成时，应明确声明源文件优先，要求翻译 Agent按源执行并上报出入，不得让手工计数覆盖源文事实。

并发是运行时决定：服从用户当前上限，并结合宿主能力、账户当前负载、在途任务和近期限流表现。限流后等待在途数下降再补派；新约束只对后续分派生效，不中止已经产生有效进展的任务。规格不写固定 Agent 数。

### 5.6 翻译与即时复验

翻译默认遵循以下底线，项目规则可以在不降低准确性和完整性的前提下细化格式：

- 技术含义忠实，中文表达自然；复杂长句可拆分，但不得改变逻辑关系。
- 代码围栏、标识符、命令、选项、路径和要求保留的英文逐字保留。
- 标题、图题、表题、脚注和特殊块按项目模板转换，不发明源中不存在的编号或说明。
- 疑似原文错误先回源确认。技术性误导照录并由主 Agent决定是否加译注；不得静默纠正。
- 官方重复内容保留；确认与既有权威文本完全一致后，可以逐字复用既有译文并程序化复验。

每个工作包完成后，主 Agent立即运行匹配源家族的校验并处理失败，再接受下一个依赖该结果的步骤。

### 5.7 集中术语合并与语义复核

主 Agent逐条把 Agent 上报的新术语与项目全量术语表、基准项目和已译内容对照。同词多译先判断是否为合理语境差异；确属冲突时按第 2.2 节裁决并全局检查实际用法。

结构脚本通过后仍须回源进行语义复核，重点检查技术难句、否定和条件关系、数量与单位、交叉引用、表格重建、原文瑕疵及脚本警告。校验脚本不代替这一步。

语义复核或术语统一产生的每次修改都是新的出错面。修改后必须重新运行受影响的结构校验并检查实际差异，不能沿用修改前的通过结果。

### 5.8 合并、终验与交付

合并只做经批准的拼接、标题层级调整和固定模板装配。禁止对全文执行不感知围栏的空白压缩或格式归一化。合并文件视为新的产物，必须重跑全量结构校验和必要的语义抽查。

交付时报告：源与版本、交付文件、术语表变化、校验结果、仍保留的不确定项，以及可获得的模型、token 和墙钟时间。

### 5.9 中断恢复

恢复时以本地源、译文、术语表和重新运行的校验结果为事实：

1. 发现已有目标文件后先验证，不因没有状态记录而重译。
2. 通过复验的文件继续复用；缺失、截断、校验失败或源已变化的文件才重新处理。
3. Agent 失败但留下产物时，先判断产物是否完整有效，再决定补派。
4. 不依赖中央状态 JSON、数据库或人工维护的逐段完成标记。

用户要求切换到更强模型或更高推理深度时，不默认重做全部工作，也不只重读最终译文。主 Agent先复核已有产物及其上游事实，包括页面清单闭合、解析损伤和校验脚本盲区，再复用通过复核的部分，只重做已证明失效的部分。

## 6. 术语库的最小制度

1. 每个翻译项目以人和 Agent 可直接读写的 `术语表.md` 为权威来源。
2. 后续项目可以显式选择一个或多个共享术语库，项目 `术语表.md` 覆盖共享默认；共享库的格式、选择与回流规则见[可复用术语库设计](./2026-08-30-reusable-glossaries-design.md)。
3. 翻译 Agent 只读术语表并按固定字段上报候选，主 Agent拥有唯一写权限。
4. 词条允许记录语境。同一英文词在 API 名称、操作语义或不同技术领域中采用不同译法不自动视为冲突。
5. 术语维护发生在真实翻译中：开始前预置必要项、翻译中收集、每批结束后集中裁决、终验时扫描实际偏离。
6. Skill 可以查阅官方文档、标准或可靠技术资料解决具体术语，但不维护后台爬虫、审批队列或不可变快照。
7. Skill 向翻译任务“提供术语”的方式是读取并把相关子集写入任务上下文；不额外建设术语服务。

## 7. 已被实践证明的脚本能力

### 7.1 源家族解析

解析脚本按源家族保留差异，至少覆盖实践中已经出现的能力：

- NVIDIA 分页 HTML：保护 `<pre>`，提取分页章节、标题、表格、公式、图片和代码。
- Sphinx/单页指南：按 `<section>` 切章，处理 `dl` 的定义列表、选项列表与表格脚注等多种语义。
- 数学密集单页：同时提取行内公式和 `div.math` 块级公式，未识别块不得静默丢弃。
- 深层嵌套参考手册：处理 `li`、`dd`、`blockquote` 内的 figure/pre 及 H6–H8 等深级标题。
- 多页面 API/DSL 文档：规范化相对链接、去除锚点并发现页面直到清单闭合，再处理页面级标题、代码标签页、暗亮图片对和无编号标题。

现有 `parse_nvidia_html.py`、`parse_bpg_html.py`、`parse_cublas_html.py` 和 `parse_ptx_html.py` 是这些能力的候选来源。实现可以复制并精简，但不得在首版合并成通用解析框架。

### 7.2 资源提取与核对

脚本应能下载或复制图片资源、验证实际文件类型、检查译文引用路径，并把解析图片数量与官方源数量和顺序对账。文件扩展名不能代替魔数验证；暗亮图片对、无编号图片和跨章复用由主 Agent按全局映射裁决。

### 7.3 结构校验

校验脚本按源家族设置不变量，可组合检查：

- 标题集合、原文标题和顺序；代码围栏外的 H1 唯一性；
- 围栏配对以及源/译代码块的逐字或逐行等价；
- 图片数量、顺序、相对路径和实际文件有效性；
- 脚注引用与定义配对；
- 解析占位符、HTML 注释或其他残留标记；
- 段落、列表项、表格、公式和提示框等内容块覆盖；
- 标识符、命令行选项、API 名或其他强 token 的计数及多重集差异。

合法格式转换可能造成分类计数变化，脚本应把不能直接证明丢失的差异降为警告，交由主 Agent定性；不得为了消灭误报而放宽真正的内容守恒。每次修改校验口径后，都必须先对已知正确文件和当前批次做回归。

清理解析伪影或比较两种提取结果时，可以先做 token 多重集差异，再以字母字符多重集检查是否丢字符。字母多重集只能作为内容损失兜底，不能证明字符顺序、结构或语义正确。

现有各项目的 `verify_*.py` 是候选来源。首版不要求一个通用 verifier；共享函数只有在不削弱源家族不变量时才提取。

### 7.4 代码围栏拼接

代码密集文档应支持从源文程序化抽取围栏内容并拼入译文，避免大模型或人工转写。`tile_ir/scripts/splice_fences.py` 是候选来源。拼接后仍需逐块比对，不能以脚本执行成功代替结果验证。

### 7.5 合并与重排

合并脚本默认只做去除文件首尾空白后的纯拼接，以及项目明确要求的标题层级调整。工作包跨小节或同一小节被拆分时，允许严格按“小节—片段—源顺序”映射重排；不得靠文件名或启发式正则猜测顺序。任何正文规范化都必须感知代码围栏。禁止使用全局连续空行压缩，因为实践已证明它会改变围栏内代码。

现有 `merge_sections.py`、`merge_chapter.py`、`merge_ops.py` 和 `merge_api.py` 提供不同源家族的候选实现；首版只保留验收场景实际需要且不会改写内容的部分。

### 7.6 工具选择记忆

“记住什么时候用哪个工具”由 Skill 的源家族判断表和失败条件实现，不建立运行时注册中心。每个脚本说明：适用源特征、输入、输出、已知不变量、失败信号和回归样本。新源只有在结构特征吻合并完成总量对账后，才能复用既有脚本。

## 8. 文件事实与写权限

Skill 不强制整个翻译项目采用统一目录，但必须能定位以下事实：

- 本地权威源或可复现的源定位；
- 项目 `术语表.md` 及其基准说明；
- 待译工作包和每个工作包的唯一译文目标；
- `images/` 或等价资源目录；
- 最终交付文件和可重新执行的校验脚本。

主 Agent在分派前明确每个路径的读写者。并行任务不得共享可写目标；术语表、资源映射和最终合并文件始终由主 Agent集中写入。运行日志、token 记录和临时校验产物默认放在翻译项目或工作区外，不写入本模块源码目录。

## 9. 失败与停止条件

出现以下情况时，不得把任务标记为完成：

1. 权威源、版本或用户范围无法确认；多页面源的页面清单没有闭合。
2. 解析后的标题、图片、围栏或关键内容块与源无法对账，且差异没有逐项解释。
3. 代码围栏、公式或强 token 校验失败。
4. 术语冲突可能改变技术含义而主 Agent无法根据现有优先级裁决。
5. 疑似原文错误尚未回到权威源确认。
6. 只有 Agent 自检或结构脚本通过，没有独立复验和必要的语义审查。
7. 合并后没有重新运行全量校验。

可恢复的限流、单个工作包失败或工具不适配不是整项任务失败；主 Agent应保留有效产物、降低并发、派生最小脚本或向用户报告具体选择。

## 10. 直接验收

首版实现至少用一个用户认可的、未被实现过程预先手工修正的 HPC 技术文档范围做真实试译，并直接证明：

1. Skill 能从权威源和项目约束开始，选择正确源家族工具并产出可阅读的中文 Markdown，而不是只生成中间结构或计划。
2. 源与译文的标题、代码围栏、图片、公式、脚注及项目指定强 token 完成对账；所有差异有明确解释。若使用多页面源，页面清单与官方 TOC/导航闭合。
3. 对技术难句、条件/否定关系、数量单位和表格重建做回源语义审查，没有已知的实质误译、漏译或擅自补写。
4. 至少一次并行或分批翻译证明翻译 Agent只写自己的目标，术语由主 Agent集中合并，最终译文不存在未裁决的术语冲突。
5. 在一个工作包完成后模拟中断，或按用户要求切换到更强模型/更高推理深度；恢复时复核上游事实并复用有效产物，只补做缺失或已证明失效的部分。
6. 合并前后的校验都运行，语义或术语修正后重跑受影响检查；代码围栏在最终文件中仍与源一致，合并没有进行全局空白改写。
7. 交付说明准确列出源版本、产物、术语变化、验证结论和可获得的模型/token/墙钟时间。

单元测试、文件存在、标题匹配、`git diff --check` 或旧项目重新跑通只能作为辅助证据，不能替代上述真实译文验收。

## 11. 演进规则

本模块的终态仍是“可持续积累经验的 Skill + 确定性脚本”，不是预先建好的翻译平台。

1. 新实践先以任务局部规则或源家族派生脚本解决；确认可复用后再沉淀进 Skill。
2. 只有两个以上不同源家族出现相同不变量，并且提取共享代码不会隐藏各自失败条件时，才考虑公共函数。
3. 只有真实用户需求证明 Markdown 术语表或文件恢复不足时，才重新设计存储、索引或状态能力。
4. PDF/OCR、出版 PDF、更多输出格式或外部术语检索集成分别由对应真实任务触发，不作为首版必备。
5. 每完成一种新源家族，更新适用特征、失败案例、脚本回归样本和翻译规则；不保存与当前行为无关的迁移叙述。
