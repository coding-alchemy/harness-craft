## 1. 问题陈述

用户提交文字版 PDF 后，需要得到完整、可回源的中文 Markdown，以及在明确要求时生成的 PDF。现有流程接受可可靠转换的 PDF，却缺少从 PDF 原始页面到源 Markdown 的确定性准备与校验入口。单篇论文的人工清单和裁图经验不能证明其他 PDF 可用，也不能证明后来变更过的译文仍为已验收版本。

本设计解决三个连续问题：建立有页面依据的翻译输入；把代码、图片、脚注等保真要求接入既有检查；让翻译验收身份一直约束到导出前。机器辅助检查只提供定位线索，视觉复核未闭合时仍只提供候选。

### 1.1 影响设计的当前接口与限制

| 当前事实 | 设计约束 |
| --- | --- |
| 四类 HTML 解析入口具备分派前独立对账；`verify_delivery` 的源家族枚举为 single、paginated、reference、api | PDF 新增明确家族分支，不冒充 HTML，不把二进制快照送入 HTML 对账，也不改四类家族的解析和工作包行为 |
| 共享检查已有 `scan_code_fences`、`compare_code_fences`、`compare_headings`、`footnote_diffs`、`image_occurrence_fails` | PDF 校验复用这些事实和比较规则，补足 PDF 权威依据；不复制项目正则版校验器 |
| 单页 `run_checks` 可接收候选文本、源文和最终目录；源 Markdown 尚不是 PDF 原始结构的独立证明 | 先验证 PDF→源 Markdown，再验证源 Markdown→译文；两者职责不能合并成源译自证 |
| 代码回填已支持按出现顺序从源围栏回填；共享扫描保留正文空白，但文本读取仍需注意换行转换 | PDF golden 固化后按实际字节建立比较基准；不能把项目脚本的行尾剥除带入通用实现 |
| `check_source_chains`、`run_source_reconcile`、来源图片事实提取当前依赖 HTML；显示映射含源快照、资源上下文、节点与摘要 | PDF 提供页面/区域依据并接入这些消费点；显示映射仍复用，不能因源类型不同丢掉图片身份或尺寸合同 |
| `KNOWN_TOOLS` 为固定核验入口，真实 `parse_args` 负责解释参数；检查上下文包含入口和有限共享依赖身份 | PDF 项目核验入口须有受约束的 Interface 和完整身份，不能开放任意 shell 命令注册 |
| `compute_delivery_identity`、`expected_review_binding`、发布前重读已形成单一身份口径 | 在既有口径中增加 PDF 源依赖；导出前复用翻译侧投影，不新增漂移台账或自动重签记录 |
| 完整交付检查要求目标 PDF、视觉复核与持久证据均存在 | 导出前只检查翻译就绪条件，不能直接调用完整完成检查而要求尚未生成的 PDF |
| 导出与核验已支持独立 Markdown 导出、默认出处前置、尺寸映射和候选门禁 | 新增的翻译验收检查仅在翻译加导出时启用；独立导出不被强制补英文源 |
| torch.fx 清单中的标题/表格候选为空；项目校验器漏检正文否定词、行尾空格和同名换图，当前译文 H1 复验失败 | 样本不是现成通用实现或已验收正例；候选生成、严格比较和来源绑定须单独验收 |

### 1.2 既有机制重审依据

本设计将扩展持久记录和身份依赖，先沿用留痕设计 §9 的重审结论：正常多来源输入需要保留每次来源归属；曾经仅将新增依赖补到局部 binding 的做法，会使第二来源、映射或导出政策变化漏出其他消费者。当前实现已收敛到统一身份构造，本设计不恢复多处各算一份摘要的方式。

PDF 的新增问题是来源事实尚无入口，而不是旧身份比较需要另一套算法。正常场景下，同一 PDF、裁决清单、源 Markdown 与译文得到稳定绑定；源 PDF、区域、golden、图片或检查器任一相关项变化，都应使对应旧复核失效。选择向原身份与源对账入口增加 PDF 事实，拒绝另建项目状态文件后再与交付记录同步。

## 2. 解决方案

用户仍交付权威源、范围和输出位置。主 Agent 先勘察页面并裁决机器候选，再按已裁决区域程序化提取代码和图片、准备可翻译的源 Markdown。源对账通过后进入现有翻译、术语、目录及工作包流程；最终由 PDF 源校验和既有交付检查收口。

完整业务顺序为：只读 PDF 与范围 → 页面事实和两种文本快照 → 主 Agent 裁决结构、阅读顺序与素材区域 → 素材及源 Markdown → 独立源对账 → 翻译与代码回填 → 硬检查及回源语义验收 → 比较验收身份并重跑检查 → 可选 PDF 导出 → 真实视觉复核 → 完成检查与持久证据。

机器不能裁决的顺序、表格或字符差异明确进入待处理项；不把缺失当作零，不把“候选已生成”当作“可以分派”。通用脚本与参考文档随 Skill 维护；项目只保存来源、裁决数据、复验入口和产物，不继续维护一套论文专用算法。

## 3. 用户故事

1. 作为提交 PDF 的用户，我希望知道正文是否有可靠文本层，以免扫描内容被当作已提取。
2. 作为提交带插图论文的用户，我希望位图素材与正文类型分别判断，以免一张插图导致整篇被误判为扫描件。
3. 作为用户，我希望未授权时不执行 OCR，以便控制处理范围与依赖。
4. 作为主 Agent，我希望获得有页面定位的标题、图题、表格、脚注候选，以便逐项裁决。
5. 作为复核者，我希望同时查看保版面与通读用文本快照，以便核对双栏和跨栏顺序。
6. 作为读者，我希望正文、表格和脚注按原文关系保留，以免阅读顺序改变含义。
7. 作为读者，我希望代码程序化提取并回填，以免手工转写改变字符或缩进。
8. 作为复核者，我希望 golden 先与原页面核对，以免提取错误被当作正确基准。
9. 作为读者，我希望图形、文字标签和图例完整，以免裁图只留下线条。
10. 作为主 Agent，我希望无大面积外框或同页有表格的图也能有据裁剪，以免工具算法限制被误当作需求边界。
11. 作为复核者，我希望每次图片出现都能回查源区域和已确认资源，以便发现同名换图与乱序。
12. 作为读者，我希望标题层级、英文原题、代码顺序和脚注不缺失，以便与原文对照。
13. 作为复核者，我希望整对删除脚注也被发现，以免内部配对检查掩盖遗漏。
14. 作为读者，我希望关键标识符、数字和单位保留，以免技术含义变化。
15. 作为用户，我希望文本层缺陷按更高保真证据处理并有译注，以便区分提取错误与原文异常。
16. 作为论文读者，我希望参考文献和附录表格有明确处理口径，以便查证引用与数据。
17. 作为用户，我希望翻译验收后的任何相关输入变化被定位，以免导出未经复核的新内容。
18. 作为用户，我希望正文改动即使通过硬检查也不能沿用旧验收，以免机器 PASS 掩盖语义漂移。
19. 作为已有 Markdown 的用户，我希望独立导出仍按原合同执行，以免被要求补做无关翻译验收。
20. 作为无法查看图像的执行者，我希望有逐页辅助统计，以便定位疑似异常，同时如实报告视觉缺口。
21. 作为交付接收者，我希望视觉复核未完成时只收到明确标注的候选，以免误认为成品已验收。
22. 作为维护者，我希望 PDF 复用现有检查与证据合同，以免同时维护两套规则。
23. 作为复核者，我希望清理临时目录后仍能回查当前源与验收证据，以便复现交付结论。

## 4. 实现决策

本节定义已批准的 Module、Interface 与数据合同；内部实现文件名在实施时按项目风格确定。

### 4.1 Module 职责与复用

| Module | Interface 与责任 | 复用 / 新增 / 替换 |
| --- | --- | --- |
| PDF 源准备 | 一个源处理入口，分勘察与按裁决物化两种操作；输入只读 PDF、范围、输出位置及裁决清单，输出页面依据、源 Markdown、素材和映射 | 新增 PDF 专属提取，复用既有资源身份、目录和映射合同 |
| PDF 源校验 | 一个已知核验入口，接收源 PDF、裁决清单、源 Markdown、译文与最终目录；返回定位差异和机器结论 | 新增 PDF→源 Markdown 对账；源→译文调用共享检查，不复制比较器 |
| 交付检查 | 增加 PDF 家族与对应核验入口；同一源预检、身份构造、复核绑定和证据发布消费 PDF 事实 | 扩展现有有限分支；HTML 分支保持原有参数和行为 |
| PDF 导出 / 核验 | 翻译加导出接入翻译就绪检查；无图像输入时可请求逐页辅助统计 | 复用原导出和核验入口，不建立第二个导出驱动 |

不引入插件发现、统一文档 IR、调度平台或新的工作包格式。源准备与校验必须分开：前者生成候选，后者独立重读 PDF 与交付产物；把校验藏在生成器内部会失去独立核验。

### 4.2 源类型与结构勘察（R1、R2）

源处理入口首先记录源身份、实际范围、页数、页面尺寸和坐标口径，再按页面/区域检查文本层覆盖、可读性及与版面的对应。正文文本层可靠但含位图仍为文字版；正文区域一部分需 OCR 才属于混合。文本提取为空、乱码或不能解释的覆盖缺口先标为未确定，不能仅据字符数或位图数判断已支持。

使用已在样本中使用过的文本提取与 PDF 对象读取工具：文本提取分别保留版面模式和通读模式；对象读取提供文本块、字形位置、绘图、链接、批注和位图区域。具体工具调用收敛在 PDF 源准备 Module 内；不为假想后端建立 Adapter 注册层。依赖采用已批准的 D5 口径，运行前记录可用命令、解释器、包版本与实际兼容性，不自动重复安装。

结构候选由编号、字体/位置、图题和页面对象共同提供线索，候选正则只作线索。主 Agent 对照全部范围逐项接受、修正或补充候选，并解释排除项。跨栏顺序以实际页面为准，在清单中记录块顺序与裁决依据；未知结构不得被候选过滤器静默删除。

### 4.3 一份 PDF 裁决清单与源 Markdown

清单是源转换的输入，不是执行状态库。使用带版本的单一清单，从候选逐项补充裁决；重新勘察不得覆盖已有裁决，源或范围改变时旧裁决须重新核对。权威资格来自针对当前 PDF 的实际回源复核及其绑定，不能仅靠清单内一个“已批准”布尔值。

| 清单内容 | 必须能回答的问题 |
| --- | --- |
| 来源与环境 | 哪份 PDF、哪些页/区域、何种文本与坐标口径、哪些工具版本产生本次依据 |
| 页面块与结构 | 每个标题、正文区域、代码、图题、图形、表格、脚注来自何页何处，按何种顺序进入源 Markdown |
| 裁决与排除 | 候选为何接受、修改或排除；页眉页脚和装饰为何不进入正文；还有哪些未解决项 |
| 素材对应 | 代码区域到 golden、图形区域到资源身份及每次出现的对应；同一图多个代码块或多个子图不得按图号计数猜测 |
| 转换与修正 | 标题层级、表格重建、跨栏重排、链接目标回退及译注的范围和依据 |
| 项目口径 | 已裁决强 token、参考文献处理及明确批准的局部范围；待定决策不能自动取默认 |

页面与区域统一使用明确的页面坐标，记录旋转和有效页面区域；裁剪工具坐标经转换后再调用，不能把像素坐标当作 pt。对象序号只在同一 PDF 身份下有效。清单定位与源 Markdown 区间显式关联，不能用输出总数反推源范围。

物化操作按裁决顺序组织源 Markdown：正文先还原段内硬换行，表格保留单元格与说明的对应，代码由 golden 包装为围栏，图形写入本地引用，脚注保留引用/定义关系。表格不能机械表示时由主 Agent 回源重建并记录映射；正文与表格的语义裁决不冒称全自动解析。物化结果有未解释缺失、多余或错位时阻断分派。

快照、清单和 golden 按需求规定保存到项目源资料目录；图片进入既有资源目录，新建项目辅助脚本进入项目脚本目录并从该位置复验。过程报告和页面检查图使用获准的工作区外位置；正式证据归入既有持久证据目录。既有用户项目不因本设计自动迁移。

### 4.4 代码与图形提取（R3）

代码区域从文本层程序化提取，保留字符、行序与等宽缩进。提取器产生的分页分隔符或区域外空白只能依据明确的区域与提取口径排除，不能通用剥除每行尾部空白。PDF 没有原始代码文件的字节表示，因此逐字节基准是经页面回源确认后固化的 UTF-8 golden；固化前的提取取舍留档，固化后不再以归一化改变基准。

源 Markdown 的围栏正文由 golden 生成，译文继续使用既有程序化回填。PDF 核验从保持原始换行的输入取得正文切片，与 golden 字节比较；不会用默认文本换行转换证明严格字节一致。新增读取口径限于 PDF 路线，不改变四类 HTML 的比较行为。围栏标记和语言信息沿用既有生成及检查规则，代码中的弯引号原样保留，运行性说明放围栏外。

图形以已裁决区域渲染为 PNG，记录 dpi、矩形、源页及输出身份。大面积绘图聚类只提供候选；没有可用外框时，由主 Agent 依据页面文本、图题及绘图范围明确区域，再由程序裁剪。不存在“自动算法没找到大框就拒绝整张图”的限制，也不凭未经核对的固定坐标批量裁图。

覆盖检查针对分配给本图的绘图与文字对象：遗漏图内标签、图例或绘图均定位失败；其他图、表格边框与装饰有独立归属。对象检查不能证明阅读正确，仍须对照源页查看裁剪结果。跨区域或重叠归属不清时保留待复核，不能扩大裁框把无关内容混入后声称完整。

位图素材自动提取和公式重建按已批准的 D3/D4 不纳入。遇到时定位、报告并按用户确认方式回源处理；不能删掉这些内容后完成全文验收，也不能把公式检测不到当作源无公式。

### 4.5 独立对账与硬检查（R1、R4–R6）

PDF 源校验入口重新打开源 PDF，核对源身份和范围，按清单定位重读页面内容，再与源 Markdown 的对应区间比较。标题、代码、图片、脚注按出现逐项核对；表格、正文的重建差异逐区域解释。不能只比较物化操作自己输出的两个清单；页面视觉证据和独立回源裁决负责覆盖机器候选可能共同遗漏的部分。

源 Markdown 通过该对账后，译文校验复用共享标题、围栏、脚注与图片事实检查，并直接以清单/golden 检查来源基准。无关语义改写不由结构比较器承诺检出，源全量对账和语义复核仍独立登记。

- 标题按权威层级、编号、英文原题与顺序对照；模板变换需已有逐项映射。
- 代码数量、出现顺序与 golden 正文必须一致；行尾空格变化也失败，不使用项目脚本的 `rstrip` 比较。
- 图片从独立确认的源区域资源取得有序身份，调用既有最终路径检查；同名换图、乱序、重复/缺失均拒绝，图号转代码围栏按转换映射解释。
- 脚注同时检查译文配对与权威清单覆盖，整对删除失败；译注新增脚注按既有规则单列，不补偿源脚注遗漏。
- 强 token 按 D2 从文本生成候选，主 Agent 裁决后显式传入。标识符与含单位数值均需覆盖；未配置显示“未检查”，不能据此完成需求要求的数字复核。
- URL 等文本层缺陷保留原提取值、页面位置、更高保真证据和修正值；源 Markdown 与译文采用经裁决的值并加译注，不静默修订只读 PDF。
- 参考文献按已批准的 D1 默认处理；附录表头/分类标签中英对应、数值保持；数字与单位、否定/条件、交叉引用、术语首现逐项回源复核。

硬失败、源依据不足与待人工复核分别报告，诊断含页/区域、源译位置、期望与实际。最终交付的必要项未闭合均不能完成；生成候选的成功退出不授予分派或验收资格。

### 4.6 PDF 来源与既有证据、尺寸映射的衔接

交付记录新增 `pdf-source` 家族，保持记录主版本和已有模式含义；PDF 源条目关联只读 PDF、实际范围、裁决清单、两种文本快照、源 Markdown、golden 与解析期映射。新家族字段只在 PDF 分支必需，不能向已有 HTML 记录补填虚构页面字段。源版本缺少出版方版本号时使用实际 PDF 身份定位版本，不编造版本信息。

来源图片身份使用“PDF 身份 + 页面/区域定位 + 提取口径 + 已确认资源摘要”。源页面文字和图形归属亦由裁决清单绑定。重新运行核验时读取这份固定依据，不能从待验译文重新生成期望摘要；重新提取或工具变化导致资源不同，进入重验，不覆盖旧来源证明。

解析期及交付级显示映射继续使用既有逐次出现、确定尺寸/未确定原因、来源与资源身份字段；PDF 来源明确标识家族，并以清单中的区域定位替代 HTML 节点定位。图片源宽度由已核对区域的物理宽度给出，按既有 pt 到 CSS px 口径转换；渲染 dpi 只影响栅格分辨率，不能被当作显示宽度。源宽度不能确定时保留 `unresolved-size` 原因，遵守原普通/严格策略。代码清单转围栏不生成伪图片条目。

来源预检、独立源对账和来源图片事实枚举在同一 PDF 家族分支消费清单；尺寸绑定复用现有绑定核心，导出仍消费原交付映射。新增依据进入 `compute_delivery_identity`，源对账/语义复核和视觉复核继续从其投影；缺摘要不是相等，清单或区域变化会使旧复核失效。旧 PDF 项目无该来源链时可保存和复验其文件，但不能自动生成已通过的复核记录；仅导出旧 Markdown 的模式不受影响。

PDF 项目校验器通过固定的 PDF 核验工具标识声明，项目脚本作为该已知入口的可复验副本或薄包装，使用同一真实参数解析与公共检查核心。声明包含实际入口、受控的本地依赖与项目数据，其身份一起绑定；项目专有清单移为数据，不另留弱化公共硬检查的实现。完整交付只接收符合此 Interface 的项目入口；历史 torch.fx 专用脚本需要适配，不能仅凭退出 0 加入已知工具。不会开放 shell 字符串、动态工具发现或未知检查器自动信任；这是已批准的兼容取舍。

### 4.7 翻译验收到导出前的身份检查（R7）

在既有交付检查 Module 中提供只读的“翻译就绪”操作，供导出入口调用。它复用源预检、独立源对账、真实核验参数解析、统一身份和翻译类复核比较；只检查本次实际有序输入覆盖的翻译事实，不要求尚未生成的 PDF、视觉复核或完成证据索引，也不修改交付记录。

导出与核验 Interface 增加可选的翻译验收记录参数。翻译加导出流程必须传入；只导出既有 Markdown 的调用方式保持不变，不根据文件名或旁边存在源文件猜测模式。显式记录声明的模式、范围与实际输入不符即拒绝，不能把错误记录降级为独立导出。

执行顺序如下：

1. 导出生成之前读取验收记录与当前依赖，比较验收时绑定和当前翻译身份，再重跑当前译文检查。记录缺失、复核未完成或依赖不可读时报告证据不足；身份不同报告漂移，列出变化路径或参数，并停止本次导出。
2. 标题删除等硬损伤由当前检查定位；只改正文否定词而硬检查仍通过时，身份比较仍拒绝。用户裁决后须完成受影响复核并绑定新身份；不能重算摘要后沿用旧结论。
3. 就绪操作返回本次只读身份，由导出报告记录其与验收记录中翻译事实及复核结论的关联。只投影本次范围的源、译文、资源、翻译检查与已完成的源对账/语义复核；不把尚待生成的 PDF 身份、导出报告或视觉复核写回翻译绑定，避免循环依赖。导出前及替换目标前以同一口径确认相关依赖和翻译复核未在运行中变化；发生变化不替换旧 PDF。该返回值是本次运行事实，不另存“已就绪”状态文件。
4. PDF 核验核对当前记录的同一翻译投影与导出关联；后补 PDF 身份及视觉复核本身不使此前翻译投影失效，但修改翻译输入、口径或复核结论会失效。最终交付检查仍执行全部源/译/PDF 检查、视觉复核和发布前重读，且保留发布期间完整交付记录字节变化即拒绝的既有规则，不能因导出前已通过而跳过。

持久证据仍按原合同在全部完成条件满足后发布新批次并原子切换索引。导出前操作不生成完成索引，不以目标 PDF 的缺失反向阻断首次导出。多 PDF 输出按各自实际输入检查，最终汇总覆盖仍沿用现有合同。

### 4.8 无图像输入时的辅助检查（R8）

在既有 PDF 核验入口增加显式辅助检查选项，由主 Agent 根据模型能力选择；不让脚本猜测模型是否能看图。辅助操作逐页渲染，记录渲染成功与否、墨迹覆盖率、图片对象与链接注解目标；阈值和渲染参数进入报告。覆盖率异常作为定位线索，不能沿用 torch.fx 的比例范围作所有页面的合格阈值。

渲染失败明确报告检查缺口，正常统计也只表示辅助项已完成。结果归入同次核验报告及后续持久证据，不另建视觉资格文件，不写入 `reviews` 的视觉通过结论。没有实际视觉复核时维持候选状态，完整交付检查拒绝完成；后续人工复核绑定同一 PDF、输入及政策后才可完成。

该辅助选项的渲染依赖按需探测；未启用的普通导出不安装 PDF 源处理依赖。真实目检继续覆盖所有页面、代码/表格/图形与接缝，并按原合同核查链接；对象统计不能代替实际跳转或阅读。

### 7.2 Karpathy 精简与自检

1. **基线。** 已对照需求 V0.2、完整性设计、留痕设计 §4.7/§9、PDF 导出设计和当前源码；§1.1 列出固定家族/工具、HTML 源链、共享比较器、单一身份投影及完成门禁这些实质限制。读取样本脚本和前轮反例证据确认其不能直接作为通用实现；§1.2 给出本次扩展记录前的机制重审。
2. **假设与差异。** 单篇论文不足以证明通用提取；源页面/区域由主 Agent 裁决，机器不承诺自动解决所有版面。§7.1 列明已批准的 D1–D5 与新增 Interface/记录兼容取舍；已确认的视觉门禁、输入漂移和图片身份要求全部保留，没有已实施但未经批准的行为变化。
3. **最小方案。** 比较两种可满足同一目标的方案：将 PDF 的页面准备、校验、身份和导出前检查集中写入独立驱动，也能通过完整实现满足合同，但会重复既有身份、资源和发布规则；本设计只新增 PDF 源准备/校验职责，嵌入现有交付和导出入口，选择后者。源准备可进一步拆成类型、标题、裁图、代码四个公共入口，但这些操作消费同一源与裁决数据，不值得增加四套调用合同。仅一条文本转换命令不能交付图形和来源证明，是不满足需求的下界，不把它当作可行备选。没有更简单且保留独立源对账、导出前门禁的已知可行替代。
4. **删除审计。** §1 对应 G1–G8 和机制重审；§2–§3 对应 R1–R8 的可观察行为；§4 按 R1–R8 分配新增与复用职责；§5 对应 A1–A10；§6–§7 保留非目标、已批准取舍和设计证据。裁图聚类只保留为候选方法，未引入框检测配置平台；项目硬编码清单改为数据，不复制旧弱校验；删除独立漂移台账和视觉资格文件的需要，依赖既有身份与复核记录。保留源独立对账和真实目检，因为二者证明不同结果，不能以精简为由合并。既有实现及外部脚本本轮均未删除，后续项目适配时只替换本次迁入的重复逻辑，不擅自清理外部历史文件。
5. **直接验收。** §5 以同一 PDF→Markdown→可选 PDF 的实际交付链证明结构、代码、数值、图片与来源对应，另用等计数损伤、正文漂移和无视觉输入反例证明拒绝行为。统计数量、文件存在、链接有效及机器 PASS 均不是替代证据。（V0.2 修订时状态：链路已实现并在 torch.fx 样本完成 A1–A10 直接验收，§7.3 重审后的边界反例与连续生命周期路径均有真实 CLI 回归；本句保留设计轮的自检口径，实施证据以验收记录与 CHANGELOG 为准。）

### 7.3 机制重审：位图区域待裁决枚举与裁决身份绑定（2026-09-27）

位图区域判定与 stale 机制连续两轮修复仍被评审触发新边界，按 AGENTS.md §5 执行本重审；证据齐备前不叠加新补丁。

**根因（正常/失败场景）。**

- 机制 A（位图区域枚举与类型判定）。正常场景：文字版 PDF 含插图，应判文字版并把位图区域单列待裁决；正文局部确需 OCR 时定位该区域并判混合（A10 原文）。失败场景一（第二轮评审）：以"面积 ≥25% 且不与文本块重叠"作用途判定，大幅独立插图被误判为混合、较小扫描正文区域漏判。失败场景二（第三轮复审）：为修正误判而加的 0.5% 噪声下限与"与任一文本块相交即跳过"，使小面积扫描正文区域、以及与可提取页眉边缘稍有相交的扫描正文区域从待裁决范围整体消失。共同根因：机器试图用单一几何信号（面积阈值、相交）闭合按 R1/A10 必须回源裁决的用途判断——无论把信号用作"判混合/判插图"还是用作"是否值得裁决"，都是越权裁决。
- 机制 B（stale 与重核绑定）。正常场景：源/范围变化后 inspect 标 stale 并保留旧裁决，主 Agent 逐项重核、记录 revalidate 依据后清除。失败场景一（第二轮评审）：二次 inspect 不继承旧 stale，标记自动消失。失败场景二（第三轮）：stale 只是建议性标记——清单不记录"裁决是针对哪个源/范围作出的"，直接从 JSON 删除 stale 且无有效 revalidate 依据时，materialize 与独立校验无任何残留事实可检出，随即放行。失败场景三：再次勘察整体保留旧 `pending` 列表，范围扩大后新页出现的位图区域等新发现项被旧列表覆盖丢失。

**方案比较与选择。**

- 继续局部修补（再调面积下限、相交容差等）：仍是用几何信号做裁决，每一轮都会出现新边界反例；拒绝。
- 收敛方案（选择）：枚举侧不做任何"消失性"过滤——文字版页面上全部嵌入位图区域一律进入 `pending` 待裁决（面积占比、文本相交等只作线索留档 basis），用途一律由主 Agent 对照原页回源裁决；裁决为需 OCR 正文的区域转 `ocr_region` 且清单类型判为 `mixed`（恢复 A10 原口径），未处置前拒绝物化；插图素材裁决后按 D3 单列。stale 侧从"标记"收敛为"裁决身份绑定"：清单记录裁决作出时绑定的源身份与范围；materialize 与 verify_pdf_source 在裁决绑定与当前源/范围不符、且无覆盖该变化的有效 revalidate 记录时拒绝——无论 stale 字段是否被人为删除。pending 由整体保留改为按区域身份合并，旧项裁决状态与新发现项各自保留。
- 对持久清单契约的影响：清单新增裁决绑定字段（裁决时的源 sha256 与范围）与 revalidate 记录的结构性校验（须含依据并覆盖绑定到当前的迁移）；兼容口径——既有 torch.fx 清单无该字段且其声明源身份与实际一致、无 stale 时，视为裁决即针对当前源（无不一致证据），不强制回填；一旦出现不一致证据即拒绝，不补签。清单 version 保持 1，新字段缺失按上述兼容口径解释。
- 行为差异说明：本轮恢复 A10 原文"定位需 OCR 区域并判为混合"（第二轮实现曾收窄为页内区域不参与类型判定），属回到已批准需求；其余已批准行为不变，无未经批准的行为差异。

**生命周期缺口的追加重审（2026-09-27 同日收尾复审）。**

- 失败场景四：连续生命周期断裂。pending 合并键包含可变的 `kind`——区域被裁决为 ocr_region 后，同源再次 inspect 对同一物理区域重新生成 bitmap_region 候选，键不同被当作新发现项追加，已裁决区域重新出现未裁决项；inspect 只继承 `classification.adjudicated` 标记、不继承已裁决的类型值，机器候选类型（text）覆盖人工裁决的 mixed。根因与机制 A/B 同源：机器重新勘察的输出没有按稳定身份与人工裁决对应，等同于用机器候选越权改写裁决。
- 最小修法：候选与裁决项按稳定区域身份 `(page, rect)` 对应（kind 不参与对应；无 rect 的项退回 `(kind, page)` 键，避免无关项误合并）——同一 PDF 同一区域内位图出现的枚举是确定性的，真正不同的位图出现具有不同 rect，不会被误合并；机器重新勘察时，已按区域身份对应的裁决项抑制同源候选的重复产生。`classification` 已裁决（adjudicated 有依据）时继承类型值与依据，机器类型判定只写入勘察报告作候选，不回写清单；源/范围变化时继承内容随 stale 一并冻结待重核。不增加第二套状态库，清单契约字段不新增（合并语义与继承规则的行为化），无新的持久契约或行为差异需另行批准。
- 绑定信任边界复核（撤回项）：仅删除 stale 而无有效 revalidate 继续拒绝（已有固定回归）。手工同时更新 `adjudicated_against` 且漏写/伪造 revalidate 时，现有事实无法区分它与"首次即针对当前源的合法裁决"——清单由主 Agent 维护是已批准的信任前提（§4.3：权威资格来自实际回源复核，不靠清单内布尔值），该场景超出机器可检边界，撤回为阻断项，不为此叠加历史状态机制；作为已知限制记录在 CHANGELOG。格式无效或 from/to/basis 不覆盖当前迁移的 revalidate 按无效处理、继续拒绝，属已实现的结构校验行为。

**完成门禁记录校验的追加重审（2026-09-28 第六轮复审）。**

完成门禁的素材补全判定连续多轮修复仍被触发新边界，按 AGENTS.md §5 执行本重审。

- 根因（正常/失败场景）。正常场景：主 Agent 回源处理素材后记录 `resolved: true` 与处理依据，门禁放行。失败场景一（第五轮）：门禁用宽松真值判断 `resolved`（`"false"` 等非空字符串放行）且不校验依据——已修为布尔严格判断并要求非空依据。失败场景二（第六轮）：依据取值写成 `resolution_basis or basis` 回退，而 `basis` 是 inspect 机器勘察自动写入的候选线索命名空间（`_pdf_source.py` 写入"面积占比/文本相交"等"用途待裁决"事实，`prepare_pdf_source.py` 原样拷入 pending 项）；真实候选仅手工加 `resolved: true`、保留自动线索 `basis` 即越过门禁。共同根因：两个命名空间混用——机器线索（候选为什么被定位）与人工解决依据（回源确认了什么、如何处理）共用/回退到同一字段族，门禁无法区分"机器说这里有东西"与"人确认已处理"。
- 方案比较与选择。继续局部修补（再列举哪些 basis 形态不算依据）：仍是字符串启发式，每轮会出现新写法；拒绝。重命名机器线索字段：churn 清单持久契约与既有测试/产物，而门禁不再读取该字段后冲突即消失，收益不抵成本；拒绝。收敛方案（选择）：解决依据只认单一人工字段 `resolution_basis`（非空字符串），`resolved` 须为布尔 true；机器线索 `basis` 在门禁语义中降格为纯诊断展示（仅用于问题定位消息），永不充当解决依据。不新增状态库或字段，清单 version 不变。
- 对持久清单契约的影响：`resolution_basis` 成为素材类解决依据的唯一受检字段；pending 项的 `basis` 明确为机器线索命名空间（与 revalidate 记录内的 `basis` 子字段互不相关）。既有真实清单无依赖旧回退的用法（torch.fx 清单无 pending 项），无迁移。
- 附带核查：materialize 门禁（`prepare_pdf_source.py`）的 pending 豁免口径为 `resolved` 真值或 `user-resolved`，与完成门禁不同层——materialize 管候选物化，D3 的"未补全不得按全文完成"由完成门禁独立强制；本轮不扩大修改 materialize，其口径如须收紧另行评审。
