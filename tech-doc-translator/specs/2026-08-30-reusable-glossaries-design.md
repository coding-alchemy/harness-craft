## 1. 设计目标

在不引入数据库、服务或新的翻译平台前提下，增加一层可移植的共享术语库。首个资产是从 `HPC_Trans` 的 12 份权威项目术语表整理出的 NVIDIA 术语库；项目 `术语表.md` 继续拥有最高的术语文件优先级。

本设计必须同时解决四件事：

1. 完整读取源文件中的多个 Markdown 表格并核算每条记录；
2. 保守去重，显式暴露实质冲突；
3. 为具体源文提供相关术语子集，并应用项目覆盖；
4. 让已验收项目的新术语按同一流程回流，且以后可增加同级术语库。

## 2. 既有接口、行为和限制

### 2.1 必须保留

- `tech-doc-translator` 仍是唯一对外 Agent Skill；新增脚本仍是内部工具，不承诺公共 CLI 或 Python API。
- 当前项目 `术语表.md` 仍是该项目的权威，翻译 Agent 只读，主 Agent 集中裁决和写入。
- 未批准候选不得入库；脚本不得做语义裁决。
- 术语相关修改后仍需检查译文实际用法并重跑受影响的结构校验。
- `/Users/nanzhang/workdir/HPC_Trans` 只作为初始实践来源，不能成为运行时依赖。

### 2.2 必须改变

- Practice-first 规格第 6.2 节原先用“声明基准项目”避免全局词库。本设计增加显式选择的共享术语库，替代反复复制多个基准项目的做法。
- Skill 的项目口径阶段需要在项目术语表之前读取所选共享术语库，并按“项目覆盖共享”形成有效术语子集。
- 现有 `merge_glossary.py` 只解析第一个表格且按英文键保存单行，不能直接用于初始多源整合或同词不同语境；保留它的项目候选合并职责，不把共享术语整理强塞进该接口。

### 2.3 输入事实

源术语表存在以下差异：

- 一个文件可有多个术语表格；
- 表头中的位置列可能叫“首现”“本章首现”“本书首现”“承接出处”等；
- 部分表格使用“定稿译法”，部分保留词表只有“英文原词”和处理说明；
- 中文字段有时混入“首现附英文”“承某项目”等说明；
- 同一英文键可能是格式差异、项目例外或真正的语境差异；
- 斜杠复合词和带括号缩写不能安全地自动拆分或合并。

## 4. 权威术语库格式

### 4.1 文件结构

每个 `glossaries/<library-id>.md` 包含简短元数据和一个权威表格。`<library-id>` 是稳定、显式选择的标识，并直接映射到同名 Markdown 文件；它不表达固定的厂商或学科分类树。

```markdown
# NVIDIA 术语库

| 元数据 | 内容 |
| --- | --- |
| 术语库标识 | nvidia |
| 来源范围 | 已验收 NVIDIA 技术文档项目 |
| 更新日期 | 2026-08-30 |

| 英文原词 | 中文译法/保留形式 | 处理方式 | 语境/备注 | 来源 |
| --- | --- | --- | --- | --- |
| kernel | kernel | 首现中英，后文英文 | CUDA 编程语境；首现写作“核函数（kernel）” | cuda_programming_guide:1.2.1; ... |
```

来源使用稳定的项目标识和原表位置，不保存对本机绝对路径的运行时引用。多个来源用分号分隔并稳定排序。

### 4.2 处理方式

权威表只使用四种处理方式：

1. `中文`：正文使用中文；
2. `首现中英，后文中文`；
3. `首现中英，后文英文`；
4. `英文`：始终保留英文。

源表中的“译”“首现附英文”“保留+首现注”等自由文本由主 Agent 根据实际含义映射到以上四类；附加限制放入“语境/备注”，不继续制造同义状态字符串。

### 4.3 唯一性

规范化键为“英文原词 + 语境”。英文原词只做 Unicode 规范化、去除 Markdown 行内代码标记、大小写折叠、首尾裁剪和连续空白折叠；不删除标点、不展开缩写、不拆分斜杠复合词。

- 空语境表示该术语库的默认口径，同一规范化英文键只能有一个默认词条。
- 只有技术含义或所需译法确实随语境变化时才增加带语境词条。
- 项目特殊写法优先留在项目术语表，不为了记录每次例外而膨胀共享术语库。

权威行按规范化英文键、语境稳定排序。排序、来源顺序和 Markdown 输出确定，保证相同输入与裁决不会产生无意义 diff。

## 5. 整合流程

### 5.1 扫描与解析

`consolidate_glossaries.py` 接受一个现有共享术语库（初次可为空）、一个或多个项目术语表及用户指定的报告路径。它扫描每个 Markdown 表格，并按表头含义映射字段，而不是按“第一个表格”和固定列号读取。

可识别表格至少覆盖：

- `英文原词` + `中文译法`；
- `英文原词` + `定稿译法`；
- `英文原词` + 明确的保留处理方式。

表头无法识别、行列破损或只有英文而没有可判定处理方式时，记录文件与行号并使完整核算失败。程序不得把普通内容表当作术语表，也不得静默跳过已经识别为术语表的异常行。

### 5.2 分组与核算

每条源记录保留源文件标识、标题区段、行号和原始单元格，然后按第 4.3 节的保守英文键分组：

1. 与现有权威词条等价：记为重复并补充来源；
2. 组内口径等价且无现有权威词条：生成权威候选；
3. 中文、处理方式或语境不等价：生成冲突组；
4. 无法可靠映射：生成明确错误。

报告按“权威、重复、候选、冲突、错误”给出数量，并满足：

```text
输入记录数 = 权威覆盖记录数 + 重复记录数 + 候选记录数 + 冲突记录数 + 错误记录数
```

这里的各类计数按源记录互斥计算。报告默认写到 Git 工作区外，权威库只包含已经裁决的最终结果。

### 5.3 裁决与发布

主 Agent 先按源表声明的基准关系和实际已验收译文判断冲突：

1. 仅格式或字段错位：整理为一个权威词条；
2. 项目例外：选择共享默认值，例外继续留在项目术语表；
3. 真正同词多义：建立明确语境的多个词条；
4. 仍存在两种合理口径：停止并请用户裁决。

整合工具可以生成只含无冲突候选的草稿，但不能直接覆盖权威库。主 Agent 使用 `apply_patch` 审阅并写入最终词条，再以验证模式重新运行完整核算。只有错误为零、冲突均有裁决且每条输入有去向时，`nvidia.md` 才能交付。

## 6. 翻译时使用

### 6.1 显式选择

用户或当前项目通过任务约定明确给出共享术语库路径或标识。Skill 不根据 URL、文件名或厂商字符串自动启用术语库。

选择多个共享术语库时，声明顺序就是共享层优先级；项目术语表始终高于所有共享术语库。同级冲突会在生成有效子集时显示来源和被覆盖值，未声明顺序时拒绝继续。

### 6.2 相关子集

`select_glossary.py` 读取源 Markdown、按顺序选择的共享术语库和可选项目术语表，输出供当前工作包读取的临时 Markdown 子集。

- 默认按英文原词在源文中的边界感知字面出现选择；大小写不敏感。
- 带标点、缩写或复合表达的词只在可证明匹配时选择，不用模糊相似度猜测。
- 项目词条覆盖相同英文键和语境的共享词条。
- 同一英文键命中多个语境词条时，项目覆盖或调用方必须明确选择语境；选择工具不得根据周边文字猜测，未选择时报告歧义并失败。
- 输出列出最终值和来源；未裁决词条不会出现在权威输入中，因此不能进入子集。
- 主 Agent 可以显式追加源文未字面出现但翻译任务确实需要的词条；该动作只影响当前任务。

子集是可重建的任务上下文，不是新的权威术语表，默认放在翻译项目的临时工作位置或 Git 工作区外。

## 7. 验收后回流

已验收项目的 `术语表.md` 可以作为 `consolidate_glossaries.py` 的新增来源：

1. 重新扫描并与现有共享库对照；
2. 重复项只补来源；
3. 新词进入候选，主 Agent 审阅后加入；
4. 冲突项显示既有值、新值、项目来源和语境，不覆盖既有词条；
5. 更新权威库后重新核算，并在代表性源文上重跑术语选择。

共享库更新不反向批量修改旧项目。某个默认口径确需改变时，用户必须先批准该差异；实现阶段再检查受影响的权威词条和新翻译行为，不以“新来源更晚”作为覆盖理由。

## 8. 错误与停止条件

出现以下任一情况时不得发布共享术语库：

- 识别出的术语表存在未核算行；
- 同一默认键有未裁决的实质冲突；
- 来源字段丢失或不能定位回输入项目；
- 权威库自身出现重复规范化键；
- 选择工具在没有明确顺序时静默处理同级冲突；
- 项目覆盖没有生效；
- 输出依赖 `HPC_Trans` 的绝对路径才能使用；
- 整合过程修改了任一输入术语表或既有译文。

## 9. 验证设计

### 9.1 确定性回归

`tests/run_glossaries.sh` 在临时目录内构造少量多表格术语源，直接验证：

1. 一个文件中的所有术语表格均被读取；普通 Markdown 表格不被误收；
2. 完全重复去重并合并来源；
3. 中文差异、处理方式差异和同词不同语境分别进入正确路径；
4. 异常行使核算失败并报告文件和行号；
5. 相同输入重复执行得到逐字一致输出；
6. 选择结果只含源文相关词条，项目表覆盖共享默认；
7. 两个任意名称的测试术语库可以按显式顺序组合，证明代码未硬编码 NVIDIA。

测试数据在脚本运行时写入临时目录，不增加一批只服务于表格样例的 fixture 文件。

### 9.2 NVIDIA 全量核算

实施时以 12 份项目根部 `术语表.md` 运行完整扫描，记录输入文件、表格、记录和结果分类总数。核算报告写到用户批准的交付位置或 Git 工作区外，不默认提交评估产物。

对已知差异至少复核：

- `kernel`：格式/处理方式归一；
- `leading dimension`：共享默认与 cuSPARSE 项目例外；
- `happens-before`：PTX 与 Tile IR 的语境判断；
- `peer access`：真正译法冲突；
- `preprocessor directive`：C/C++ 与 PTX 语境差异。

### 9.3 直接行为验收

选择一段包含权威词条、项目覆盖词条和未入库英文表达的真实 NVIDIA 源文：

1. 生成相关子集并人工核对来源；
2. 确认项目覆盖生效、未裁决项未进入；
3. 使用该子集完成小范围试译，检查实际译文遵循有效口径；
4. 将试译中一个已批准新词回流，再次选择时能够命中且不重复。

全量核算和真实试用是核心证据；文件存在、行数、单元测试与 `git diff --check` 只是辅助门禁。

## 10. 方案取舍

### 10.1 采用的最小方案

采用“同级 Markdown 文件 + 一个整合脚本 + 一个选择脚本”：共享资产仍可直接审阅，整合和相关子集由确定性脚本完成，语义裁决仍由主 Agent 负责。

更简单的方案是保留 12 份项目术语表，由新项目逐份引用。它不需要新文件或脚本，但不能消除重复、不能形成稳定默认值，仍依赖 `HPC_Trans` 的本机路径，也无法证明冲突是否已处理，因此不能满足核心目标。

另一个更简单的方案是只生成一份大 Markdown 并让每个翻译 Agent 全量读取。它能形成单文件，但 1,300 余词会无条件占用每个工作包上下文，也没有项目覆盖和相关子集的确定行为，因此拒绝。

### 10.2 拒绝的复杂方案

不建立数据库、后台审批服务、Web UI、术语本体、自动分类树、外部抓取器、不可变快照、公共 SDK 或自动回写旧译文。当前需求只证明文件型共享库、确定性核算和相关选择是必要的。

### 10.3 删除审计

设计不保存一次性统计脚本、盘点日志或全量冲突报告到仓库；这些是验证过程，不是产品资产。没有增加术语库 manifest、版本迁移层、自动领域识别、模糊语义匹配或多用户审批流。NVIDIA 之外只用临时测试库证明通用性，不创建空壳领域文件。

## 11. 假设、不确定项和批准状态

### 11.1 假设与取舍

- 初始权威来源限于项目根部 `术语表.md`，排除验收候选和临时清单。
- NVIDIA 术语库提供默认值，项目例外不反向污染共享默认。
- 同级术语库用显式标识和顺序组合，不建立统一分类体系。
- 首版保留 Markdown 权威和人工语义裁决，接受其吞吐量低于数据库审批系统，以换取可审阅和最小实现。
- `consolidate_glossaries.py` 与 `select_glossary.py` 分开，是因为前者修改候选资产、后者只生成任务上下文；合并为多子命令管理器会扩大接口并混合写权限。

### 11.2 已批准差异

本设计替代 Practice-first 规格中“不建立新的全局词库”的原决定，新增 `glossaries/` 资产、两个内部脚本和一个回归入口，并调整术语优先级。上述差异已于 2026-08-30 获得用户明确批准。

现在可以编写对应执行计划；执行计划再次获得用户明确批准后，才能开始实现。
