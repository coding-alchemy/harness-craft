## 1. 用户结果与边界

用户使用组件处理 CUDA/Sphinx 文档时，原始页面中的公式、图片、嵌套结构、复杂表格及格内代码能够完整进入翻译流程；合法产物不被错误阻断，真实遗漏、错绑和损伤不能通过核验。工作包使用一致且可追溯的规则，合并后的导航、图片尺寸映射和 PDF 与实际交付位置相符，减少项目重复编写适配及修复脚本的需要。

本文提取产品结果和验收要求，不把项目 monkeypatch、正则补丁、参数名或宿主错误码直接确定为通用实现。CUDA 样本用于证明真实结构可处理，不把页面名、表号、章数、固定并发数或本机安装路径写成组件规则。现有其他源家族的保真、独立核验与失败保旧要求继续有效。

本文定义需求，方案见同主题设计。需求、设计和完整计划已批准；2026-10-24 用户明确启动并批准最后修复及修订验收，当前结果见第10节。CUDA原项目只读，不执行全书重译；用户追加授权将CHANGELOG记为V1.4正式版更新并本地提交；不执行标签、推送或远程发布。

## 3. 公共要求

1. 原始来源只读。独立对账继续从原生来源建立预期，不以渲染器自己的结果、转换映射或统计证明自身正确；不得关闭门禁使解析通过。
2. 保持内容、顺序、角色、父属及实例对应。公式与代码按既有精确内容合同处理；表格计数、文件行数和摘要相等不能替代逐项核验。合法转换须可定位、可解释。
3. 相关源、规则、资源、检查器或转换变化使受影响旧证据失效；实际重核后恢复资格，无关有效包按既有局部事实复用。禁止补新摘要追认历史通过。
4. 使用现有解析、结构扫描、转换映射、任务差异和恢复入口。只有既有机制确实不能满足本次要求时才增加职责明确的能力；不把必要的独立来源核验合并掉。
5. 批量转换先验证候选再替换目标，失败保留原文件与有效证据。只修改明确目标；对当前转换不涉及的正文和资源保持不变。
6. P0 表示内容损伤、错绑、硬检查误判或真实来源无法进入流程；P1 表示工作流、恢复或运行可靠性；P2 表示说明与一致性体验。优先级不等于实施顺序，也不代表已取得执行授权。

## 4. 优化需求

### R1 数学内容与包装一致性（P0）

来源：原 §1.1、§1.5、§2.1。

- 标点紧排不得改写已识别的公式内容，包括 `$\overline{v} := \alpha \overline{v}$` 中的空格与符号；普通正文整理不得引入既有家族合同之外的公式空白变化。该保真要求不应由调用方逐次打开开关。
- 原 HTML 的数学节点、解析 Markdown 与独立对账采用一致且有依据的包装口径。仅剥除被确认是数学定界的外层包装，不对全文无条件删除 `\[…\]` / `\(…\)`，不借修复改变公式表达式或家族既有行内 / 块级类型。
- 保留共享数学扫描对代码、转义、普通货币及未解决定界的区分。无依据的数学差异仍须定位并阻断。

### R2 Sphinx 结构容器完整性（P0）

来源：原 §1.2、§1.3；补充 S1 为适配层中的 `sd-tab-set` 及嵌套缩进处理。

- API 家族保留链接包裹的图片、关联文字及适用链接事实；沿用暗亮图选择与图片来源身份合同，不因递归处理重复输出图片。
- 引用、脚注列表、折叠区域等容器内的列表、定义、代码、表格、图片和脚注按原顺序及归属保留。已支持的 `details`、脚注分支保持；只将复现失败的结构列为缺陷，不把纯文本未知容器静默视为已识别。
- `sphinx-design` 的 `sd-tab-set` 标签及内容保留对应关系；出现在列表或定义项中时不脱离父项，不改变相邻列表分组或代码正文。与已有 `sphinx-tabs` 一并验证。
- 各家族复用适用的结构处理，但保留各自已确认的输出合同，不以机械复制全部分支代替核对。

### R3 复杂表格与格内代码的完整链路（P0）

来源：原 §1.4、§1.6、§2.2、§2.7。

- 提供显式启用的跨行 / 跨列展开能力，将可解释的源表转为可阅读的真实 GFM 表格并生成现有合同兼容的逐表转换映射。默认未启用或结构不能可靠表示时继续明确拒绝，不静默展平。
- 源格到输出覆盖格位一一可追溯，保留表头分组、空格位、文字、公式和行内代码；格内围栏代码不因覆盖位展开而重复。转换含义仍需回源确认，映射不是自动语义批准。
- 同表多个格内代码块、跨围栏后的标记及相邻多表必须正确归属。坐标错绑、代码漏项、额外孤儿代码与重复代码须可检出。
- 明确 `[TABLE-CODE …]` 在解析源、中间工作包、核验与最终交付的生命周期。需要它建立格位关系的阶段允许保留并校验；最终 Markdown / PDF 不残留实际解析标记，原文代码中的同形字面示例保留；移除前后仍能核对代码属于哪个源格。
- 项目规则与残留检查必须使用同一阶段合同。不得仅扩展全局黑名单，导致仍按合法中间格式工作的任务失败；不得仅删标记而丢失格位关联。具体转换位置与存量中间产物处置见 D2。

### R4 表格相关修改不破坏数据（P0）

来源：原 §2.6、§3.6、§7.1、§7.2。

- 表格分隔行、数据行和锚点位置的结构性操作须依据实际 Markdown 块结构及格位进行。锚点落在目标表格外的合法块边界，保持题注 / 表格目标关联，不能插入表头与数据之间造成渲染断裂。
- 标记移除仅作用于该阶段允许移除的标记节点或独立标记行；围栏、行内代码中的字面示例及管道数据行不作为删除目标。不能用“从标记删除到空行”等范围推断吞掉正文。
- 写回前后检查逐表数据内容、顺序、列位、代码归属及实际渲染结构。文件行数差用于审计，合法增删标记 / 分隔行按预期解释；不能把全文件行数恒等作为所有操作的硬条件或充分证据。
- 失败不得覆盖原产物。已有数据损伤不能由格式修复自动补造内容，恢复必须有可回查的同源基线。
- 本次设计前须完成第 5 节的表格机制重审；是否需要新增官方重建脚本，依据现有能力能否承接 R3/R4 决定，不默认再建一套修表器。

### R5 核验入口与结构计数可信（P1；列表信息计数为 P2）

来源：原 §2.3、§3.1、§3.3、§3.5。

- 拆包的 `content_blocks.tables` 识别源解析格式的 `[TABLE]` 块及适用的真实 Markdown 表格，不把合法表报告为零，不把代码中的示例当真实表格；任务计数与拆包采用同一事实。
- 源译列表信息计数采用一致的嵌套项口径，覆盖有序 / 无序列表并排除代码示例。其信息性用途保持，合法结构差异仍定位解释，不新增仅凭计数判失败的门禁。
- API 核验接受至少一个源页面，单页章仍核对页面清单、独立官方 TOC、源内容和资源，不以改用通用校验器绕过家族检查；零源、缺页、错序仍拒绝。
- 项目辅助流程使用已有标题提取能力，覆盖长反引号、波浪围栏及缩进代码；不新增简单布尔翻转的平行扫描器。导出的标题工作清单只用于准备，不冒充独立官方标题依据。

### R6 合订导航与图片映射定位正确（导航 P0；映射组合 P1）

来源：原 §2.4、§3.2；与 R4 的锚点位置约束共同适用。

- 页内、章内及跨章引用都能回查来源与实际目标。不同源页或章节有同名自动 ID 时，不凭全书第一次匹配或“其他地方恰好存在”认定目标；缺失和歧义须准确定位，不能删除链接求通过。
- 明确源 `.html` 引用与交付 Markdown / PDF 目标的对应。翻译阶段保留目标与交付阶段获准的路径转换不互相冲突，转换前后能证明仍指向原对象。
- 用户已接受 D1：裸 `#fragment` 只查当前章，跨章必须明确目标文件；本章缺目标时报告引用位置，不再跨章回退。存量依赖回退的链接须据源修正，不能删除链接或凭唯一同名目标自动迁移。
- 各章图片尺寸映射组合到交付根时，Markdown 和图片条目均按最终映射位置正确解析，保留出现序号、来源身份及显示尺寸。支持既有单章布局和多章组合，不依赖当前工作目录或只修改路径字符串前缀。
- 不预定新增 `--markdown-base`；所需能力是可验证的映射输出 / 组合基点及完整引用转换，仍遵守交付根 `export/images_display.json` 的现行合同。

### R7 规则、任务与检查使用同一口径（P1）

来源：原 §3.4、§4.3、§4.4。

- 分派前明确当前规则、术语、输出模板和适用检查，确认它们对链接、表格标记等关键行为没有冲突。已确认冲突必须解决后才分派；不要求通用程序自动裁决任意自然语言。
- 复用任务中已有内容、引用选区和摘要，以及 `--previous-task` 的精确差异能力。规则变更后暂停受影响旧任务的完成认定，保留旧任务及实际旧文本，说明变化与重验范围，按当前口径更新任务。
- 新旧产物均按当前规则和来源实际复验；旧回报、已读消息或“磁盘最新”声明不能证明已同步。缺旧文本只报告依据缺口，不猜差异；无关有效包继续复用。
- 给出可执行的规则更新使用说明及规则—检查对应示例，优先覆盖本次链接、标记冲突。无需增加通用规则引擎或第二份版本登记库。

### R8 停滞与限流后的自动减并发及可靠接续（P1）

来源：原 §4.1、§4.2。

- 使用宿主可取得的在途、终止、失败与限流事实，区分“运行中”“已失败”和“状态不明”。目标文件长时间未修改只作为检查线索，不直接推断 Agent 死亡或任务未分派。
- 接续前确认旧执行者已退出或不再拥有目标写权限；同一目标同一时刻只由一个执行者写入。已有 draft / target 按当前源、规则和已有恢复入口核对，不能把文件存在视作完成，也不默认重译全部内容。
- 用户明确要求“Agent 停滞或限流”就自动减少子 Agent 数量。主 Agent 在已授权任务中依据可取得的宿主事实自动下调并发，遵守用户当前上限；设计须明确触发、降幅、最低值、重复事件处理及降至最低后的行为，不逐次等待用户批准降并发。
- 一次 CUDA 项目中的“10 降至 5”不成为固定阈值或跨账户公式，`1302` 不作为所有宿主的统一接口。状态不明不能以自动减并发为由认定旧执行者退出，或启动同目标的第二写者。
- 自动减并发通过现有主 Agent 协作流程实现；D3 不扩展为独立调度平台、无人值守重派、自动提并发或通知服务。接续仍须核对现有产物、当前规则和旧执行者所有权。
