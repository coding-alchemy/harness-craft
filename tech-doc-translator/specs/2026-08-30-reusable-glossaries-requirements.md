## 1. 背景与核心目标

`HPC_Trans` 已完成的 NVIDIA 技术文档各自维护项目级 `术语表.md`。这些术语表存在大量重复，也包含合理的项目例外、同词多义和未经统一的译法。后续翻译若继续逐项目复制基准术语，会重复整理工作，并使已经裁决的口径难以稳定复用。

本需求的核心目标是：把已验收 NVIDIA 翻译项目中的术语整合为一份可复用的 NVIDIA 术语库；新项目可以采用其中的默认口径，并用自己的项目术语表覆盖；项目验收后，新的已批准术语可以继续回流。相同机制应允许以后建立其他同级术语库，但本次只交付 NVIDIA 术语库。

核心结果不是“生成一个大文件”，而是用户能够确认：来源术语均有去向，重复项已消除，实质冲突没有被静默裁决，项目例外不会被共享默认值覆盖，新项目能复用并继续积累术语。

## 2. 基线事实

截至 2026-08-30，只读盘点得到以下事实：

1. `HPC_Trans` 下有 12 份项目根部的权威 `术语表.md`，总计 2,139 行。
2. 从带有英文词和中文译法字段的 Markdown 表格中可解析出 1,499 条记录、1,356 个规范化英文键。
3. 至少 62 条记录的译法和处理方式完全重复。
4. 38 个英文键存在中文字段差异，另有 22 个英文键中文一致但处理方式不同。
5. 源文件包含多个表格和多种表头；现有 `merge_glossary.py` 只读取第一个表格，不能完整承担本次整合。
6. 一部分差异只是把首现说明写进中文字段等格式问题；另一部分会改变译文，例如 `leading dimension`、`happens-before`、`peer access` 和 `preprocessor directive`。

以上数字用于说明输入规模和冲突类型，不作为最终验收的固定条数。最终数量取决于逐项去重、拆分复合词条和冲突裁决，但每条源记录必须被核算。

## 3. 术语与优先级

### 3.1 术语库层级

- **共享术语库**：从多个已验收项目提炼的可复用默认口径。本次首个实例为 NVIDIA 术语库；以后其他术语库与其同级。
- **项目术语表**：单次翻译项目中的权威术语，可记录项目特殊口径和当前文档语境。
- **候选术语**：尚未获准进入项目术语表或共享术语库的记录。

### 3.2 冲突优先级

同一翻译任务发生术语冲突时，顺序为：

1. 用户对当前任务的明确要求；
2. 当前项目的 Agent 指令、交付约定和项目 `术语表.md`；
3. 当前项目明确选择的共享术语库；
4. 当前项目声明的其他基准资料和已批准译文；
5. Skill 默认规则和一般翻译习惯。

项目术语表覆盖共享术语库时，不修改共享术语库。项目同时选择多个共享术语库且同一术语冲突时，必须使用项目明确给出的顺序；没有顺序且冲突会影响译文时停止并请用户裁决。

## 4. 功能需求

### 4.1 初始整合

1. 初始输入只包括 `/Users/nanzhang/workdir/HPC_Trans` 下每个翻译项目根部的 `术语表.md`。
2. `validation/` 中的章节候选、批准清单和验收中间文件不作为独立来源重复导入；已经批准的结果应以项目根部术语表为准。
3. 输入目录和文件保持只读；交付物必须进入 `tech-doc-translator` 模块，并可脱离该绝对路径使用。
4. 所有可识别的术语表格和术语行都必须被扫描，不得只读取每个文件的第一个表格。
5. 每条输入记录必须归入以下一种结果：进入权威库、与既有权威词条重复、成为需裁决冲突，或因格式/信息不足而明确报错。不得静默跳过。

### 4.2 去重与冲突

1. 英文键比较至少忽略大小写、首尾空白、连续空白和 Markdown 行内代码标记。
2. 不得自动删除标点、拆分斜杠复合词或合并近义词；这些转换可能改变术语身份，必须经人工语义判断。
3. 只有英文键、中文口径、处理方式和语境均等价的记录才能自动折叠。
4. 仅首现位置或来源不同的等价记录合并后必须保留全部来源。
5. 中文译法、保留策略或语境不同的记录必须进入冲突裁决；程序不得按输入顺序、文件时间或数量多数自动选择。
6. 源文件已明确声明基准继承关系时，主 Agent 可以据此裁决；仍有两种合理解释且会改变译文时，必须请用户决定。
7. 未裁决项不得进入权威 NVIDIA 术语库，也不得被新翻译任务当作默认口径。

### 4.3 权威词条

每个权威词条至少记录：

- 英文原词；
- 中文译法或保留形式；
- 处理方式；
- 必要的适用语境或例外说明；
- 一个或多个来源标识。

共享术语库必须允许同一英文词在明确不同的技术语境中保留不同词条。没有语境差异的同一规范化英文键只能有一个默认口径。

### 4.4 新项目使用

1. 新项目必须明确选择是否使用一个或多个共享术语库；不得仅根据 URL 或厂商名静默启用。
2. 主 Agent 只向具体翻译任务提供与其源文相关的术语子集，不把整份大型术语库无条件塞入每个工作包。
3. 翻译和验收仍以项目 `术语表.md` 为当前项目权威；共享术语库提供默认值，不取代项目表。
4. 术语子集无法覆盖语境冲突时，翻译开始前完成裁决或记录项目覆盖项。

### 4.5 持续积累

1. 只有已经通过项目验收并由主 Agent 确认的术语才能成为共享术语库候选。
2. 新候选仍按第 4.2 节去重和冲突规则处理；项目中出现过不等于自动晋升。
3. 已有权威词条不得被候选静默覆盖。修改既有默认口径必须显示旧值、新值、来源和影响范围，并获得明确批准。
4. 更新后相同输入和相同裁决应产生稳定顺序和稳定内容，便于通过 Git diff 审阅。

### 4.6 同级扩展

1. NVIDIA 不是硬编码的唯一术语域；以后可增加其他同级术语库。
2. 每个术语库独立维护来源、默认口径和版本差异，不自动互相合并。
3. 本次不预定义厂商、学科或产品的分类树。术语库由稳定标识和用户/项目显式选择区分。

## 5. 安全与质量要求

1. 初始来源、现有项目术语表和译文不得被批量改写。
2. 自动化只负责解析、规范化、分组、核算和确定性输出；语义裁决由主 Agent 完成。
3. 解析失败、列含义不明确或 Markdown 单元格损坏必须报告文件与行号。
4. 冲突报告和临时核算结果默认写到 Git 工作区外；只有用户明确批准具体路径时才能作为仓库文件保存。
5. 共享术语库必须是人和 Agent 可直接审阅的 Markdown，不引入数据库、后台服务或外部运行时依赖。

## 6. 非目标

本次不做：

- 自动抓取互联网术语或调用外部术语服务；
- 自动判断专业译法正确性；
- 用共享术语库批量重写既有译文；
- 建立术语审批数据库、Web UI、不可变快照或本体分类系统；
- 同时创建 NVIDIA 之外的真实术语库；
- 为每个词保存完整历史版本或构建公共 CLI/API。

## 7. 直接验收标准

1. NVIDIA 权威术语库可在没有 `/Users/nanzhang/workdir/HPC_Trans` 的环境中被 Skill 读取，并包含英文、中文/保留形式、处理方式、语境和来源。
2. 12 份项目根部术语表中的每条可识别记录均能在一次完整核算中对应到“权威词条、重复项、冲突项或明确错误”之一，核算总数与输入一致。
3. 完全重复记录只形成一个权威词条且保留全部来源；重新运行不会产生重复或无意义排序变化。
4. 用至少三个真实冲突验证程序不会静默选择，其中至少包含一个项目例外和一个同词不同技术语境。
5. 在代表性 NVIDIA 源文上选择相关术语子集，结果包含源文实际出现的权威词条，不包含未裁决候选；项目表中的覆盖值优先于共享默认值。
6. 将一个已验收项目的新术语作为候选再次合并：首次经批准后进入共享库，再次执行被识别为重复；冲突候选不会覆盖既有词条。
7. 使用同一机制和一个最小测试术语库证明同级扩展不依赖 `nvidia` 文件名或 NVIDIA 专用代码；测试术语库不作为正式领域资产交付。

文件存在、Markdown 格式正确、脚本退出成功或单元测试通过只能作为辅助证据，不能替代上述来源核算、冲突保护、项目覆盖和新项目复用结果。

## 8. 假设、不确定项与待批准差异

### 8.1 当前假设

1. “术语库”指经过项目验收的权威口径；因此初始导入排除 `validation/` 下尚可能包含候选状态的文件。
2. NVIDIA 术语库是可复用默认值，不是凌驾于项目规则之上的全局强制词典。
3. 同级术语库使用显式选择，不在本次设计厂商与学科的统一分类体系。
4. Markdown 仍是权威存储；输入规模尚不足以证明需要数据库或服务。

### 8.2 相对现行规格的行为变化

[Practice-first 规格](./2026-08-29-tech-doc-translator-practice-first-design.md)第 6 节原先要求后续项目声明基准项目，而不是建立新的全局词库。本需求以用户 2026-08-30 的新方向增加“可复用共享术语库”层级，同时保留项目表优先、Markdown 权威、人工裁决和无术语服务等原约束。

上述需求与行为变化已于 2026-08-30 获得用户明确批准。执行计划再次获得明确批准前，不修改现行 Skill、脚本或术语资产。
