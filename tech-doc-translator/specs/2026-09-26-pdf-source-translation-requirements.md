## 1. 目标与基线

用户能把文字版 PDF（学术论文等）作为源交给 skill 完成翻译：先判定源类型并勘察结构，素材按"代码清单 / 图形"分治提取（代码逐字保真、图形裁剪为图），译文按从 PDF 建立的权威清单做硬不变量校验，按论文交付形态产出；翻译+导出任务对输入漂移和无图像输入的视觉复核有明确防线。上述能力沉淀进 skill（通用脚本 + 参考文档），不留在单项目目录。

基线为当前 [SKILL.md](../skills/tech-doc-translator/SKILL.md)、[翻译约定](../skills/tech-doc-translator/references/translation_conventions.md)与 [PDF 导出规则](../skills/tech-doc-translator/references/pdf_export.md)。已确认的现状：源家族表只覆盖 HTML 四类；PDF 仅按"可被外部工具可靠转为 Markdown 的 PDF"口头接受，无判定、勘察、提取与校验脚本；扫描版仅约定"用户明确要求时用宿主 OCR"。术语表、`00_目录.md`、图题格式、代码回填与逐块比对、强 token、证据与目录合同（留痕需求 R1–R9）、PDF 导出全链路均为既有能力，本需求不重述。

torch.fx 经验按证据性质区分：

- **已有样本证据**：项目保存了两种文本快照、6 个代码 golden、3 张裁剪图与 8 个图题定位；本轮在临时副本恢复符合既有约定的 H1 后，项目校验器全部通过。这只证明其现有检查通过，不代表语义或通用能力已验收。
- **人工完成的工作**：36 个标题与 58 个强 token 为人工清单；交付说明记载 5 张表和 1 条脚注已回源对账。现有 `structure_inventory.json` 的 `headings` 与 `tables_pages` 为空，不能作为标题、表格候选生成成功的证据。
- **待新增或补足的能力**：完整结构候选生成、严格代码字节比较、PDF 源图身份绑定与输入漂移防护。项目校验器会剥除代码行尾空白；本轮反例中代码添加行尾空格、正文“都可以使用”改为“都不可以使用”、图 6 文件内容替换为图 7 均仍通过，不能据此声称相应保真能力已具备。
- **当前样本状态**：2026-09-27 复验当前译文，H1 缺英文原题导致 FAIL；历史交付说明中的 PASS 不代表当前文件仍有效。正向验收样本须按第 4 节固定版本并重新复核，不能直接把当前目录当作已验收基准。

## 2. 共同约束

- 本需求只新增文字版 PDF 源链路与导出协同补强，不改变四类 HTML 家族的解析、校验、工作包与恢复行为；术语表、目录交付、强 token、代码回填、证据与目录合同继续适用。
- PDF 为只读源；文本快照、结构清单、代码 golden 等对照依据持久化到翻译项目 `source/`，辅助脚本写入项目 `scripts/` 并从该路径复验（SKILL.md 执行顺序既有规则）。这些对照依据（含块映射与裁决清单）是源/译核验与工作区恢复的保留输入；翻译任务收尾清理按 [翻译产物清理需求](./2026-10-01-translation-artifact-cleanup-requirements.md) R5 保护，不作为可重建过程产物删除。
- 单项目沉淀的校准常数（矢量绘图聚类面积阈值、页眉装饰线位置、裁剪边距、渲染 dpi、标题候选正则）不得硬编码为通用规则；采用相关方法时须先确认适用条件，再参数化并记录取值依据，参数化本身不证明方法通用。torch.fx 项目的 36 标题、58 强 token 等人工对账产物是证据样例，不是可复用的通用数据。
- 外部工具依赖（poppler `pdftotext`/`pdftoppm`、PyMuPDF 等）显式声明并记录版本与已知 API 兼容差异（如 rebased API 中 `Rect` 无 `get_area()`）；环境探测优先于安装：先查已有浏览器构建与包版本，不重复安装。
- 需求描述保真性质，不锁定具体工具与实现；交付说明中记录工具链与复现命令。

## 3. 功能需求

### R1：PDF 源类型判定与结构勘察

- 源为 PDF 时分别判定文本可提取性与素材类型。文本按本次范围内页面/区域判定为文字版（正文有可靠文本层）、扫描版（正文需 OCR）或混合（两类正文区域并存）；素材另记文本型代码、矢量图与嵌入位图。嵌入位图的存在不直接把文字版判为混合，也不能仅凭嵌入位图数量判断是否需要 OCR。
- 判定证据（文本层质量、需 OCR 的区域、嵌入位图数量、矢量绘图、批注对象数）留档并写入交付说明；文件名与元数据声明（如 "with-annotations"）不作为事实依据，以对象级核查为准。扫描版及混合源中需 OCR 的区域维持既有口径（仅用户明确要求且使用宿主 OCR 工具），不自动进入新链路；含位图素材的处理边界按 D3 裁决。
- 文字版执行结构勘察：枚举页面文本块、绘图、链接与批注，生成结构清单候选（标题、图题定位、表格页、脚注），持久化到项目 `source/`；候选经主 Agent 逐项对账裁决后才成为权威清单，机器候选不自动成为权威。
- 勘察与提取结果须能与 PDF 原始结构逐项对账（标题候选、图题、代码区域）；未解释的缺失、多余或错位阻断分派，沿用既有"独立对账"理念，权威源从 HTML 快照换成 PDF 结构勘察。

### R2：版面感知的文本提取

- 复杂版面（如双栏）用两种互补模式提取：保栏间排版模式适合局部核对（表格、代码），裸模式接近阅读顺序适合通读；两种模式的源文快照均持久化到 `source/` 作为对照与回源依据。
- 跨栏混排区域（致谢、参考文献等）的顺序不得由单一模式裁定，须回到页面版面分析确认真实顺序并记录结论。

### R3：素材分类提取（代码清单与图形分治）

- 逐图判定素材类型：文本型（代码清单，本质是文本层的图）或图形型（矢量/位图统计图）；判定依据留档。
- 文本型：按区域程序化提取为 golden 文件，提取通道必须保留等宽缩进（已知不满足该性质的通道，如按行 clip 提取丢行首缩进，须规避并记录）；golden 经页面回源确认内容、行序与缩进后，译文代码围栏从 golden 程序化回填并逐字节比对，比较时不得剥除行尾空白或归一化差异，禁止手工转写；弯引号等内容性字符原样保留，影响可运行性时加译注。区域坐标口径（如 pt/72 dpi）在脚本与文档中一致。
- 图形型：按明确且可复现的 dpi 口径裁剪为 PNG；裁剪区域须有页面、图号/图题及区域归属依据，坐标、边界取舍与复核结果可回查，不凭无依据的坐标猜测裁剪。逐图核对图形、图内文字标签与图例完整，图题与图形对应，漏裁或归属不明即失败；同页其他图、表格边框、正文与装饰须区分归属，不要求一张图覆盖全页非装饰绘图。
- torch.fx 的“大面积矢量绘图聚类求并集加边距”是该样本已使用的方法，仅在图表框可识别、聚类与目标图逐项对应时作为候选提取方式；不作为所有矢量图的强制算法。仅覆盖绘图对象不能证明文字标签完整；无大面积外框或同页混有其他结构时，仍须满足上述保真与归属要求，具体提取方法由设计确定。
- 位图型图的自动提取为未验证能力（知识来源样本为 0 嵌入位图），是否纳入本期及对整篇输入的处理见 D3；遇到时定位并报告，不虚构支持，未解决的素材缺失不得按全文完成交付。

### R4：基于权威清单的 PDF 源校验

- 硬不变量至少包括：标题数量、层级、英文原题与顺序（对照 R1 权威清单）；代码围栏与 golden 按出现顺序逐字节一致；图片来源身份、出现数量与顺序、最终引用及实际文件一致；脚注引用与定义配对且相对权威清单不缺失；强 token 逐字命中。上述不变量针对 Markdown 译文验收：译文 H1 保留英文原题、URL 还原译注保留在 Markdown 中不变；PDF 成品另按获准投影核对——可见总标题为中文题名、已标识译注不进 PDF（见 [PDF 导出排版优化需求](./2026-09-28-pdf-layout-optimization-requirements.md) C4），二者不互相放宽。
- PDF 源图区域须与译文每次图片出现逐项对应，依据至少能回查源 PDF 身份、页面/区域、对应图号或定位及经回源确认的提取资源身份；代码清单转围栏按 R3 留存转换对应，不计作漏图。绑定依据独立于待验译文和待验图片建立，不能仅凭文件名、总数或对当前文件重算摘要证明来源。图片引用仍须落在交付根内、文件存在且魔数有效；同名换图、换序、漏图均失败。脚注整对删除也须按权威清单检出，不能仅检查译文内部配对。
- 强 token 须同时覆盖标识符与关键数值（含单位，如操作数、加速比、时延、百分比）；清单生成口径见 D2，未配置时校验器明示"未检查"，不冒称已核对。
- 校验脚本写入项目 `scripts/` 并从该路径复验；FAIL 先区分产物问题与口径问题，修复后重跑（既有规则）。

### R5：文本层缺陷与原文异常的权威回退

- PDF 文本层与视觉排版不一致（如 URL 下划线在文本层丢失而视觉存在）时，以更高保真证据（内嵌链接目标等）为权威回退并加译注；提取缺陷不得当作原文内容带入译文。译注随 Markdown 保留并参加翻译验收；PDF 导出视图排除该译注（仅正文文本节点，代码与原文引用不扫描），正确 URL 目标仍在 PDF 中可见（C4）。
- 疑似原文笔误沿用既有约定：回源确认、按语义译出、加译注，不静默改正。

### R6：论文类交付形态

- 参考文献按学术惯例保留英文原文，不强制翻译（默认值待 D1 确认）。
- 附录数据表格：表头与分类标签译为中文并括注英文，数值逐字保留；关键数字与单位进入强 token。
- 图题、全书目录、术语表、笔误处理沿用既有翻译约定，不重复定义。

### R7：翻译+导出的输入漂移防护

- 翻译任务同时要求 PDF 导出时，翻译验收证据须绑定验收时的译文、相关源与资源身份及校验口径，复用既有证据合同；导出前将当前身份与该验收身份比较。输入变化即报告漂移并定位差异，旧验收失效；校验口径变化同样使相关旧复核失效。不得用当前身份重写旧验收基准后放行；缺少有效验收身份时报告证据不足，不能默认输入未变化。
- 导出前仍须对当前译文重跑译文级校验（含项目级校验器），但硬检查通过不证明输入未漂移。差异交用户裁决；按裁决处理并重新完成受影响验收、绑定当前身份后才能继续，不以导出机器检查通过替代翻译验收。
- 导出证据继续绑定输入摘要（既有"输入保护确认"）；项目级校验器可声明为交付检查的核验入口参与复跑，具体机制由设计定义，不另建一套验收状态或证据体系。仅导出已有 Markdown 的模式维持既有合同，不因此强制补做翻译验收。

### R8：无图像输入时的辅助检查与候选交付

- 执行模型无图像输入时，导出后执行程序化辅助检查：逐页渲染并计算墨迹覆盖率（辅助定位疑似空白页/渲染失败页）、枚举每页图片对象与链接注解目标。统计正常不证明不存在缺字、重叠、局部裁切或跨页损伤。
- 辅助检查结论写入说明，只能提供候选 PDF 并报告“待人工视觉复核”缺口；真实视觉复核及其他既有完成条件闭合前，不得宣称正式交付完成，也不得把辅助检查记为视觉复核通过。模型具备图像输入时仍须真实目检，全部页面及细节检查范围沿用既有完成合同。

## 4. 直接验收

每项在实际交付路径核验；自动化测试与 torch.fx 样本复跑是机器证据，不替代直接验收。

验收前固定源 PDF、正向译文、golden、图片、权威清单及检查器的版本/摘要与口径，说明人工对账依据和已知缺口。当前 H1 缺英文原题的 torch.fx 译文保留为失败样本；正向样本须完成相应修正、回源复核与验收绑定，不能仅修正 H1 后凭脚本 PASS 认定全文有效。本节为待实施验收标准，不把历史交付记录当作本需求已通过的证据。

| 编号 | 场景 | 成功标准 |
| --- | --- | --- |
| A1 | 文字版论文 PDF（torch.fx 样本）源勘察 | 类型判定为文字版且证据留档（可靠文本层、0 嵌入位图、矢量绘图、0 批注对象）；结构清单候选生成，人工对账后 36 个标题、图 1–8、5 张表、1 条脚注全部定位 |
| A2 | 双栏正文与跨栏区域提取 | 两种模式快照落 `source/`；正文阅读顺序正确；致谢/参考文献等跨栏区域顺序经版面分析裁定且有记录 |

## 6. 范围与精简自检

- **非目标**：新增扫描版 OCR 能力（维持既有口径）、改变四类 HTML 家族行为、新增本需求之外的图片转换或降采样（既有获准口径不变）；公式自动提取/重建与位图素材自动提取按 D4、D3 不纳入。
- **基线**：第 1 节区分样本已有产物、人工对账工作与待补能力；项目的 0 批注对象、工具 API 差异、110/200 dpi 等仅为样本记录，不推导为其他 PDF 的事实。当前译文复验失败和已复现的校验漏检保留为基线，不将历史 PASS 当作当前或通用验收结论。
- **假设与差异**：经验来自单一论文项目，未在书籍、报告等其他形态验证；适用条件和校准常数均为项目经验。V0.2 按用户同意的意见撤回 V0.1 中“带视觉复核缺口正式交付”的表述，维持既有完成门禁；D1–D5 已随本版需求及设计获批，不构成计划或实施授权。
- **复用边界**：素材分治沿用代码回填与逐块比对、图片来源身份与离线验收；权威清单沿用独立回源对账，新增 PDF 来源依据；导出补强接入既有验收身份与交付检查，不建新的状态或证据体系。仅整篇提取文本不能交付图形；仅比较译文与提取结果不能证明提取完整；仅重跑硬检查不能证明验收版本未变。具体提取算法、接口与证据接入机制由后续设计确定。
