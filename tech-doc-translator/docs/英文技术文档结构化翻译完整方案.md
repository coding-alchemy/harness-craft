# 英文技术文档结构化翻译完整方案

> **文档版本**：2.0
> **文档状态**：现行方案与未来路线图
> **修订日期**：2026-08-30
> **适用范围**：计算机、工程、数学、物理等理工科英文技术文档
> **核心交付**：可回源核对、结构完整、资源可离线读取的中文 Markdown

本文说明 `tech-doc-translator` 已有能力、完整执行流程、验收标准和未来方向。它用于理解方案全貌；实际执行以 [Skill](../skills/tech-doc-translator/SKILL.md) 和 [翻译约定](../rules/translation_conventions.md) 为准，设计边界以 [Practice-first 设计](../specs/2026-08-29-tech-doc-translator-practice-first-design.md) 为准。

发生冲突时按以下顺序裁决：

1. 用户对当前任务的明确要求；
2. 当前项目的 Agent 指令、交付约定和 `术语表.md`；
3. 当前项目声明的基准项目术语及已批准译文；
4. `tech-doc-translator` Skill 与翻译约定；
5. 本文的一般建议和未来方向。

---

## 1. 目标、原则与边界

### 1.1 核心目标

用户最终应得到一组位于指定交付路径的中文 Markdown，满足：

- 范围、版本、章节顺序与权威源一致；
- 标题、代码、公式、图片、脚注和关键标识符没有无声丢失；
- 术语在同一语境内一致，疑似原文问题有可追溯处理；
- 合并文件和资源能够离线读取；
- 结构校验通过后仍完成技术语义复核。

完成验收需要同时满足上述可观察结果和相应的过程证据。

### 1.2 已验证原则

1. **先确认源，再翻译**：重定向、版本和范围错误会使后续全部工作失效。
2. **HTML 也会解析损伤**：必须从原始源独立统计关键结构，与解析结果对账。
3. **按源家族复用**：单页、分页、参考手册和 API 站点分别维护自身不变量。
4. **自然边界优先**：按页面、章节或完整小节拆包，保持结构和语义单元完整。
5. **全局决策集中**：页面顺序、图片身份、术语裁决和最终合并由主 Agent 持有。
6. **合并是新的出错面**：合并产物必须重新完整验证。
7. **结构与语义分别验收**：脚本发现确定性损伤，回源复核判断技术含义。

### 1.3 当前边界

当前交付由 Agent Skill 和内部脚本组成，以中文 Markdown 为默认产物。

## 3. 现有实现架构

```text
权威 URL / 文件
      │
      ▼
本地只读源快照 ── 官方 TOC / 范围基准
      │
      ▼
源家族解析器 ── 标题/图片/代码/公式总量与顺序对账
      │
      ▼
可读源 Markdown ── 项目术语表 ── 全局图片映射
      │
      ▼
自然边界工作包 ── 翻译 Agent 独立目标
      │
      ▼
逐包校验 ── 术语集中裁决 ── 回源语义复核
      │
      ▼
安全合并 ── 最终路径全量校验 ── 中文 Markdown + images/
```

模块分为四类：

| 组件 | 责任 | 代表文件 |
|---|---|---|
| Skill 与规则 | 决策顺序、停止条件、任务合同、翻译约定 | `skills/tech-doc-translator/SKILL.md`、`rules/translation_conventions.md` |
| 解析器 | 从本地源提取可翻译结构 | `parse_single_page_html.py`、`parse_paginated_html.py`、`parse_reference_html.py`、`parse_api_html.py` |
| 校验与合并 | 检查不变量、拼接代码和文件、定位损伤 | `verify_*.py`、`splice_fences.py`、`merge_*.py` |
| 工作包编排 | 拆分、术语候选合并、恢复 | `split_work_packages.py`、`merge_work_packages.py`、`merge_glossary.py`、`recover_work_packages.py` |

脚本按 Skill 的内部接口使用。

## 4. 完整执行流程

### 4.1 确认权威源与范围

1. 对 URL 运行 `curl -sIL`，记录最终落地 URL、版本和抓取日期。
2. 确认是否存在 Archive、legacy、deprecated 或新版迁移提示。
3. 以官方 TOC/导航界定章节范围；存在两种合理解释时请用户裁决。
4. 多页面文档准备独立官方 TOC/导航快照，并以它作为页面发现结果的对账基准。
5. 若计划公开发布，另行确认版权与再分发边界。

### 4.2 保存本地源快照

使用 `curl -sL` 或等价方式保存 HTML/PDF。解析器只读本地快照，避免翻译过程中远端页面变化。实际项目可把快照放在 `source/`；验收在用户指定的真实交付目录执行，`/tmp` 只承载回归过程。

### 4.3 建立项目口径

- 读取项目指令、`术语表.md`、基准项目和同构已译样文。
- 没有术语表时创建最小 Markdown 表：英文、中文/保留方式、语境/处理方式、首现位置。
- 只预置高频、标准或事后统一代价高的术语。
- 参考样例优先选择与目标模板同构的产物；存在结构差异时明确适用范围。

### 4.4 选择源家族并解析

先检查页面组织、标题深度、代码、公式、图片、表格、定义列表和标签页，再选择最接近的已验证脚本，并在代表页上校准后复用。

| 源家族 | 入口 |
|---|---|
| 单页 HTML | `parse_single_page_html.py <html> [section_id] <out.md>` |
| 分页代码文档 | `parse_paginated_html.py <page...>` |
| 数学/深层参考手册 | `parse_reference_html.py <html> <out.md>` |
| 多页面 API/DSL | `discover_pages.py` → `parse_api_html.py` → `merge_api.py` |

### 4.5 解析前后对账

分派翻译前，从原始 HTML/PDF 独立统计并按顺序核对：

- 标题及层级；
- `<pre>` / 代码围栏；
- 图片和图题；
- 块级与行内公式；
- 脚注、提示框、表格及其他关键块。

解析器遇到未识别块级结构时输出显式占位符；出现 `[TAGNAME]`、`[TABLE]` 等未处理标记时停止翻译，修复解析后重新提取。

### 4.6 资源本地化

主 Agent 建立全局图片身份和顺序映射：

- 图片下载或复制到最终 Markdown 旁的 `images/`；
- 无官方图号的图片使用描述性名称，`figure_NN` 保留给官方编号图片；
- 跨章复用同一资源并保持单一副本；
- 暗/亮图片对只嵌入一个可读版本，并记录取舍；
- 最终用魔数或 `file` 检查实际文件类型。

### 4.7 拆分工作包

小文档可由主 Agent 直接翻译；大文档按完整页面、章节或小节拆分，把切点放在代码、公式、表格及紧密语义结构之外。

每个工作包必须包含：

- `source_file`、唯一 `target_file`；
- `source_order`、`section_id`、`fragment_index`；
- 标题、列表、表格、围栏等脚本计数；
- 项目规则、相关术语、输出模板和特殊结构处理规则；
- 完成后返回的新术语、原文/解析问题、检查结果和不确定项。

计数断言由脚本生成；若与源文冲突，以源文为准并上报。

### 4.8 翻译

翻译必须遵循：

- 标题保留官方英文原题、编号和内容性字符，括号附中文；
- 代码围栏、标识符、命令、路径和选项逐字保留；
- 公式保持原内容，只翻译解释文字；
- 交叉引用保留官方节号，只复用原文已有的链接关系；
- 官方重复内容完整保留；确认源文本完全相同时才复用既有译文；
- 疑似原文错误先回源，技术性误导照录并按需加译注；
- 长句允许按语义拆分，段内硬换行先还原语义。

代码密集文档优先用 `splice_fences.py` 从源文程序化回填代码，避免手工转写。

### 4.9 逐包复验与术语裁决

每个工作包完成后，翻译 Agent 先自检，再由主 Agent 运行匹配源家族的校验器并独立复验；主 Agent 再把候选术语与全量术语表、基准项目和实际译文逐条对照。

同词多译先判断语境差异；确属冲突时按项目优先级裁决并检查全局实际用法。只有批准后的候选写入权威术语表。

### 4.10 合并、终验与交付

合并只做：

- 按源顺序拼接；
- 经批准的标题层级调整；
- 固定头部、分隔线和资源路径装配。

合并过程保留代码围栏内的原始空白，只执行感知围栏边界的格式处理。合并产物视为新文件，必须在最终交付路径重新运行全套结构校验和语义复核。

交付说明至少包括：源与版本、交付文件、术语变化、验证结论和仍保留的不确定项；模型、token 与墙钟时间仅在可获得时报告。

## 5. 解析保真规则

### 5.1 代码

- 解析前保护整个 `<pre>` 块；
- 块内只移除已知高亮标签，其余字符逐字保留；
- 代码密集路线按顺序逐块比对内容，以内容一致作为最终标准；
- 合并和格式化必须感知围栏边界。

### 5.2 公式

- 同时处理行内 `span.math` 和块级 `div.math`；
- 每个公式只使用一组 Markdown 或 LaTeX 定界符；
- 解析前后核对公式数量，关键公式必要时按内容比较。

### 5.3 表格、列表与定义结构

简单表格可直接转 Markdown；复杂 `rowspan` / `colspan` 表格允许根据官方页面重建。空单元格若承载“不支持/不适用”等含义，统一写为 `—` 并保留说明。

`dl`、`blockquote`、`li`、`dd` 等容器可能包含定义、脚注、图片、代码或多段内容，必须按实际 DOM 定性并选择对应转换。

### 5.4 原文与解析器问题

翻译 Agent 负责准确上报“公式缺失”“表格碎裂”等现象，主 Agent 回到权威源完成技术定性：

- 解析器损伤：修解析器并重新提取；
- 技术性原文错误：忠实照译，必要时加译注；
- 无害语法残缺：按明显本意顺句；
- 构件泄漏：照录或按项目规则处理。

## 6. 术语制度

### 6.1 权威来源

每个项目的 `术语表.md` 是权威来源。后续项目可声明基准项目。项目词表可以覆盖一般建议，同一英文词允许按语境记录不同译法。

### 6.2 三类基本处理

1. 有稳定中文定名：首现使用“中文（English）”，后文可纯中文；
2. 社区惯用英文：保留英文，如 kernel、warp、tile、PTX、stream；
3. 代码/API/产品名/版本/公式：原样保留。

具体口径始终以项目术语表为准。

### 6.3 候选与合并

翻译 Agent 只读权威术语表，并上报“英文、候选译法、处理方式、首现位置、语境”。主 Agent 使用 `merge_glossary.py` 检查新增、待定和冲突；只有批准清单中的候选才能写入合并结果。

自动候选抽取可以作为未来辅助，最终由人工或主 Agent 裁决。

## 7. 校验与验收

### 7.1 分层校验

| 层级 | 核心问题 | 结论方式 |
|---|---|---|
| 源与范围 | 版本、页面和章节是否闭合 | 与最终 URL 和独立官方 TOC 对账 |
| 解析保真 | 关键结构是否从 HTML/PDF 进入源 Markdown | 总量、顺序、占位符和代表内容检查 |
| 翻译结构 | 标题、代码、公式、图片、脚注、强 token 是否损伤 | 硬不变量失败即阻塞 |
| 重建漂移 | 表格、列表、段落是否因合法转换变化 | 逐小节定位、解释并人工定性 |
| 技术语义 | 数字、单位、条件、否定、指代、术语是否正确 | 回到权威源复核 |
| 最终交付 | 合并文件和资源在真实路径是否完整 | 从最终 Markdown 目录重新验证 |

### 7.2 硬不变量与告警

硬不变量至少包括：

- 标题数量、层级和顺序；
- H1 等项目结构约束；
- 代码围栏配对及代码密集路线的逐块内容；
- 公式、图片顺序/存在性/有效性；
- 脚注引用与定义配对；
- 项目指定的 API、枚举和强 token。

段落、列表、表格和“语义块总数”可能因合法重建漂移。每项漂移都要定位到具体小节并人工定性。token/字母多重集用于发现潜在损失，最终结论由结构对账和语义复核共同给出。

### 7.3 语义复核重点

- 数字、单位、版本和范围；
- 否定、条件、例外和比较关系；
- 代词指向与跨节引用；
- 术语首现和同语境一致性；
- 表格重建后的列归属和空值含义；
- 原文瑕疵、译注与解析告警。

任何内容、术语、合并或校验脚本修改都是新的出错面；修复后重跑受影响检查。校验脚本修改后先用已知正确样本回归，再验证新产物。

### 7.4 当前回归入口

模块包含五组离线回归：

- `tests/run_single_page.sh`；
- `tests/run_paginated.sh`；
- `tests/run_reference.sh`；
- `tests/run_multipage_api.sh`；
- `tests/run_work_packages.sh`。

这些测试分别覆盖正确路径和故障路径，包括未知块、链接/公式损伤、代码剥离、漏图、漏强 token、页面不闭合、工作包映射错误和中断恢复。

## 8. 失败、恢复与并发

### 8.1 必须停止的情况

- 权威源、范围或版本未确认；
- 解析后的关键结构无法与源对账；
- 校验器报告未修复的 FAIL；
- 术语冲突可能改变技术含义且未裁决；
- 合并后尚未重新完整校验。

### 8.2 从文件事实恢复

恢复以文件事实为准：

1. 重新从源生成预期工作包；
2. 检查目标译文是否存在、完整且通过计数/结构验证；
3. 只复用验证通过的文件；
4. 缺失、截断、源已变化或无法独立验证的工作包重新处理；
5. Agent 失败但留下产物时，先验证产物再决定是否补派。

### 8.3 动态并发

并发服从用户当前上限，并结合账户负载、宿主能力、在途任务和近期限流表现动态决定。限流后保留在途任务，等待在途数下降再补派；每轮按当前状态重新计算并发数。

## 9. 推荐项目形态

项目可以按实际需要调整目录，最小交付通常包括：

```text
<project>/
├── source/            # 建议保留的权威源快照
├── 术语表.md          # 项目权威术语
├── <chapter>.md       # 独立章节或最终合并译文
└── images/            # 最终 Markdown 的本地图片
```

工作包、解析中间文件和回归产物可以位于项目内约定目录或工作区外临时目录。真实交付路径承担最终验收；额外元数据按项目实际需要增加。

## 10. 未来路线图

未来能力遵循“真实任务先行”：只有出现明确用户需求和代表性验收样本时才进入实现。

### 10.1 文本型 PDF

触发条件：没有权威 HTML，且 PDF 文本、阅读顺序、公式和代码可被可靠提取。

实施方向：

1. 用宿主 PDF 工具生成保留页码和结构的 Markdown；
2. 建立 PDF 原文与转换结果的标题、公式、代码、图片基线；
3. 为真实文档补一个 PDF 源家族解析器和回归；
4. 沿用现有工作包、术语、合并和语义复核流程。

### 10.2 扫描 PDF / OCR

用户明确要求且现有文本源质量不足时启用。先对少量页面试点并量化损伤，把 OCR 输出与页面视觉结果逐项对照；达到代码、公式和表格的质量门槛后再扩展到全文。

### 10.3 动态页面

触发条件：`curl` 获取的 HTML 缺少正文或关键交互内容。届时可增加浏览器渲染后的 DOM 快照，但后续仍复用现有源家族适配、对账和验证原则。

### 10.4 官方版本增量维护

触发条件：同一文档出现第二个需要维护的官方版本。

实施方向：保存版本化源快照，按页面、标题和关键块定位变化；程序化证明源文一致的内容复用旧译文，变化内容重新走术语、翻译和校验，并在发布前完成结构与语义复核。

### 10.5 术语候选辅助

当项目规模使人工发现候选成为瓶颈时，可增加缩写、API、枚举和高频概念扫描。输出进入候选区，由主 Agent 批准后写入权威术语表。

### 10.6 出版与 PDF 交付

只有用户明确要求时，才在 Markdown 终验之后增加渲染层。渲染产物必须可由已验收 Markdown 重建；Markdown 修改后重新校验并重新渲染。排版工具、字体和模板根据交付环境选择。
