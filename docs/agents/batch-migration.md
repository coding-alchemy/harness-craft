# 大需求分批迁移流水线

适用于：大需求先在**原始开发分支**形成成果，再按可独立验收的小需求，经**迁移分支**分批进入主分支；每批合入后，将最新主线 rebase 回原始开发分支，最后处理剩余增量。本文件是操作流程，不替代 [AGENTS.md](../../AGENTS.md) 的授权、Git 安全与规格规则，也不构成任何阶段的批准。

执行前核对任务是否采用上述分支角色与分批合入关系；条件不成立时按 AGENTS.md 的通用规则处理，不进入以下步骤。

若任务只要求规划，完成下节并停在计划交付点；若用户已将迁移分支合入主线、只要求 rebase，先做第 1 步状态核对，再从第 9 步继续，并核对前期验收是否仍适用。

## 启动与分批

1. 核对原始开发分支、主分支、远端跟踪引用、工作树和已有备份的实际状态，记录完整 SHA 与共同祖先。发现未提交或未知改动时，先查清归属，不覆盖或丢弃。
2. 从获准需求与设计拆出本批可独立验收的结果，列出依赖、正反例和本批之外仍留在原始开发分支的范围。按 [issue-tracker](issue-tracker.md) 维护对应规格、计划与 tickets；需求、设计、计划和执行分别遵守 AGENTS.md 的门禁。
3. 建立逐文件清单：整文件迁入、块级迁入、保持主线、暂留原始开发分支、删除的重复内容。交集文件写明每块取舍；无法解释的差异不进入提取。

**完成条件：** 本批目标、排除范围、直接验收与授权明确；基线可按 SHA 回查。仅获计划批准时停在计划交付点。

## 修复来源并提取迁移分支

4. 本批发现的来源缺陷先在原始开发分支复现、重审并修复，再把受影响实现与测试回提迁移分支，不在两边独立发明不同版本。同一机制连续修复仍出问题、改变持久合同或扩大职责时，先按 AGENTS.md 记录正常/失败事实、根因与收敛选择。
5. 从已核实的目标主线建立本批迁移分支，按清单仅提取本批实现、必要整合、测试和使用文档。对照修复来源核对回提内容；相对主线的每项增量都须归属本批需求。额外 worktree 与主分支操作遵守 AGENTS.md 的 Git 边界。

**完成条件：** 迁移分支的代码与来源修复一致或差异已解释；未迁移需求、计划产物和运行日志没有混入。

## 评审、验收与文档收尾

6. 在迁移树分别做规格符合性和仓库标准评审，并对实现及全部评审建议做 Karpathy 终审。以真实正常/失败场景判定阻断项；修复后复审受影响范围，直到阻断项闭合。
7. 在迁移树直接运行本批正反例、受影响测试、完整回归及适用的真实集成链路。区分本次实测、代码未变而可沿用的历史证据与未验证范围。日志和临时证据按 AGENTS.md 放在工作区外。
8. 归并需求状态、设计、使用文档和 CHANGELOG：只记录最终行为、兼容变化、限制与验收；同一未发布版本不按修复轮次累积条目。仅当所属计划的全部用户可观察结果和直接验收已满足，才按 issue-tracker 删除已完成计划并同步索引。

**完成条件：** 评审无阻断，核心结果直接验收通过，文档状态与实际一致；交付迁移分支 SHA、范围清单、差异统计、验证证据和剩余缺口。主线合并须符合当前授权；未合入时停在交接点。

## 主线合入后回收重复增量

9. 核对远端主线确已包含本批最终产品内容。若采用 squash 合并，用最终树和范围比对确认，不能只凭原迁移提交是否成为主线祖先判断。
10. 在 rebase 前确认原始开发分支工作树干净，并创建不覆盖既有名称的备份引用。将已核实的最新主线 rebase 回原始开发分支；逐块解决冲突，保留主线已评审实现及原始开发分支独有的未迁移需求。
11. 对照备份分支与新主线审计剩余差异：已迁移代码没有第二套实现，未迁移代码、测试与规格没有误删或弱化。检查冲突标记、差异与适用回归。远端历史若因 rebase 分叉，强制推送逐次按 AGENTS.md 取得明确确认。

**完成条件：** 主线是原始开发分支祖先；剩余增量均有未迁移需求归属，工作树与远端状态已报告。记录 rebase 前后、备份和主线完整 SHA，以及冲突取舍和验证结果。

## 重复与最终合入

12. 下一批重新从“启动与分批”开始，先核对新主线和剩余需求，不沿用已经失效的 SHA、授权或验收结论。
13. 所有批次处理后，审计主线与原始开发分支的最终差异。差异非空时，对真正剩余的需求执行同等评审、直接验收和主线交接；差异为空时，无须为了合并而制造提交。

每个停止点报告：完整 SHA、迁入/排除/保留范围、直接验收、未解决问题、工作树与远端状态，以及下一步依赖的授权或外部合并事实。测试通过、提交存在或计划删除不能单独证明需求完成。
